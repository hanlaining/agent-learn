## 2. 硬目标与放行条件

### 2.1 工程 95+ 硬目标

只有同时满足以下条件，才可以把工程覆盖率写成达到 95%：

1. 122 个源码文件口径不变。
2. 覆盖率分母不通过排除源码、删测试、改脚本、改阈值或修改统计规则来改变。
3. 源码行覆盖率连续两次独占运行均不低于 95.00%。
4. `npm run check`、`npm run test:discovery`、`npm test`、`npm run test:coverage` 均通过。
5. 两条条件 skip 的条件和原因仍被最终报告明确记录。
6. 每个新增覆盖行都由行为测试触发，禁止空 import 或只为覆盖率执行的无意义测试。

### 2.2 总体 95+ 不能只靠覆盖率

工程覆盖率达到 95% 不代表五项评分自动达到 95，也不代表科研、论文或生产放行。以下证据仍需分别完成：

- 同 SHA 远端 CI、干净 Windows 和第二机器证据；
- 真人计时彩排至少 3 次、非作者试讲至少 1 次；
- 真实 Provider 正式实验、正式 Raw、formal Verified、外部基线和独立复现；
- 论文引用核验、论文级审阅；
- 签名安装包、干净机安装、升级回滚和长稳运行。

缺少这些外部条件时，相关项目必须保留 No-Go，不得以文档、评分或本机 Mock 替代。

## 3. 分阶段执行顺序

### 阶段 A：中断与取消状态收口

目标：避免循环容错把不同原因错误显示成“中断”或长期停在 `cancelling`。

最小切片顺序：

1. 区分用户主动取消、总时限超时、Provider `AbortError`、Provider 普通错误和 `outcome_unknown`。
2. 验证迟到 Model/Tool 响应不能覆盖已收口终态。
3. 验证启动恢复的遗留 `running` 显示为独立的等待恢复事实，不冒充用户取消。
4. 验证取消 RPC 与自然完成竞态不会长期停在 `cancelling`。

每个切片必须经过：行为测试 → 专项测试 → `npm run check` → 正式 coverage。

### 阶段 B：覆盖率补强到 95%

按真实行为优先级补齐：

1. `src/app-server/main.ts`；
2. `src/cli/main.ts`；
3. Runtime Store、lease、lifecycle 和恢复循环；
4. MCP、命令工具和 Electron IPC；
5. 迟到响应、终态保护、恢复等待和失败分类。

每个切片的回滚点是该切片修改前的工作区状态；不得覆盖用户已有修改。

阶段 B 结束条件：连续两次独占 coverage ≥95.00%，且分母仍为正式源码口径，并在报告中说明任何自然变化来源。

### 阶段 C：本机完整门禁

### 阶段 D：外部证据补齐

本机不能自动完成的证据必须由真实环境、真实参与者或独立执行者提供。每项证据必须绑定候选版本或 SHA、采样时间、环境身份、原始记录、可复核派生结果以及明确边界。

Fake/Mock 只能继续标记为离线防御或 local pilot，不能升级为真实 Provider、正式实验或独立复现。

## 4. 当前已完成的相关修复

- 启动恢复不再把遗留 `running` 会话伪装成 `cancelled`，独立显示 `interrupted / 等待恢复`。
- 取消 RPC 与自然完成竞态会读取持久终态，避免状态长期停在 `cancelling`。
- 真实 App Server 畸形 stdin 输入会输出协议错误并安全关闭。

这些修复只证明本机行为边界改善，不改变科研正式性、独立复现或生产放行结论。

## 5. 最小下一切片

为 `AgentLoop` 增加一组取消/超时/Provider `AbortError` 分类回归：

- 用户取消 → `interrupted` / 取消语义；

- Provider 普通错误 → `failed`；
