# Runtime 本机压爆与短时持续容量基线（2026-08-19）

> 全部结果来自 `deterministic-local-fake-provider (NO NETWORK / NO PAID PROVIDER)`，只衡量本机 Runtime 控制面。30 秒运行属于 short-soak，不是长期 soak；不得外推真实模型 Provider、网络限流或长期生产容量。

## 环境与可复现入口

- Windows `10.0.26200` x64，Node `v20.19.0`
- Intel Core i7-12700H，20 logical CPU，约 16 GB RAM
- Benchmark v1.0.0，Schema v1；Git commit `512d7a8f3742d5a8e049c63e03cfac8f58b16852`（测试实现未提交，`dirty=true`）
- Spike：每 Job 最多 10 Task、全局并发最多 32、2 ms Fake 延迟、单档墙钟 30 秒
- Duration：固定并发、有界 in-flight、每 5 秒窗口、结束后完整 drain

```powershell
npm run capacity:runtime -- --levels 20,100,500,1000,2000,5000 --label local-bounded-spike-safe-stop
npm run capacity:runtime:short-soak
npm run capacity:runtime:short-soak:shaped
```

S5 在 30 秒墙钟门禁触发后停止派发，2,802 Task 未启动；已经启动的 2,198 Task 全部成功。所有档位成功率 100%、重复 Return 0、丢失 Return 0、lease 恢复探针通过。

**Spike 裁决**：稳定安全批次建议 100 Task；500 Task 是首个吞吐退化档。2,000 Task 可以在 30 秒内完成但已严重退化，不应作为安全值。5,000 Task 明确触发主动超时拐点。

**Short-soak 裁决**：在 100 ms Fake 响应模型下，建议短时持续并发为 4，并发 8 是首个退化档。这个数字只对当前机器、当前代码和 30 秒窗口成立，不是长期容量。

## 调优建议

1. 对 Return `idempotencyKey`、Job、Task 建立直接索引，避免对象量增长后反复全表扫描。
2. 按 Job 分区 Runtime 数据，并为已消费 Return、历史 Evidence 和完成 Run 设置可审计的保留/压缩策略。
3. 持续运行时增量消费 Return，避免直到末尾才形成集中 outbox；保留 drain 正确性门禁。
4. 用 CPU profile/火焰图确认线性扫描与序列化热点，再优化数据结构，不能只靠增加并发。
5. 优化后重复本套 Spike 与 short-soak，再补 30 分钟、2 小时和带真实 Provider 限流的长期测试。
