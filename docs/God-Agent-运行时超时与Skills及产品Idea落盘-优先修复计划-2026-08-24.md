# God-Agent：运行时超时、Skills 接入与产品 Idea 自动落盘计划

> 任务标题：God-Agent 最新版运行时稳定性与新手友好交付调整  
> 计划日期：2026-08-24  
> 计划边界：先解决“能稳定运行、能找到我的 Skills、产品 Idea 有 Markdown 文件可打开”三个问题；本文件只做方案，不开始业务代码执行。

## 0. 先区分用户请求与截图内容

截图不是一份需要照做的外部指令，只是本次故障证据。截图中真正可确认的信息是：

- God 桌面端显示“Turn 已超时”；
- 输入框仍可用，但当前轮没有给出可交付的计划文件入口；
- 不能仅凭截图推断 API Key、模型、网络或具体 Skill 内容。

本次以用户明确提出的三项要求为最高优先级：

1. 解释并修复最新版 God 的超时体验；
2. 让用户自己的 Skills 能被 God 发现和使用；
3. 产品 Idea 默认整理成可打开、可追踪的 `.md` 计划，而不是只返回长文本。

## 1. 当前事实与根因判断

### 1.1 “Turn 已超时”的直接原因

当前 Agent Loop 的默认整轮上限是 `120000ms`（2 分钟）；OpenAI Responses Provider 默认请求上限也是 `120000ms`。一轮中还可能叠加：

`澄清需求 → 读取 Skill → 模型思考 → 工具调用 → 写计划 → 汇总回答`

因此，产品 Idea 或长任务在正常工作时也可能超过 2 分钟。当前界面把结果压缩成“Turn 已超时”，没有把“卡在哪一步、是否已经生成草稿、能否继续”讲清楚。

### 1.2 为什么没有看到你的 Skills

最新版 God 项目内目前只发现 2 个 Skill：

- `clarify-before-execute`
- `finance-analysis`

God 的 Skill Loader 默认只扫描 `<workspace>/skills/<skill-name>/SKILL.md`，或扫描 `AGENT_SKILLS_PATH` 指定的根目录；它不会自动继承 Codex 全局目录 `C:\Users\dell\.codex\skills`，也不会自动把插件缓存里的 Skills 全部复制进项目。

官方 OpenAI 文档也区分了“全局 Skills”和“仓库/项目 Skills”：Skills 只有在对应目录被加载后，God 才能发现其元数据，再按需读取完整 `SKILL.md`。

### 1.3 为什么产品 Idea 变成长文本

源码里已经有 `prepare_requirement_plan` 和 `RequirementPlanWriter`，但它是一个“模型必须主动调用”的工具，不是每条长文本自动转换器。当前计划默认写到：

`C:\Users\dell\AppData\Local\god-agent\plans\`

这会造成两个问题：

1. 如果模型没有调用 `prepare_requirement_plan`，就只会产生普通聊天长文本；
2. 即使已经写入，文件在用户不熟悉的 AppData 目录，用户会以为没有记录。

因此，本次不把问题归咎于用户操作，按“运行时没有强制计划交付、路径不可见、超时没有草稿恢复”处理。

## 2. 调整后的优先级

### P0：产品 Idea 必须先落成 Markdown 计划

默认识别以下请求为“产品 Idea / substantial requirement”：产品构想、做一个应用、页面/功能方案、完整软件交付、需要多个步骤或需要文件记录的请求。

固定流程：

1. 父 Chat 先澄清目标、范围、不做内容、交付物和验收标准；
2. 自动调用 `prepare_requirement_plan`；
3. 在可见的工作区计划目录生成一个版本化 `.md`；
4. 聊天中只给“已生成计划 + 文件路径 + 计划摘要”；
5. 必须等用户点击或明确选择“确认执行”，才允许改代码、跑命令、创建子 Agent 或发布内容。

普通问答、简单事实查询和一句话改字不强制生成计划；用户明确说“只聊想法”时只记录讨论，不执行。

### P0：把用户 Skills 做成显式、可验证的导入清单

推荐建立一个独立的用户 Skill 根目录，例如：

`D:\练手\agent-learn-god-latest-audit\skills-user\`

只导入用户明确需要的 `hln-*`、`lov*` 等 Skill，保留原始来源，不复制密钥、缓存、插件运行时和系统内部 Skill。运行时通过 `AGENT_SKILLS_PATH` 配置项目 Skill 根目录与用户 Skill 根目录，并在启动卡片中显示：

- 已发现 Skill 数量；
- 每个 Skill 名称与描述；
- 来源根目录；
- 解析失败原因；
- 当前任务实际使用了哪些 Skill。

不建议直接把整个 `C:\Users\dell\.codex\skills` 无筛选复制进 God：其中包含 Codex 专用、浏览器专用、插件专用和系统维护 Skill，部分依赖 God 当前没有的工具；盲目复制会制造“看似加载、实际不能执行”的假成功。

### P0：超时改成“可配置 + 可继续”，不只是把数字调大

建议分层配置：

| 层级 | 第一版建议值 | 规则 |
|---|---:|---|
| 单次 Provider 请求 | 180 秒 | 网络/模型无响应时停止该请求，并保留调用事实 |
| 普通用户 Turn | 10 分钟 | 覆盖澄清、Skill、计划生成和一次汇总 |
| 复杂产品 Turn | 15 分钟 | 仍受取消按钮和阶段级心跳约束 |
| 工具调用 | 2 分钟 | 工具单独超时，不拖死整轮 |

超时后的行为必须是：保存已生成的需求草稿、保留运行阶段和错误原因、显示“继续生成计划/重新开始/停止”三个清晰选项；不能静默重放模型请求，也不能把可能已经产生的外部副作用当成未发生。

### P1：修复“源码已更新但运行的是旧构建”的风险

启动时显示以下版本信息：

- 当前 worktree 路径；
- Git commit 或本地构建时间；
- App Server 与 Renderer 构建版本；
- 实际加载的 Skill 根目录与计划目录。

启动前执行一次 `check → electron:build → 启动` 的一致性检查，避免源码已经有计划卡片，但桌面端仍运行旧 `dist` 或旧 Renderer 的情况。

## 3. 建议的实施切片

### Slice A：先修交付语义（最高优先级）

- 目标：所有产品 Idea 都能看到 `.md` 计划路径和“打开计划”入口。
- 预计改动：需求识别/计划工具调用边界、计划目录配置、桌面计划卡片、聊天摘要文案。
- 验证：输入“我有一个产品 Idea，请先给我方案”，必须生成 `.md`，状态为“等待确认”，不能执行代码。
- 回滚点：保留现有 `RequirementStore` 和 `RequirementPlanWriter`，只撤回强制触发与路径展示层。

### Slice B：接入并验收用户 Skills

- 目标：用户 Skill 根目录可配置、可列出、可按需读取，并能在一次测试任务中留下使用记录。
- 预计改动：Skill 根目录配置、来源清单、启动诊断、Skill 使用事件。
- 验证：启动显示导入清单；显式选择一个用户 Skill 后，模型先调用 `read_skill`；未知 Skill 被明确拒绝。
- 回滚点：恢复只加载项目内 `skills/` 的安全默认值，不删除源 Skills。

### Slice C：超时与续跑

- 目标：长任务不再在 2 分钟时直接变成无上下文失败。
- 预计改动：Turn/Provider/Tool 分层超时配置，阶段心跳，超时后的草稿保存和继续入口。
- 验证：Fake Provider 延迟超过单次请求上限时，得到可解释错误；超过整轮上限时，需求草稿和恢复按钮仍存在；取消后不产生重复模型调用。
- 回滚点：保留现有 120 秒默认值作为兼容开关，关闭续跑时仍能安全失败。

### Slice D：新手验收与文档

- 目标：不懂代码的用户只需要看状态、点按钮、打开文件即可完成验收。
- 预计改动：新手操作说明、启动诊断页、计划路径复制/打开按钮、故障提示文案。
- 验证：不看源码，仅按界面提示完成“输入 Idea → 打开 md → 点击确认执行 → 查看结果”。
- 回滚点：文案和入口均可独立回退，不影响 Runtime 状态机。

## 4. 验收标准（面向不懂代码的用户）

- 输入产品 Idea 后，聊天不再只返回长文；必须出现计划卡片和可打开的 `.md` 文件。
- `.md` 文件默认位于当前项目可见的计划目录，聊天中同时显示完整路径。
- 用户未确认前，不会修改项目、运行命令、创建子 Agent 或发布内容。
- “Skills”面板能显示用户 Skill 数量、名称、来源和不可用原因。
- 任务超过单次请求或整轮时，界面明确显示阶段、已保存内容和下一步按钮。
- 重启 God 后，历史需求、计划路径、确认状态和超时原因仍可恢复。
- 旧的普通问答仍可正常使用，不会被强制生成无意义的计划文件。
- 全量检查、需求计划测试、Skill Loader 测试、Electron UI 测试和超时恢复测试通过。

## 5. 用户可直接照做的验收步骤

1. 打开 God 最新版，先看“Runtime 能力”里是否能看到 Skills 数量和计划目录。
2. 新建 Chat，输入：`我有一个产品 Idea，请先整理成方案 md，不要改代码。`
3. 等待计划卡片出现，点击“打开计划”，确认文件是 `.md`，内容包含目标、范围、交付物、验收标准和执行步骤。
4. 不点击“确认执行”，检查项目文件没有被修改。
5. 再点击“确认执行”，观察任务状态、超时提示和最终结果。
6. 关闭并重新打开 God，确认该计划仍在历史中，路径仍可打开。
7. 输入一个明确的用户 Skill 名称，确认界面显示“已使用 Skill：xxx”；输入不存在的名称，确认收到清晰的不可用提示。

## 8. 需求修订 v2：设计确认后，工程默认并行 3 个 Chat

本节覆盖对原计划的新增要求：工程阶段需要细化前端、后端，并默认同时启动 3 个工程 Chat。它不是让 3 个 Chat 重复做同一件事，而是让 3 条互相有边界的工程工作流并行推进。

### 8.1 修订后的完整流程

```text
用户输入产品 Idea
  → God 澄清需求并生成需求方案.md
  → 用户确认需求
  → 产品 Agent 制作产品原稿
  → 生成 Mock 交互预览
  → 用户查看、反馈、确认设计稿
  → God 冻结设计版本和设计稿哈希
  → 父 Agent 默认创建 3 个工程 Chat
      ├─ Chat 1：前端工程
      ├─ Chat 2：后端/API/数据工程
      └─ Chat 3：联调、测试、构建与运行保障
  → 3 个 Chat 并行执行各自任务
  → 各 Chat Return：变更文件、测试证据、风险和启动方式
  → 工程负责人做联调验收
  → 测试 Agent 对照设计稿和交互原型独立验收
  → 不通过则只返工对应 Chat
  → 通过后由 God 汇总并交付
```

### 8.2 三个工程 Chat 的职责

| 默认 Chat | 负责内容 | 不负责内容 |
|---|---|---|
| 前端工程 Chat | 页面、组件、状态管理、交互、响应式、前端测试 | 不擅自改后端契约，不改变已确认的设计稿 |
| 后端工程 Chat | API、数据结构、业务逻辑、权限、服务端测试 | 不直接改前端页面，不改变产品交互 |
| 联调/质量工程 Chat | 前后端接口联调、构建启动、端到端测试、环境与回归记录 | 不替前端或后端大范围重写代码 |

如果某个产品没有后端，第二个 Chat 转为数据/本地状态工程；如果没有复杂联调，第三个 Chat 转为测试、构建和交付保障。默认数量是 3，但不制造无意义的重复工作。

### 8.3 并行规则

- 默认配置：`engineeringChatCount = 3`。
- 三个 Chat 必须拥有独立的任务合同、文件边界和 Return 记录。
- 前端与后端可以并行；联调 Chat 必须等双方接口/页面契约至少冻结后再进入联调子阶段。
- 同一个文件不能被两个工程 Chat 同时写入；共享内容通过任务合同、共享数据板和版本化接口契约传递。
- 任一 Chat 失败，只重试或返工该 Chat，不自动重跑其他已通过的 Chat。
- 只有设计稿已获用户确认，三个工程 Chat 才能获得正式前端/后端写入权限。

### 8.4 需要调整的实现位置

1. `skills/clarify-before-execute/SKILL.md`：增加“需求确认”和“设计确认”两个独立确认点，并规定设计确认前不得创建可写工程 Chat。
2. `src/agents/agent-profile.ts`：把工程角色细化为 `frontend_engineering`、`backend_engineering`、`integration_quality` 三种角色。
3. `src/execution/workflows/software-product-delivery.ts`：把阶段改为“产品原稿 → Mock 预览 → 用户设计确认 → 三路工程并行 → 联调 → 独立质量验收 → 负责人汇总”。
4. Workflow Coordinator / Team Execution Engine：增加 fan-out/fan-in，默认并行度为 3，并保存每个 Chat 的独立 Attempt、Lease 和 Return。
5. `src/electron/renderer/App.tsx` 与桌面类型：显示 3 个工程 Chat、各自状态、变更文件、测试结果、失败原因和返工按钮。

### 8.5 新增验收标准

- 用户确认设计稿前，看不到“开始前端开发/后端开发”的执行状态。
- 用户确认设计稿后，默认出现 3 个工程 Chat，而不是一个笼统的“工程 Agent”。
- 前端 Chat 和后端 Chat 能并行运行，并且各自只能修改授权范围内的文件。
- 第三个 Chat 能看到前后端契约，并负责联调、构建和回归记录。
- 一个 Chat 失败时，其他已通过 Chat 不被重复执行。
- 父 Agent 汇总时必须列出三个 Chat 各自的变更、测试和风险。
