# God-Agent 下一阶段详细执行计划

> 日期：2026-08-18
> 当前基线：父子团队恢复、Model Invocation WAL、Tool Invocation WAL、启动恢复已完成本地实现与回归验证。
> 总目标：把“单进程下可恢复”推进到“多进程可协调、异常可人工处置、真实 Provider 可控验证、科研实验可复现”。

## 1. 当前完成基线

### 1.1 父子团队恢复

- V2 工作流支持 `resume(jobId)` 与 `recover(jobId)`。
- 自动启动恢复默认零付费；显式恢复才允许继续模型阶段。
- 已完成阶段不重复模型调用，终态 Job 重复恢复保持幂等。
- V2 Return 与动态团队 Return 分流，避免父 Continuation 误消费。
- 恢复循环具有 32 步上限和无进展停止条件。
- Job 进入 `completed` 前必须校验 Checkpoint、Evidence 和 Return 引用。

### 1.2 Model Invocation WAL

- 状态链：`prepared -> submitted -> response_received -> committed`。
- 中断链：`submitted -> outcome_unknown`。
- 使用稳定 invocation identity 与参数摘要；Provider API Key、Authorization/Cookie 等认证字段不进入快照。
- `response_received` 可在重启后零 Provider 重放完成提交。
- `committed` 直接跳过；`outcome_unknown` 默认禁止自动重发。
- App 的 WAL Provider 配置 `maxRetries: 0`：一次 `submitted` 最多对应一次 POST；超时、网络错误、429/5xx 不在 Invocation 内隐藏重试。
- 已覆盖首次模型调用、工具续接、格式修复与上下文压缩。

### 1.3 Tool Invocation WAL

- 状态链：`prepared -> executing -> result_received -> committed`。
- 中断链：`executing -> outcome_unknown`。
- 稳定身份由 `modelInvocationId + callId + toolName + argumentsDigest` 组成。
- 工具执行前、结果返回后、Lifecycle ToolResult 写入后分别持久化。
- `result_received/committed` 重启后零工具重放；未知副作用默认阻断。
- Snapshot 已升级为 v6，并兼容 v1-v5。

### 1.4 当前验证基线

- TypeScript 静态检查通过。
- 10 组恢复专项测试共 73/73 通过。
- `npm test` 的 pretest 19/19、主测试 397/397 通过。
- `git diff --check` 通过。
- 未调用真实付费 Provider。

### 1.5 Runtime Snapshot 数据边界

- 为了崩溃恢复和可审计重放，Runtime Snapshot 按设计保存 Lifecycle 中的用户原文、Model 返回文本、Tool 调用参数以及 Tool 结果/输出。
- Provider API Key、Authorization、Cookie、access token 等凭据或认证头必须排除或按字段替换为 `[REDACTED]`。
- 这不是“业务内容全面脱敏”：需求、代码片段、路径、论文文本和工具业务结果仍可能原样存在于本地状态文件中。状态文件必须按含用户业务数据的敏感本地资产保护，不能公开上传或直接作为论文附件发布。

## 2. 仍需解决的工程边界

1. 当前互斥只覆盖单进程，两个应用实例仍可能同时恢复同一工作。
2. `outcome_unknown` 只能阻止自动重试，不能确认外部副作用究竟执行了 0 次还是 1 次。
3. Provider 是否支持幂等键、结果查询和取消取决于外部接口，客户端 WAL 不能等同于 Provider exactly-once。
4. 现有测试以确定性 Mock 为主，尚缺真实 Provider 的小预算、可审计冒烟。
5. 尚未形成固定数据集、指标定义、实验脚本和论文可引用的复现证据。

## 3. 总体推进顺序

```text
当前恢复基线
  -> A. 跨进程 Lease/CAS
  -> B. outcome_unknown 人工处置
  -> C. Provider 能力探测与受控冒烟
  -> D. GATE-30 快速门禁
  -> E. GATE-100 正式科研基准
  -> F. 论文实验、复试演示与公开材料
```

A 与 B 可以并行开发；C 的离线框架可以并行，但真实请求必须等待预算批准。D 可先基于当前能力设计，正式基线应在 A、B 合入后运行。E 只使用冻结版本和固定数据集。

### 并行前契约冻结

总控先冻结四个最小契约，后续任务只能通过兼容扩展演进：

- `RecoveryDecision`：恢复动作、事实指纹、期望版本、是否允许付费/副作用。
- `OutcomeIncident`：未知调用身份、风险级别、证据引用、处置状态和审计版本。
- `ProviderCapability`：幂等、查询、取消、重试与计费能力声明。
- `BenchmarkRunRecord`：代码版本、数据集、seed、配置、指标与复现包引用。

文件所有权保持互斥：A 不改 UI/Provider/research；B 不改 Lease 和 LLM adapter；C 不改 Runtime 状态机/UI；D 优先只新增 research、runner、fixture 和测试。跨边界需求先由总控调整契约，避免四个任务互相覆盖。

## 4. Phase A：跨进程持久 Lease 与 CAS

### 目标

保证两个 God-Agent 进程同时启动或恢复时，同一个 Job、Turn、Model Invocation、Tool Invocation 在同一时刻只有一个合法 Owner；旧 Owner 即使恢复运行，也不能提交迟到结果。

### 实现切片

#### A1. Lease 数据模型

- 字段：`resourceType`、`resourceId`、`ownerId`、`leaseVersion`、`fencingToken`、`acquiredAt`、`renewedAt`、`expiresAt`。
- 所有时间通过可注入 Clock 获取，测试不依赖真实等待。
- 旧 Snapshot 没有 Lease 时按“无人持有”读取，不破坏兼容性。

#### A2. 原子协议

- `acquire(resource, expectedVersion)`：CAS 成功后返回新 fencing token。
- `renew(resource, owner, fencingToken)`：仅当前 Owner 可续租。
- `release(resource, owner, fencingToken)`：仅当前 Owner 可释放。
- 过期接管必须增加 fencing token；旧 token 的任何提交都被拒绝。

#### A3. 恢复链路接线

- App 启动恢复、显式 `resume/recover`、Model WAL 提交、Tool WAL 提交统一校验 Lease。
- 持有 Lease 的进程崩溃后，其他进程仅在过期后接管。
- 一次只推进一个可持久化步骤，成功持久化后再续租或释放。

### 测试

- 两实例同时 acquire，只有一个成功。
- Owner 续租后其他实例不能接管。
- Lease 过期后新 Owner 接管并获得更高 fencing token。
- 旧 Owner 的迟到 `response_received/committed` 被拒绝。
- 进程崩溃、重启与旧 Snapshot 兼容。
- 100 次竞争循环无双提交。

### 验收门槛

- 竞争测试中 `duplicateCommit = 0`。
- 旧 Owner 迟到写拒绝率 100%。
- TypeScript、专项测试、全量测试全部通过。
- 不引入后台无限轮询；Lease 过期与退避均有上限。

### 科研数据

- 竞争实例数、接管耗时、CAS 冲突数、Lease 续租次数、重复提交数、恢复成功率。

### 停止条件

- 持久层无法提供原子比较交换且无可靠文件锁替代时，不得声称跨进程安全。
- 系统时间回拨会破坏 Lease 判定时，先完成单调时钟/服务端时钟策略。

## 5. Phase B：`outcome_unknown` 人工处置 API 与 UI

### 目标

把未知结果从“只能阻断”升级为“可查看、可证明、可处置、可审计”，同时坚持副作用未知时绝不自动重放。

### 用户操作

1. **确认未执行后重试**：用户提供外部证据并确认无副作用，系统创建新的 attempt，旧 invocation 永久保留。
2. **录入外部结果并提交**：用户粘贴或选择已发生的结果，系统校验摘要后进入 `result_received -> committed`，不再次调用 Provider/Tool。
3. **保持人工处理**：维持阻断并记录负责人、备注和下次检查时间。
4. **放弃本次任务**：终止当前 attempt，不把未知结果伪装成成功。

### 安全约束

- API 只接受 invocation ID 与期望版本，服务端重新读取并校验 identity/digest。
- 每次处置写入 actor、时间、旧状态、新状态、理由、证据引用和请求幂等键。
- 重复点击返回同一结果；过期版本返回冲突，不覆盖新状态。
- 高副作用工具默认不显示“一键重试”，需要二次确认和权限检查。

### 测试

- 重复请求幂等、并发处置只有一个成功。
- 非 `outcome_unknown` 状态拒绝非法处置。
- 无权限、伪造 digest、过期版本全部拒绝。
- 录入结果后重启，Provider/Tool 调用数仍为 0。
- UI 刷新、应用重启后审计记录与处置状态保持一致。

### 验收门槛

- 未知结果不存在任何默认自动重试路径。
- 所有状态变更都有审计证据。
- API、桌面 UI、重启恢复和全量回归通过。

### 科研数据

- unknown outcome 数、平均处置时长、人工重试率、外部结果录入率、误重放数、审计完整率。

### 停止条件

- 无法区分调用身份或无法验证结果来源时，只允许“保持阻断/放弃”，禁止提交为成功。

## 6. Phase C：Provider 能力探测与受控真实 API 冒烟

### 目标

用统一能力矩阵描述 Provider 的真实保证，并用严格预算闸门验证最小请求链路。

### 能力矩阵

每个 Provider 记录：

- 是否支持请求幂等键及其有效期。
- 是否可按请求 ID 查询结果。
- 是否支持取消、超时后查询、流式断线续传。
- 429/5xx/网络中断的官方重试建议。
- usage、费用、模型版本和响应 ID 是否可记录。

### 冒烟闸门

真实模式必须同时满足：

- 显式环境开关。
- Provider 与模型白名单。
- 单请求与总预算上限。
- 最大请求数、最大 token、超时和中止开关。
- 日志脱敏，禁止输出 key、完整用户隐私与原始认证头。

任一条件缺失立即退出；默认 CI 和本地测试均为离线 Mock。

### 冒烟场景

- 正常请求并记录 response ID、usage 与成本。
- 客户端在 submitted 后模拟断线，验证能否查询结果。
- 相同幂等键重复请求，观察 Provider 官方语义。
- 超时、429 与 5xx 的受限重试。

### 验收门槛

- 离线框架与测试先全绿。
- 真实冒烟必须由用户明确批准预算与凭据范围后执行。
- 报告区分“客户端未重复提交”“Provider 接受幂等键”“端到端 exactly-once”，不得混写。

### 科研数据

- 请求数、成功率、查询命中率、重复响应率、token、费用、p50/p95 延迟、错误类型。

### 停止条件

- 预算达到 80% 提醒，达到 100% 强制停止。
- 出现非脱敏日志、模型不在白名单、无法确认计费时立即停止。

## 7. Phase D：GATE-30 快速门禁

### 目标

建立 30 条可在普通开发机快速运行的确定性用例，作为每次提交的工程门禁。

### 用例分配

| 类别 | 数量 | 核心内容 |
|---|---:|---|
| Model WAL | 6 | 各持久化窗口、格式修复、压缩恢复 |
| Tool WAL | 6 | 执行前后崩溃、副作用未知、零重放 |
| 父子工作流 | 6 | Stage、Return、终态、步数上限 |
| 跨进程 Lease | 5 | 竞争、续租、过期、fencing |
| 人工处置 | 4 | 重试、录入、冲突、权限 |
| Snapshot 迁移 | 3 | v1-v6 加载、升级、未知字段 |

### 输出

- 固定 seed 的机器可读 JSON。
- 用例级输入、预期、实际、耗时、调用计数和失败复现信息。
- 门禁规则：P0 任一失败即阻止合入；非 P0 失败不得被静默忽略。

### 验收门槛

- 连续运行 10 次结果一致。
- Mock 场景 `duplicateToolEffects = 0`、`duplicateModelCalls = 0`。
- 失败时可单条复现。

## 8. Phase E：GATE-100 正式科研基准

### 目标

建立 100 条固定、可分片、可复现的实验集，为复试展示和论文实验提供可信证据。

### 指标

- `taskSuccessRate`
- `recoverySuccessRate`
- `duplicateModelCalls`
- `duplicateToolEffects`
- `unknownOutcomeRate`
- `evidenceCompleteness`
- `p50/p95 latency`
- `token/cost estimate`
- 人工介入次数与处置时长

### 实验组

- 完整 God-Agent。
- 无 Model WAL。
- 无 Tool WAL。
- 无恢复驱动。
- 无跨进程 Lease。
- 无人工处置流程。

这组消融实验用于回答“每项机制实际降低了什么风险”，不能只展示最终成功率。

### 数据规范

- 原始结果写 JSONL，只追加不覆盖。
- 汇总输出 CSV，包含代码 commit、配置摘要、数据集版本、seed、机器环境和运行时间。
- 每次失败保留最小复现包；禁止手工修改结果或填造未运行数据。

### 验收门槛

- 固定 commit、seed 与 fixture 时可重复得到一致结论。
- 指标计算脚本有单元测试。
- 论文表格可由原始数据一键再生成。

## 9. Phase F：科研经历、论文与复试演示

### 科研问题表达

建议将课题收敛为：

> 面向长程多智能体软件任务的崩溃一致性与副作用安全恢复机制研究。

核心研究问题：

1. 如何在模型输出、工具副作用和持久化提交之间建立可恢复协议？
2. 如何在无法获得 Provider exactly-once 保证时，降低重复调用和未知副作用？
3. 跨进程 Lease、WAL 与人工处置分别贡献多少可靠性提升？

### 复试演示脚本

1. 正常启动父子团队任务。
2. 在 Model response、Tool result、Return delivery 三个窗口主动终止进程。
3. 重启后展示 Snapshot/WAL、恢复决策和零重复调用计数。
4. 制造一个 `outcome_unknown`，展示系统阻断与人工处置。
5. 展示 GATE-30 与 GATE-100 的真实实验报告。

### 可交付成果

- 可运行代码、架构图、状态机和故障注入脚本。
- 需求文档、实现计划、测试用例、科研经历日志持续迭代。
- 固定数据集、实验原始数据、统计脚本和结果表。
- 技术报告或论文初稿；投稿前由导师确认题目、贡献、署名与目标刊会。

## 12. 不夸大的项目结论

当前可以严谨表述为：God-Agent 已实现客户端侧、单进程范围内的崩溃安全调用日志和确定性恢复，并对父子团队工作流的关键持久化窗口进行了系统测试。

在跨进程 Lease 和 Provider 能力实测完成前，不能宣称跨进程 exactly-once 或端到端 exactly-once；在 GATE-100 原始数据完成前，不能宣称论文实验已经成立。
