# 05｜主控集成、独立复核与最终放行

## 给主控 Chat 的指令

你负责冻结契约、集成并行 Chat 结果、运行全量门禁和决定 PASS/BLOCKED。不要为了让测试变绿而降低阈值、删除测试或伪造状态。

## 状态

`PASS`；已完成类型检查、Electron 全套测试、完整 npm 测试和 Electron 生产构建；结果记录在 `06-execution-report.md`。

## 集成顺序

1. 审核 01 的视觉令牌、Shell API 和布局截图。
2. 审核 02/03 是否只消费公开契约，检查重复文件修改和文案漂移。
3. 运行契约测试，确认 eventId、requestId、状态枚举一致。
4. 运行单测、集成、E2E、a11y、视觉回归、性能和 Electron build。
5. 在固定环境执行人工关键路径，由两名独立复核者分别记录结果。
6. 生成最终报告；任何阻断项都标记 `BLOCKED` 并退回对应 Chat。

## 合并前文件检查

- [ ] 没有 env、token、auth、机器配置、缓存和无关生成文件进入交付。
- [ ] 每个 Chat 的变更都落在声明范围内。
- [ ] 未接入能力未被改写为已完成。
- [ ] 真实外部服务仍为 mock；没有真实终端/部署/模型副作用。
- [ ] 既有工作树改动没有被重置、覆盖或隐式回滚。

## 最终测试清单

- [ ] `npm ci` 或仓库等价安装校验
- [ ] `npm run check` 或等价类型/静态检查
- [ ] 单元测试全量
- [ ] Electron 专项测试全量
- [ ] E2E 关键路径全量
- [ ] 12 张视觉截图回归
- [ ] a11y/键盘/焦点/对比度
- [ ] 断网/重启/损坏缓存恢复
- [ ] 性能与 30 分钟稳定性
- [ ] production build

## 失败处理

- P0/P1、未捕获异常、重复副作用、敏感泄漏：立即 `BLOCKED`，停止发布。
- 视觉差异：先判断是预期设计变更还是回归；没有设计复核不得更新基线。
- 测试 flaky：先隔离并修复测试稳定性，不得直接重跑到偶尔通过就算 PASS。
- 跨 Chat 冲突：主控记录冲突文件和责任边界，由对应 Chat 修复；不在主控里随意覆盖。
