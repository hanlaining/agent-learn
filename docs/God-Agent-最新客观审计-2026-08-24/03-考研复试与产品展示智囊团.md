## 1. 一句话裁决

God-Agent 已经是一个**技术深度明显高于普通学生课程设计的单机 Agent Runtime 研究原型**。它最有价值的部分不是 Codex 风格界面，而是围绕模型/工具调用、Lease/Fencing、Return Receipt、崩溃恢复和 `outcome_unknown` 建立了可解释、可测试、能保留负结果的可靠性语义。

当前最影响复试得分的不是内核不足，而是**项目入口与真实能力严重脱节**：根 README 仍声称“没有进入 Electron 或 Multi-Agent、165/165”，仓库却已有成熟度更高的桌面端、多 Agent、离线 Benchmark 和科研 Artifact。再加上没有安装包、一键 Demo 和精炼后的项目故事，现场老师很可能先看到“说明过期、怎么启动不清楚”，还没来得及看到真正亮点。

建议对外定位为：

> 我独立实现并持续验证了一个面向长程 Agent 任务的本地 Runtime 原型，重点研究进程崩溃、重复投递、并发接管和外部副作用结果未知时，系统怎样保存事实、拒绝旧执行者、恢复父子任务并避免盲目重放。当前主要证据是本机自动化和确定性 Fake Provider 下的 E2，另有一个严格限定为 1/40 的真进程 E3 窄检查；它不是生产级平台，也不是已经完成的论文。

## 3. 三类评委视角的判断

### 3.1 考研复试老师视角

老师最容易认可的不是文件数量，而是以下学习轨迹：

1. 从单 Agent Loop 和工具调用出发；
2. 做到多 Chat、多 Agent 后遇到恢复与一致性问题；
3. 发现“机制存在”不等于“生产入口接线完整”；
4. 用反例逼出 WAL、Lease/Fencing、Receipt 和 Outcome Unknown；
5. 主动把结论限制在 E2 和窄范围 E3，没有把测试全绿说成论文完成。

这条轨迹能体现系统能力、研究意识和科研诚信。风险是仓库材料过多、术语太密，如果三分钟内先讲 `generation/state-capability CAS` 或 100/150/66 账本，非本方向老师会失去主线。

### 3.2 导师视角

导师会看重：

- 研究问题来自真实工程反例，而不是先想标题再补实验；
- 有 Claim–Evidence Matrix、证据等级、冻结 Artifact 和复现 SOP；
- 负结果没有被删除，尤其明确保留未定位 flake、旧原始结果缺失和 E3 仅 1/40；
- 能区分协议模型、生产实现检查和真进程检查；
- 知道 exactly-once 对不可查询外部副作用并不成立。

导师也会立刻追问：研究创新相对现有 Workflow Engine、数据库 WAL、Actor/Saga、Temporal、Ray、LangGraph/CrewAI 到底在哪里；为什么当前消融结论不是“在自定义模拟器里证明自己的设计”；统计效度、外部基线和第三方复现在哪里。当前材料对“证据边界”回答较好，但对系统文献中的差异化定位仍不够集中。

### 3.3 工程面试官视角

工程面试官会认可：

- 生命周期、权限、Sandbox、MCP、Context Compaction 和持久化不是拼 UI；

- 多 Chat 并行与取消、父子 Agent 状态、Outcome Unknown 人工裁决有明确 UI；
- 测试覆盖大量失败路径，而不只覆盖 happy path；
- Process Chaos 使用真子进程强杀，但诚实声明 Provider 为 Fake。

工程面试官会扣分于：

- 根 README 与最新代码不一致；
- `package.json` 的 description 出现乱码，author/keywords 为空；
- 声明 `ISC`，但仓库未找到独立 `LICENSE` 文件；

- Runtime 持久化仍以本地文件和单机语义为主，不能外推到多机生产部署。

## 4. 现场亮点

### 4.1 第一亮点：问题真实且有研究味道

“模型回答得好不好”不是这个项目最强的问题。真正有辨识度的问题是：

> 模型结果返回后进程崩溃、工具副作用发生但确认未持久化、父 Agent 等待子 Return、Lease 接管后旧 Owner 又迟到提交时，Runtime 应该如何裁决？

这个问题能自然引出状态机、WAL、幂等键、Lease/Fencing、Receipt、恢复入口和人工处置，比“我做了多 Agent 协作”更具体、更能被追问。

### 4.2 第二亮点：知道何时必须承认 Unknown

`outcome_unknown` 是现场最值得展示的概念之一。项目没有把不可查询的外部副作用简单标记为成功或失败，而是阻止自动重放并提供人工裁决路径。这能说明作者理解：

- “请求失败”不等于“副作用没有发生”；
- 幂等、at-least-once、at-most-once 和 exactly-once 不能混用；
- 系统可靠性有时来自安全停止，而不是无限自动恢复。

### 4.3 第三亮点：保留负结果与 Claim 上限

科研材料明确保留了：

- 旧结果只剩摘要、原始文件缺失；
- Runtime-E2E 曾因临时路径进入确定性投影而失败；
- Process fault point 曾超时；
- 全量测试曾出现一次详情丢失的未知 flake；
- Process E3 只有 1/40；
- 外部第三方复现未完成。

这比堆“测试全部通过”更能打动严谨导师，因为它展示了可证伪性和研究诚信。

### 4.4 第四亮点：桌面端已经具备产品展示骨架

从代码和 74 项 Electron 专项检查看，桌面端已经包含：

- 三栏可调整布局和响应式降级；
- 历史任务、多个 Chat 和草稿切换；
- Commentary、Activity、Reasoning、最终结果分层；
- 父子 Agent/固定软件团队状态与 Return 流程；
- 文件、Skill、命令面板、模型与推理强度选择；
- Permission once/session；
- Outcome Unknown 展示、重试授权、外部结果登记和终止；
- 本地预览与受限多标签浏览器。

这些能力适合用一张截图建立“它确实是产品原型”的第一印象，然后立即转向可靠性问题，避免把答辩讲成 UI 仿制。

### 4.5 第五亮点：已有分层复现材料

`research/artifacts/v0.1` 把 Model Check、Runtime Implementation Check、Process Check 分开，并通过 Manifest、SHA-256、Claim Matrix 和同机干净副本记录限制结论。这种分层方式比单个测试数字更适合科研答辩。

## 5. 现场风险

### P0：根 README 事实错误

README 仍写：

- “Codex-like 单 Agent Runtime 学习项目”；
- “当前没有进入 Electron 或 Multi-Agent”；
- `npm test 165/165`。

这与当前代码和科研文档明显冲突。老师若先看 GitHub，会怀疑材料拼接、项目缺乏维护或答辩内容夸大。这是复试前必须修的第一项。

### P0：没有稳健的一键现场 Demo

当前演示依赖 Node/npm、101 个依赖、Electron 构建、本地环境变量和可能的 Windows 文件锁。没有安装包、环境医生、固定演示状态、单条启动脚本和自动回退说明。首次 `npm ci` 的 EPERM 已证明该风险真实存在。

### P0：无 Key 时核心聊天不可用

App Server 会在缺少 `OPENAI_API_KEY` 时进入 ready，但明确禁用 `turn/run`。也就是说，桌面壳可能打开，核心对话却不能现场工作。离线科研 Runner 不需 Key，但它展示的是状态机与报告，不是完整产品聊天体验。必须准备“两轨 Demo”：离线可靠性证据为必达，真实 Provider 体验为可选加分。

### P1：项目故事分裂

仓库同时存在四种叙事：

1. Agent Learn 单 Agent 学习项目；
2. Codex 风格桌面客户端；
3. God-Agent 多 Agent 产品；
4. 可靠性科研 Runtime。

当前没有一个首页把它们串成演进故事。复试时若随意切换名称和目标，老师会追问“你到底做了什么”。

### P1：资料很多，但现场证据包不够小

科研日志很完整，但篇幅巨大。缺少一个真正可投屏的最小包：一页架构图、一页故障时序、一页结果表、一页限制、三分钟 Demo 脚本。材料数量不能替代信息设计。

### P1：安装与发布成熟度低

- 没有 Electron 安装包或 portable release；
- 没有 `engines` 固定 Node/npm 支持范围；
- 没有 `doctor` 或 Demo preflight；
- 没有独立 `LICENSE` 文件；
- 没有 release checklist、CI badge 和下载说明；
- 版本号 `1.0.0` 与“尚无正式发布”容易产生错觉。

### P1：原创说明有原则，缺逐项来源账本

《原创、借鉴、引用与 AI 辅助说明》对 Codex-like、AI 辅助、开源许可证和非官方关系说明得较清楚，这是优点。但它主要是原则声明，尚不足以替代：

- 具体功能/文档参考了哪个上游文件或论文；
- 是否有直接改写或代码级移植；
- UI 图标、设计语言、协议语义分别来自哪里；
- 第三方依赖许可证汇总和 NOTICE。

老师问“是不是 Codex 帮你写的、你自己做了什么”时，必须回答个人决策和验证责任，不能只引用免责声明。

### P2：可见的未完成界面会削弱产品感

桌面端明确展示“变更检查尚未接入”“桌面终端尚未接入”“阶段 D 开放个性化键位”。这些可以作为边界说明，但现场不要主动点击，否则观众会把注意力从已完成的 Runtime 转移到缺失功能。

## 6. 老师高概率追问与建议回答

### Q1：这和普通调用大模型 API 有什么区别？

建议回答：

> 普通 Demo 关注一次请求是否得到答案，我关注请求跨多轮工具调用和进程重启后的状态是否仍然可信。项目自己维护 Thread/Turn/Invocation、工具 WAL、Task/Return、Lease 和 Evidence，并对重复投递、迟到提交和结果未知做确定性裁决。模型负责语义决策，Runtime 负责状态和副作用边界。

### Q2：为什么需要 WAL，模型请求失败了再调一次不就行了吗？

建议回答：

> 网络错误只能说明客户端没有收到确定结果，不能证明 Provider 或工具没有执行。若模型已计费、工具已产生副作用，再调一次可能重复。WAL 的作用是先记录稳定调用身份和状态；如果结果仍不可判定，系统进入 outcome_unknown，而不是盲重放。

### Q3：Lease 是否保证 exactly-once？

建议回答：

> 不保证端到端 exactly-once。Lease/Fencing 能拒绝旧 Owner 对本地状态的迟到提交，但无法替外部不可查询系统撤销或确认副作用。项目保证的是一组明确的本地提交和安全停止语义，不把它包装成全链路 exactly-once。

### Q4：多 Agent 为什么比单 Agent 好？有实验吗？

建议回答：

> 当前工作重点不是证明多 Agent 普遍优于单 Agent，而是研究多角色和父子任务引入的恢复问题。固定软件团队和动态父子调度已有实现，但尚没有足够的真实任务、单 Agent 公平基线和统计结论，所以我不会声称多 Agent 提高了成功率。

### Q5：你的创新点是什么？WAL、Lease 都不是新概念。

建议回答：

> 单个机制不是我的原创发明。我的候选贡献是把这些系统机制映射到 Agent 的 Model Invocation、Tool Effect、Parent Return 和 Completion Evidence 上，明确哪些窗口能自动恢复、哪些必须暴露 Unknown，并建立分层故障注入与 Claim 证据链。它是否构成论文创新，还需要系统文献对比、外部基线和正式实验验证。

### Q6：Benchmark 是不是自己设计、自己证明自己？

建议回答：

> 这是当前局限。协议 GATE 主要验证参考状态机，Implementation Check 才直接运行生产类，但仍使用 Fake Provider。现阶段它适合回归和消融方向检查，不足以证明外部有效性。后续需要外部任务集、其他系统基线、真实故障分布和第三方复现。

### Q7：为什么只有 1/40 也要展示？

建议回答：

> 因为它验证了方法能从组件测试走到真 App Server 强杀、PID 更换和文件/RPC 重载，但范围只有 Team Return 的一个固定窗口。展示它是为了说明证据升级路径，不是把它外推为完整 E3。

### Q8：Codex-like 是否涉及抄袭？Codex 在项目里做了什么？

建议回答：

> Codex-like 只描述公开可见的交互和 Agent 产品范式，不表示复制专有源码。项目使用公开协议、依赖和资料，并单独声明引用与 AI 辅助边界。Codex 参与过拆解、草拟、测试补充和文字整理，但架构取舍、是否采纳、反例设计、运行验证和最终责任由我承担。我也需要继续补齐逐项来源账本和许可证清单。

### Q9：如果今天让你部署到生产，最大问题是什么？

建议回答：

> 最大问题不是界面，而是单机本地文件状态、外部副作用可查询性、真实 Provider/Tool 的故障模型、队列耐久性、多租户隔离和可观测性。当前是研究原型，我会先限定单机工作负载和副作用类型，再引入数据库事务、持久队列、端到端追踪、权限审计和受控灰度。

### Q10：你从这个项目中最重要的负结果是什么？

建议回答：

> 最重要的发现是“代码里有 Lease/WAL”不等于生产链路所有 commit boundary 都受保护。另一个反例是确定性报告因为临时绝对路径进入错误信息而不确定。这让我把验证对象从功能存在升级到接线覆盖、可观测状态和证据保管链。

## 7. 适合的表述

### 7.1 30 秒版本

> 我做了一个本地 Agent Runtime 原型 God-Agent。最初目标是实现单 Agent、工具调用和多 Agent 协作，后来我发现真正困难的是模型、工具和父子任务在进程崩溃或重复执行后怎样保持状态可信。因此我实现并验证了 Model/Tool WAL、Lease/Fencing、Return Receipt、Checkpoint 和 Outcome Unknown 人工裁决，并把证据分成协议模型、生产实现检查和真进程检查。目前主要达到本机 E2，只有一个 1/40 的窄范围 E3；项目还不是生产系统，也没有完成论文统计闭环。

### 7.2 90 秒版本

> God-Agent 是我从零学习 Agent Runtime 时逐步形成的研究型工程项目。它有 CLI 和 Electron 桌面端，也支持 Skill、MCP、权限、上下文压缩、多 Chat 和父子 Agent。但我复试最想介绍的不是界面，而是可靠性问题。
>
> 比如模型结果已经返回但进程在持久化前崩溃，或者工具已经产生副作用但客户端没有收到确认，这时简单重试可能重复计费或重复执行。我为模型和工具调用建立稳定身份与 WAL，用 Lease/Fencing 阻止旧 Owner 迟到提交，用 Return Receipt 恢复父子任务；如果外部结果无法确认，就进入 outcome_unknown，停止自动重放并交给人工裁决。
>
> 我还把验证分成确定性协议基准、直接运行生产类的 Implementation Check 和真 App Server 强杀的 Process Check，并保留了不确定性、失败样本和证据边界。现在主要证据仍是 Fake Provider 下的 E2，真进程只覆盖 1/40，没有外部统计和第三方复现，所以我把它定位为系统化研究原型，而不是生产级平台或已完成论文。

### 7.3 项目名称建议口径

在复试现场统一使用：

> God-Agent：面向长程 Agent 任务的可恢复本地 Runtime 原型

“Agent Learn”可作为仓库历史名称；“Codex-like”只作为交互和学习背景，不作为项目主标题。

## 8. 不应声称的内容

以下说法在当前证据下均不成立：

- “完整复刻了 Codex”或“达到 Codex 稳定性”；
- “生产级多智能体平台”；
- “端到端 exactly-once”；
- “多 Agent 已被证明优于单 Agent”；
- “GATE-30/GATE-100 代表 30/100 个真实软件任务”；
- “逻辑模拟延迟就是生产 p50/p95”；
- “Process Chaos 已覆盖完整 40 个窗口”；
- “真实 Provider 和真实外部工具已经完成稳定性实验”；
- “论文已经闭环”或“创新性已经得到证明”；
- “外部第三方已经复现”；
- “所有测试当前都通过”，除非现场重新执行统一入口并保存完整结果；
- “全部代码完全手写且未使用 AI”；
- “Codex-like 就代表官方兼容或官方认可”；
- “项目已经可以下载安装到任何 Windows 机器运行”。

## 9. Demo 准备度与推荐演示方案

### 9.1 当前 Demo 准备度

当前为 **58/100**。

加分项：CLI help、类型检查、Electron build、10 项 benchmark 和 74 项 Electron 专项在本轮均通过；离线 Fixture 不需要真实 Key；已有 Frozen Artifact 和 Process Smoke 说明。

扣分项：没有安装包和一键 preflight；README 错误；首次依赖安装出现 EPERM；未完成本轮真窗口点击验收；真实聊天需 Key；没有专门的复试 Demo 文档、录屏、截图集和断网兜底包。

### 9.2 推荐三分钟 Demo

#### 0:00–0:30：先给问题，不先跑命令

用一张时序图说明：Tool 已执行 → 进程崩溃 → 确认未持久化 → 为什么不能盲目重试。

#### 0:30–1:10：展示产品壳

展示 Electron 截图或预先验证窗口：

- 左侧历史和多 Chat；
- 中间 Runtime Timeline；
- 右侧父子 Agent/Activity；
- Outcome Unknown 人工处置卡。

不要点击未接入的 Changes/Terminal。

#### 1:10–2:10：运行必达的离线证据

运行固定 seed 的 dry-run 或 GATE-30 单入口，展示：

- manifest；
- baseline/no-WAL/no-recovery/no-lease；
- `run-record.json`；
- 一个失败 repro；
- 明确说明它是协议级离线基准。

#### 2:10–2:45：展示真进程窄检查的已归档结果

展示三代 PID、最终 Return consumed 和 `return_god=1`，同时在画面上固定写“Fake Provider、1/40、窄范围 E3”。现场不建议临时强杀并等待 30 秒以上，除非已在同机连续验证。

#### 2:45–3:00：主动说局限

一句话收尾：

> 当前主要证据是 E2，下一步是补齐 Process 矩阵、真实任务对照、统计置信区间和外部无指导复现。

### 9.3 必须准备的三层兜底

1. **A 方案：现场运行**——固定工作区、固定 Node、依赖已安装、命令已预热；
2. **B 方案：离线 Artifact**——完整 JSON/CSV/repro、SHA-256 和结果解读；
3. **C 方案：短录屏+截图**——录屏必须标注录制基线、命令、seed 和 Provider，不把录像冒充现场运行。

## 11. 复试前补足顺序

### 第一优先级：一天内完成

1. 重写根 README，使当前能力、限制、命令和测试数字与最新基线一致；
2. 统一项目名称和一句话定位；
3. 新建“复试 Demo Quickstart”，固定环境、命令、seed、预期输出和失败回退；
4. 生成一页项目架构、一页故障时序、一页证据表、一页局限；
5. 准备 30 秒、90 秒和 3 分钟三套说法。

### 第二优先级：三天内完成

1. 增加只读 preflight/doctor，检查 Node、依赖、Key、端口、状态路径和输出目录；
2. 制作无需安装的固定桌面演示包或至少冻结可复用构建产物；
3. 准备无 Key 的离线演示模式，避免桌面打开后核心发送按钮不可用；
4. 固定一次全量验证输出，记录 Commit、环境、退出码和日志 SHA；
5. 补齐独立 LICENSE、包描述、author/keywords 和 Node engines。

### 第三优先级：复试前完成

1. 建立逐项“来源—借鉴点—个人实现—验证责任”表；
2. 用 5–10 个最有代表性的真实软件任务做单 Agent/多 Agent 公平对照，先作为 Pilot，不急于宣称显著性；
3. 至少找一名未参与开发者按简化 SOP 无指导复现；
4. 将完整日志留作备查，现场只展示四页证据；
5. 录制一次断网、无 Key 条件下仍能完成的可靠性 Demo。

## 12. 最终建议

这个项目值得在考研复试中讲，而且比“做了一个聊天界面”有明显竞争力。正确策略不是继续堆功能，也不是把 400+ 测试、100/150/66 清单当成成绩本，而是把最强的研究故事压缩为：

```text
从 Agent Loop 出发
→ 多 Agent 暴露恢复与副作用问题
→ 用反例找到错误的完成语义
→ 引入 WAL / Lease / Receipt / Unknown
→ 分层验证并保留失败
→ 主动限制 Claim
```

只要复试前解决 README、一键 Demo、材料压缩和来源账本四个入口问题，God-Agent 能成为一段可信、可追问、有技术辨识度的科研经历。若不解决，项目会出现典型的“内核 80 分、门面 50 分”，老师可能因入口混乱而低估实际能力。
