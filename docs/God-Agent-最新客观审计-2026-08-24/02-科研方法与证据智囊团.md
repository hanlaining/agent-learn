## 一、最终结论

God-Agent 当前已经具备一个**较强的 Agent Runtime 可靠性研究原型和科研基础设施雏形**，但还没有完成科研闭环。

最准确的阶段判断是：

> 已完成“问题发现—机制实现—确定性 Model Check—生产类 Runtime Implementation Check—单窗口真子进程检查—同机冻结 Artifact”的内部技术验证链；尚未完成“正式预注册—样本量依据—完整 Dynamic E3/GATE-40—正式重复—统计推断—真实 Provider/外部副作用—外部基线—独立复现—论文结论”的研究闭环。

本智囊团给出的科研闭环成熟度为 **50/100**，置信度 **0.93**。

这不是代码完成率，也不是复试展示分数。它只回答“现有证据距离可以投稿并经受方法审查的完整科研闭环还有多远”。

按项目自己在 RT95 计划中定义的严格门禁计算：

- Research/SOP：`0/66 Verified`，Research-95 为 **No-Go**；
- Engineering Work Package：`0/100 Verified`，工程 95% 为 **No-Go**；
- 顶层测试合同：`150/150 Designed`、`0 Verified`；
- W0 只关闭了术语、合同和方法输入，W1～W12 尚未按新分母完成。

上述“0 Verified”不表示没有代码或测试，而表示项目自己的新门禁拒绝把“文件存在、设计完成或旧 E2 测试通过”自动升级为目标版本的正式完成证据。

## 四、实现证据审计

### 4.1 已经成立的实现证据

当前代码确实不是只有研究文档。Runtime-E2E Harness 直接引用并运行了以下生产实现：

- `AgentLoop`；
- `AgentRunStore`、`AgentRuntimeStore`；
- `JsonFileRuntimePersistence`；
- `ModelInvocationStore` 与启动恢复；
- `ToolInvocationStore`；
- `PersistentRuntimeLeaseStore`；
- `WorkflowTeamCoordinator`。

最新主线还新增了 Authority、Capability Grant、Evidence Contract、Runtime Correlation、Runtime Event 等结构化基础。这些工作说明项目已经从普通多 Agent 编排转向“持久状态、所有权、证据和恢复语义”的系统研究，研究方向是成立的。

### 4.2 尚未成立的目标实现证据

项目自己的最新 RT95 账本显示：

- 100 个 Engineering Work Package 全部为 `NotVerified`；
- 66 个 Research/SOP Gate 全部为 `NotVerified`；
- 150 个顶层 Test Case 全部为 `Designed`；
- 新指标字典明确写明 F01 只闭合语义输入，F02 Schema/Validator 尚未实现。

因此不能把旧 Runtime 的 E2 测试总数直接换算成“新双链科研版 Runtime 已完成 70%/95%”。旧实现可以作为基础，但目标分母已经改变。

### 4.3 最重要的语义风险

冻结 Runtime-E2E GATE-30 报告中，baseline 同时出现：

- `taskSuccess = 30/30`；
- `unknownOutcome = 5/30`。

这在 legacy v1 口径下被允许，但不能解释为“业务 100% 完成”。项目新增的 Metric Dictionary v2 已正确指出必须拆分：

- protocol handling；
- business completion；
- completion decision validity；
- retrospective false completion；
- outcome unknown。

问题在于 v2 目前主要还是词典和设计，机器 Schema/Validator 尚未正式接入 Runner。正式实验前必须先消除这个构念混写，否则任何“成功率”都可能被审稿人质疑。

## 五、离线 GATE-30 / GATE-100 审计

### 5.1 协议级 GATE-30

Frozen Model Artifact 完整保存了 GATE-30 的 report、CSV 和失败 repro。其四变体摘要为：

| 变体 | taskSuccess | recoverySuccess | duplicateModelCalls | duplicateToolEffects | unknownOutcome |
|---|---:|---:|---:|---:|---:|
| baseline | 30/30 | 21/21 | 0 | 0 | 0/30 |
| no-wal | 24/30 | 15/21 | 34 | 6 | 6/30 |
| no-recovery | 9/30 | 0/21 | 0 | 0 | 6/30 |
| no-lease | 27/30 | 18/21 | 29 | 3 | 0/30 |

这些数字能支持的结论仅是：在固定的参考协议模型中，关闭 WAL、恢复或 Lease 会沿预设方向退化。

### 5.2 协议级结果不是实测概率

协议 `engine.ts` 根据 scenario 和 variant 用显式公式计算调用数、重复效果、成功和延迟。也就是说：

- 结果是 Model Check 的输出，不是调用真实 Agent 得到的随机观测；
- “消融方向性”大部分来自实现模型时写入的机制关系；
- latency 是逻辑模拟毫秒，不是墙钟延迟；
- token 与 cost 使用 fixture 固定费率，不是 Provider 账单。

它的价值在于发现协议矛盾、冻结预期和生成反例，不在于估计真实系统效果量。

### 5.3 最新 Offline Benchmark Runner 的实际增量

PR #35 新增的统一 Offline Runner 能生成：

- 30 个唯一 task；
- 4 个 variant；
- 120 个 execution record；
- task manifest、run record、report 和 CSV；
- seed、shard 与确定性校验。

这是**可复现性和记录治理的真实进步**。但 Runner 最终仍调用同一个 `buildReport -> runScenario` 协议公式。它没有新增 120 次真实模型、真实 Runtime 或真实 Tool 执行。因此复试时可以说“建立了 30 任务、四配置的离线协议基准入口”，不能说“完成了 120 次真实 Agent 实验”。

### 5.4 GATE-100 状态

- 协议 GATE-100 fixture 和四分片不重不漏测试存在；
- 测试会在内存中构建 GATE-100 并检查消融方向；
- 旧结果摘要保留了一个 GATE-100 哈希；
- 对应旧原始 report/CSV/repro 当前缺失；
- Frozen Artifact v0.1 只冻结 GATE-30，没有冻结 GATE-100；
- Runtime-E2E GATE-100 当前主要证明 fixture 可分片，未形成完整 100×4 生产实现 Artifact。

因此，“GATE-100 入口存在”成立，“GATE-100 科研证据闭环完成”不成立。

## 六、Runtime-E2E 与消融实验审计

### 6.1 当前最有价值的实验层

Runtime-E2E 比协议 Model Check 更接近真实系统，因为它：

- 实例化生产 Runtime 类；
- 对本机真实 JSON 文件写入并重载；
- 覆盖 Model 响应窗口、Tool 效果窗口、Return/父子反馈、Workflow Stage、Snapshot Reload、Multi-instance Lease 六个 family；
- 通过接线绕过 WAL、恢复或 Lease 做消融，而不是只修改数学参数。

Frozen Runtime GATE-30 四变体摘要为：

| 变体 | taskSuccess | recoverySuccess | duplicateModelCalls | duplicateToolEffects | unknownOutcome |
|---|---:|---:|---:|---:|---:|
| baseline | 30/30 | 25/25 | 0 | 0 | 5/30 |
| no-wal | 20/30 | 25/25 | 10 | 5 | 10/30 |
| no-recovery | 5/30 | 5/30 | 0 | 0 | 0/30 |
| no-lease | 23/30 | 23/25 | 0 | 5 | 5/30 |

这些结果支持“现有 fixture 中机制关闭会导致方向性退化”，但还不支持实际故障分布下的因果效应量。

### 6.2 消融设计的不足

当前消融仍有五个主要缺口：

1. 只有 `no-wal`、`no-recovery`、`no-lease` 三个粗粒度关闭项，尚未完成计划中的八个单变量机制消融；
2. 各 family 只有 5 个固定场景，重复并不等于独立随机样本；
3. 没有正式预注册的主要终点、排除/重跑规则和样本量依据；
4. 没有配对置信区间、效应量、count model 或多重比较校正；
5. 没有外部基线，无法回答“比简单持久队列、Temporal、LangGraph 或其他 Agent Runtime 好多少”。

### 6.3 最新主线干净串行验证

总控在依赖稳定、串行执行的环境中对 `main@3c78dca` 完成了最终验证：

| 验证项 | 最终结果 | 证据解释 |
|---|---:|---|
| TypeScript 静态检查 | 通过 | E1 |
| Pretest | 19/19 | Runtime Store 专项 E2 |
| 主测试 | 484/484 | 最新主线组件/集成 E2 |
| Electron Build | 通过 | 构建入口可用，不等于人工桌面 E3 |
| Benchmark Tests | 10/10 | 协议 Model Check 与 Offline Runner 校验通过 |
| Offline GATE-30，seed `20260824` | deterministic verified；baseline 30/30、recovery 21/21 | Provider 为 deterministic mock，不能外推真实系统 |
| Runtime-E2E | 10/10 | 生产类、真实 JSON、Fake Provider/Tool |
| Process Chaos 专项 | 2/2 | 真子进程路径，Provider 为 deterministic Fake |
| 双进程 Smoke | passed | `liveCalls=false`，不是实际模型 Provider 实验 |
| Provider Smoke | completed | offline，`liveCalls=0`；生产适配器的 idempotency/status/cancel 仍未接入 |

这些结果足以确认最新主线当前工程门禁健康，并消除“PR #34/#35 合并后出现确定性源码回归”的担忧。它们不会自动升级研究证据等级：Mock/Fake、固定 fixture、无正式样本量和无外部复现的限制仍然存在。

### 6.4 本轮并发环境负结果与最终裁决

智囊团在总控完成干净串行验证前曾观察到：

- `npm run check` 退出码 0；
- `npm run test:benchmarks` 为 10/10；
- 离线 `provider:smoke` 完成，真实调用 0。

`npm run test:runtime-e2e` 本轮为 8/10：30 条生产类 Runtime baseline、消融和报告校验通过；两个真子进程用例失败。随后只读检查发现共享 worktree 的 `node_modules/tsx` 目录正被并发任务改动，仅剩 `dist`，缺 `package.json`/`index.js`，`npm ls tsx` 报 `invalid`。子进程错误也明确为无法解析 `tsx/index.js`。

后续总控在稳定依赖环境中得到 Runtime-E2E 10/10 和 Process Chaos 2/2，因此最终裁决是：

- 该负结果应保留；
- 当前证据足以把 8/10 归为“共享依赖环境污染导致的无效并发复验”，不是 Runtime 源码回归；
- 该失败过程仍应保留，不能从审计记录中删除；
- 对最新 `3c78dca` 的最终工程裁决采用后续干净串行结果：Runtime-E2E 10/10、Process Chaos 2/2；
- 这同时说明未来科研 SOP 必须要求独占依赖安装或隔离 worktree，避免并发修改 `node_modules` 污染实验有效性。

## 七、Process Chaos / Dynamic E3 审计

### 7.1 已经成立的窄范围证据

Frozen Process Artifact 记录了：

- 真 App Server 子进程；
- 三代不同 PID；
- 两次强杀与重启；
- 公共 RPC 与 JSON 文件重载；
- Return 窗口持有 Lease、等待到期后恢复；
- Fake Provider 在 `return_god` 阶段请求计数为 1；
- Job 最终 `completed`，Return 最终 `consumed`。

这可以称为“一个固定 seed、Team Workflow Return 窗口的窄范围真进程检查”。

### 7.2 未完成项

报告自身明确记录：

- `formalFaultWindowCount = 1`；
- `gate40CompletedWindows = 1`；
- `gate40TotalWindows = 40`；
- `completeE3Matrix = false`；
- `completeGate40 = false`；
- `exactlyOnceClaimed = false`；
- `productionReadyClaimed = false`。

单个窗口观察到一次 `return_god` 请求，不能推出整个系统具有 exactly-once。最多只能说：在这个固定窗口和 Fake Provider 计数器中，没有观察到 Return 阶段的重复请求。

## 八、真实 Provider 审计

### 8.1 已有能力

项目已经实现了一个较谨慎的 Provider Smoke Harness：

- 默认 offline；
- Live 必须显式开关；
- 要求 Key、模型 allowlist、operation、请求上限、单次/总预算和 timeout；
- 输出做敏感信息脱敏；
- 有 `create/status/cancel/retry` 的 fixture 路径；
- 另有最多 2 个付费 Job 的 `team-runtime-live-baseline --smoke` 入口和需显式授权的 30 Job 入口。

这说明安全边界设计得比普通 Demo 成熟。

### 8.2 当前真实证据为零

冻结 Artifact、Clean Reproduction 和本轮 Smoke 都明确是：

- real API calls：0；
- credentials read：false；
- Provider：deterministic mock/Fake。

实际 `OpenAiResponsesProvider` 当前只接 POST `/responses`。能力矩阵明确标注：

- Idempotency-Key：not wired；
- Provider request status query：not wired；
- Provider cancellation：not wired；
- 重试只是一侧客户端有限重试，不保证 Provider 去重。

因此不能声称真实 Provider 的恢复、幂等、取消、延迟、成本或稳定性已经验证。真实 Provider 在论文里当前仍是缺失证据，不是低样本证据。

## 九、统计分析审计

当前报告提供的是描述统计：count、rate、P50/P95、重复调用数、模拟 token/cost 或本机墙钟。

尚未完成：

- 正式样本量或精度分析；
- 二项率置信区间；
- 零失败上界；
- 配对效应与效应量；
- count outcome 模型；
- RTO 分层分布与 deadline miss；
- 多重比较校正；
- unknown classifier precision/recall；
- false completion；
- 外部副作用 cardinality Oracle；
- 一键生成正式表图。

固定 fixture 的 30 或 100 个 case 不能自动形成总体推断。GATE-40 是功能覆盖门槛，也不是统计完成线。项目自己的计划已经正确写明：正式重复至少应达到每窗口 50 个配对 seed，或由样本量分析决定。

## 十、可复现性与 Artifact 审计

### 10.1 优点

当前可复现性工程是项目最值得肯定的部分之一：

- Model、Runtime、Process 三层 Artifact 分开；
- 每层有 SCOPE、Manifest、SHA-256 和 Provider 声明；
- Manifest 能拒绝缺失、篡改和未声明文件；
- Model 保存 report/CSV/repro；
- Runtime 保存 report/CSV/repro；
- Process 保存公开安全子集；
- 有同机干净源码副本的复现记录；
- 保留了历史 flake、路径确定性失败和日期规范化失败等负结果。

这种“保留失败、不回填旧来源链”的科研诚信意识是成熟的。

### 10.2 关键限制

1. Frozen Artifact 绑定的 baseline 是 `05680a4e...`，不是当前最新 `3c78dca`；
2. 当前主线在该 baseline 之后新增了大量 Capability/Evidence/Authority、RT95 Ledger、Process Smoke 和 Offline Runner；
3. 因此旧 Frozen Artifact 不能直接作为“最新 God 代码”的完整冻结证据；
4. GATE-100 旧原始报告缺失；
5. Process 公开包排除了 raw `runtime-state.json`，第三方不能只靠公开包复查全部状态；
6. Clean Reproduction 是同机 R2，不是第二人/第二环境 R4；
7. 没有顶层 Manifest 把最新 Commit、预注册、统计、外部复现与所有子 Manifest 统一绑定。

### 10.3 文档一致性风险

根 `README.md` 仍写着：

- 当前没有进入 Electron 或 Multi-Agent；
- `npm test 165/165`。

这与当前代码和研究文档明显不一致。README 过期不会否定源码，但会显著损害复试展示、第三方复现和审稿可信度。对外冻结前必须更新。

- 实验暴露了 unknown outcome、重复效果、路径非确定性和测试 flake 等负结果，并没有删除这些结果。

### 11.2 当前不可夸大

- 不可说“完成了 GATE-40”或“完整 E3”；
- 不可说“GATE-100 已形成可复核科研结论”；
