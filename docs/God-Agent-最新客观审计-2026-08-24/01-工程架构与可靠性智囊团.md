### 4.2 多 Agent 已从概念进入生产组装

最新源码明确包含两类执行路径：

1. `dynamic_v1`：动态创建子任务、等待依赖、容量限制、父级 continuation、用户反馈与显式恢复；
2. `software_product_delivery_v2`：God/Root、Lead、Product、Engineering、Quality 五角色固定工作流。

多 Agent 事实不是仅存在于 UI：`AgentRuntimeStore` 持久维护 Job、Task DAG、Agent Run、Evidence、Return Envelope、Stage Checkpoint 和 Attempt；`ExecutionEngineRouter` 对执行类型做唯一路由；`WorkflowTeamCoordinator` 执行 Product → Engineering → Quality → Lead → Return God 的阶段链，并对返工次数、Evidence、新旧 Attempt 隔离和 Return 状态做校验。

### 4.3 可靠性语义设计成熟度较高

当前实现值得重点展示的机制包括：

- **Model Invocation 状态机**：在请求前保存 `prepared`，请求提交后进入 `submitted`，收到响应后进入 `response_received`，业务事实提交后进入 `committed`。
- **Tool Invocation 状态机**：`prepared → executing → result_received → committed`，进程在执行中死亡时不盲目重跑，而是转为 `outcome_unknown`。
- **稳定 Invocation ID**：用调用事实和 digest 形成幂等身份，重复 prepare/commit 做一致性校验。
- **显式不确定结果处置**：外部调用结果无法确认时，不伪装成功，也不自动重放潜在副作用；通过服务端 resolution identity 和权限边界进入人工处置。
- **Return Outbox**：Return 支持 ready/delivering/consumed、claim、retry、receipt/幂等消费与重启恢复。
- **Attempt 隔离**：新 Job/Task Attempt 不把旧失败 Evidence 当成当前证据，同时保留审计历史。
- **恢复时零模型原则**：动态 Engine 的 `recover` 明确只恢复事实，不在进程启动时自动调用模型。
- **终态单调性**：取消、失败或已完成终态不能被迟到模型/工具结果回退。

这些设计体现了对 at-least-once、重复投递和外部副作用不确定性的真实理解。

### 4.4 单机多进程所有权机制已经落地

`PersistentRuntimeLeaseStore` 与 `ExecutionLeaseCoordinator` 实现了：

- Job 级 Lease；
- TTL、续租和有界获取；
- 持久 fencing token；
- `withFencedCommit` 提交前验证所有权；
- 进程崩溃后的过期 Lease 回收；
- 本机并发调用复用活动 Session；
- Return claim、父 continuation 和 consume 的独立 fenced commit 边界。

底层 `ProcessSafeFileLock` 采用不可变 claim 文件和 Bakery 风格排序，并通过本机 pipe/socket 判断进程存活，避免清理掉后继进程的锁。这比普通“内存 mutex + JSON 文件”方案严谨得多。

### 5.1 最新代码与 Frozen Artifact 已脱节

`research/artifacts/v0.1/README.md` 明确绑定 `05680a4...`，而最新审计基线是 `3c78dca...`。PR #34/#35 带来的 Process Chaos 和 Offline Benchmark 变化没有形成新的冻结 Artifact 版本。

这意味着：

- 旧 Artifact 可以证明旧基线；
- 最新源码存在新机制和新入口；
- 但“最新源码 = 已冻结、已 clean reproduce 的科研结果”目前不成立。

这是当前科研闭环最直接的版本证据缺口。

### 5.2 离线 Benchmark 仍不是真实软件工程任务评测

`research/benchmarks/src/engine.ts` 是协议参考状态机，任务是由固定 fixture 生成的故障场景。即使新 Offline Runner 能生成 30 个任务、四配置共 120 次记录，也主要证明 Runner、Schema、Manifest 和预注册消融方向成立。

它尚未证明：

- 能在真实仓库完成 Bug 修复、功能开发或测试任务；
- 多 Agent 比单 Agent 更好；
- WAL/Lease 在真实模型随机性和真实工具副作用下提升成功率；
- 对比 LangGraph、AutoGen、CrewAI、OpenHands、Codex 等外部基线有优势。

### 5.3 真实 Provider 实验证据仍为零或未冻结

仓库有 `provider:smoke`，并对 live 模式设置显式开关、模型白名单、请求数、费用和超时门禁，这是好设计。但 Claim Matrix 明确说明现有检查不调用真实模型 Provider。

同时，生产 `OpenAiResponsesProvider` 的能力矩阵主动承认：

- 未接入 Provider 端 idempotency key；
- 未接入请求状态查询；
- 未接入 Provider 取消端点；
- 客户端 Abort 和重试不等于 Provider 端去重。

因此真实网络故障后的 model invocation 仍只能安全地进入 `outcome_unknown`，无法声称端到端唯一执行。

### 5.4 Process Chaos 证据范围过窄

冻结 Process Check 自己声明只覆盖 Team Workflow Return 的 1/40 固定窗口和固定 seed，Provider 仍是本机 Fake HTTP。它没有覆盖：

- Dynamic Engine 的完整崩溃矩阵；
- Model submit/response、Tool 外部副作用、Evidence、Checkpoint、Return 所有窗口的真进程强杀；
- 跨机器、网络文件系统、系统断电；
- 真实 Provider 和不可回滚外部 Tool。

这一层可以叫“窄范围 E3”，不能叫“完整进程级混沌验证”。

### 5.5 持久化不是数据库级或断电级 durability

`JsonFileRuntimePersistence` 使用 generation CAS、同目录临时文件和原子 rename，能防止常见的半份 JSON 和并发覆盖，这是合理的本地原型方案。但源码未看到文件与目录 `fsync`，所以不能保证突然断电或存储控制器缓存丢失后的 durability。

另外，当前以较大的全局 JSON Snapshot 为主：

- 数据量增大后写放大明显；
- 多进程竞争依赖本地文件系统语义；
- 跨主机/共享盘的锁与 rename 语义未证明；
- 没有数据库事务、增量日志或独立快照压缩策略。

### 5.6 Lease/Fencing 只证明单机文件系统所有权

现有 Lease 设计对本机多进程很有价值，但它不是 Raft/Paxos/数据库锁，也没有网络分区、时钟漂移、多主机故障模型和线性一致存储。复试中应说“单机持久 Lease/Fencing”，不要泛化成“分布式一致性已解决”。

79 个 `tests/*test.ts` 中，有 4 个文件未被任何 `package.json` script 收录：

### 7.1 为什么它值得讲

这个项目有四个明显的复试亮点：

1. **不是套壳**：核心 Runtime、协议、上下文、工具、权限、MCP、多 Agent、Electron 和持久化均有自研实现。
2. **问题有研究味道**：从“如何让 Agent 工作”推进到“外部调用结果不确定时如何安全恢复”。
3. **能承认系统边界**：`outcome_unknown`、at-least-once、Provider 能力矩阵和 Claim–Evidence Matrix 体现了工程诚实性。
4. **有正反实验结构**：baseline 与 no-wal/no-recovery/no-lease 消融，能够解释机制为何需要，而不是只展示功能截图。

### 7.2 老师最可能认可的贡献

- 将 Agent 执行抽象为可持久化的 Job/Task/Run/Evidence/Return/Checkpoint 状态系统；
- 用 Attempt、Evidence 新鲜度和独立 Review 防止旧结果污染新执行；
- 把模型和工具外部调用分成提交前、在途、已收结果、已提交四类状态；
- 对无法确认的外部副作用选择阻断和人工处置，而不是不安全重试；
- 用消融实验展示 WAL、恢复和 Lease 的方向性作用。

### 7.3 老师最可能追问的薄弱点

- 为什么叫 WAL，它与数据库 WAL 有什么相同和不同？
- 既然 Provider 不支持状态查询，如何证明请求没有重复执行？
- Lease 过期时两个进程同时工作怎么办，Fencing 在哪个提交点检查？
- Fake Provider 实验对真实模型有什么外部有效性？
- 多 Agent 相对单 Agent 的收益在哪里，是否只是增加调用次数？
- 真实任务集、统计置信区间和失败案例在哪里？
- 为什么最新代码的 Frozen Artifact 仍绑定旧提交？

如果能诚实回答这些问题，本项目在复试中会比“做了一个智能助手”更有区分度。

## 八、补足优先级

### P0：一周内必须完成

1. 在独占、干净依赖环境串行执行 `check`、全部测试、Runtime-E2E、Process Chaos、Benchmark 和 Electron Build，保存完整退出码与日志。
2. 增加唯一 `test:all` 或自动发现入口，把遗漏的 4 个测试文件纳入门禁。
3. 更新根 README 和新增 `STATUS.md`，写清最新能力、最新数字、证据等级和限制。
4. 以 `3c78dca` 或后续最终提交重新冻结 `artifacts/v0.2`，Manifest 必须绑定最新 commit。

### P1：两到三周完成

1. 设计 20–30 个真实仓库任务，至少包含修 Bug、补测试、修改配置和多文件功能。
2. 对比单 Agent、固定多 Agent、动态多 Agent；使用相同模型、预算、任务和次数。
3. 每个配置重复多次，输出 Wilson/Bootstrap 置信区间、McNemar 配对检验或其他合适统计。
4. 扩展真进程矩阵到 Model、Tool、Evidence、Checkpoint、Return 的主要崩溃窗口。
5. 在有预算硬门的前提下完成少量真实 Provider smoke，并冻结脱敏原始记录。

### P2：论文/开源前完成

1. 使用第二台机器或外部同学无指导复现 Frozen Artifact。
2. 引入 CI、覆盖率门禁、Release Tag、License 和最小贡献说明。
3. 把大型协调器和 Controller 拆分为独立状态机/Use Case，降低后续修改风险。
4. 若目标是多机运行，迁移到具备事务/CAS 语义的持久层，并重新定义故障模型；不要直接把本机文件 Lease 外推到分布式场景。

## 九、最终评判

God-Agent 当前已经完成了“工程原型闭环”，并且可靠性机制的深度足以支撑一次有含金量的考研复试介绍。主测试 484/484、Runtime-E2E 10/10、Process Chaos 2/2 和真双进程 smoke 通过，使当前工程与恢复机制判断的可信度明显提高。它最强的证据是源码结构、状态机设计、较丰富的恢复测试和诚实的边界建模；最弱的环节不是代码功能，而是最新版本证据冻结、真实任务外部有效性、统计分析和第三方复现。

因此，本智囊团不建议继续无边界堆功能。下一阶段应围绕“最新版本可复现 + 真实任务对照 + 真进程故障矩阵 + 统计结论”收口。只要完成 P0，并补一小批可公开演示的真实任务，复试准备度可以从当前 85 分提高到约 91 分；若要称为论文级科研闭环，则仍需完成 P1/P2，特别是外部基线、真实 Provider/Tool 和独立复现。

**最终综合分：78/100。**  
**置信度：90%。**  
**裁决标签：强工程研究原型；适合复试，尚非论文完成态或生产完成态。**
