## 1. 项目定义

God-Agent 是一个从零实现的本地 Agent Runtime 研究原型。它的目标不是只模仿 Codex 的界面，而是建立一个可恢复、可审计、可扩展的 AI 软件工程执行底座。

目标形态包含两条执行链：

1. **Codex 式单 Agent / 多 Chat 链**：每个 Chat 有独立 Thread、Turn、Context、模型配置、取消和恢复状态，可以并行执行。
2. **父子 Agent / 角色专家团链**：父 Agent 拆解任务，子 Agent、评审 Agent和专家角色协同，通过 Task、Evidence、Shared Board、Return 和 Receipt 交付。

两条链共享 Model、Tool、Skill、MCP、权限、沙箱、WAL、Lease 和持久化内核，但 Job 所有权、资源预算和状态推进必须隔离。

## 2. 当前客观定位

| 目标层级 | 当前裁决 | 允许表述 |
|---|---|---|
| 可运行学习项目 | 已达到 | 可以本地构建和执行 CLI/Electron 主链 |

| Codex 完整替代 | 未达到 | 不得宣称能力等价或复制其专有实现 |

## 4. 事实与证据等级

| 等级 | 定义 | 可以如何使用 |
|---|---|---|
| E0 | 想法、草图、未执行计划 | 只能写“计划”“假设” |
| E1 | 源码存在或静态检查通过 | 可以写“已实现接口/组件”，不能写“真实跑通” |
| E2 | 单元/集成测试可重复通过 | 可以写“在测试条件下通过” |
| E3 | 生产组装、本机真实文件/子进程 E2E 通过 | 可以写“本机实现检查通过”，必须注明 Fake/真实 Provider |
| E4 | 冻结版本、外部复核、重复实验和统计分析 | 才能作为论文主要实验结论 |

证据升级必须同时记录：commit、环境、命令、原始结果路径、摘要哈希、失败用例和限制条件。

## 5. 需求、测试、实验编号

- 功能需求：`FR-领域-序号`，例如 `FR-LEASE-001`。
- 非功能需求：`NFR-领域-序号`，例如 `NFR-REL-001`。
- 测试用例：`TC-领域-序号`，例如 `TC-DYNLEASE-001`。
- 实验：`EXP-研究问题-序号`，例如 `EXP-RQ1-001`。
- 风险：`RISK-序号`。
- 架构决策：`ADR-序号`，需要单独建立 ADR 时再新增文件。

## 6. 状态定义

所有需求与任务只使用以下状态：

- `Proposed`：已提出，尚未评审。
- `Accepted`：边界明确，可以实施。
- `In Progress`：正在实施，不能对外称完成。
- `Implemented`：代码完成但验证未全部通过。
- `Verified`：规定证据和门禁全部通过。
- `Blocked`：有可复现阻塞条件。
- `Rejected`：明确不做并记录原因。

`Done` 不作为模糊状态使用；完成必须写成 `Verified` 并附证据。

## 7. 统一完成定义

一项工程能力只有同时满足以下条件才算 `Verified`：

1. 需求边界和非目标已写入 D01。
2. 生产代码不存在空接线或仅测试接线。
3. 正向、异常、恢复、并发和权限用例全部通过。
4. `npm run check`、相关专项、Electron（如涉及）和 `npm test` 全绿。
5. 没有新增敏感信息、真实凭据或未声明外部费用。
6. 失败可单条复现，原始报告可定位到 commit。
7. D02 更新实际状态，D04 记录真实过程和负结果。
8. 对外表述没有超出证据等级。

## 8. 禁止夸大的表述

在对应证据达到 E4 前，禁止写入简历、复试或论文结论：

- “完整复刻 Codex”或“拥有 Codex 全部能力”。
- “端到端 exactly-once”。
- “真实 Provider 零重复调用”，除非真实 Provider 实验和外部查询证据成立。
- “可承载 5000 Agent”或把 Task 数等同于 Agent 数。
- “线上稳定并发为 4/8”，本机 Fake Provider 数据不能外推线上。
- “论文已完成”或“可直接投稿”，除非 D05 的投稿门槛全部通过。

## 9. 当前最优先事实

当前最高优先级不是继续包装 UI，而是修复 Dynamic Engine 的生产 Lease 所有权闭环，并用真正的 App Server 双实例/子进程 kill-restart 验证。完成前，父子 Agent 底座只能称为“功能原型”。
