## 1. 课题定义

暂定课题：**面向长程多智能体软件任务的可恢复执行与副作用安全机制研究**。

God-Agent 是研究载体。项目同时包含 Codex 式单 Agent/多 Chat 链和动态父子 Agent/角色专家团链，研究重点不是界面相似度，而是模型、工具和多角色协作遇到崩溃、并发接管和结果未知时，Runtime 如何保存事实、拒绝旧 Owner、恢复调度并避免盲目重复副作用。

## 2. 研究问题

- `RQ1`：WAL 与稳定 Invocation ID 能否降低崩溃恢复中的重复模型/工具调用？
- `RQ2`：Job Lease 与 Fencing 能否阻止双实例和旧 Owner 的并发状态提交？
- `RQ3`：Return Receipt 与父 continuation 协议能否降低父子 Agent 的丢 Return、重复消费和父级停滞？
- `RQ4`：上述机制的可靠性收益会带来多少延迟、吞吐、存储和恢复开销？

这些是待实验回答的问题，不是当前结论。

## 3. 当前客观基线

### 3.1 已有能力

- 本地 CLI/Electron 主链、Chat/Turn 生命周期和执行路由已有实现。
- Model/Tool WAL、`outcome_unknown`、人工处置、Lease Store/Fencing、Return/Receipt、固定软件团队 Workflow 已有代码和自动化测试。
- Dynamic Engine production Lease、取消线性化、迟到 Model/Tool 栅栏和 Snapshot v7 generation/state-capability CAS 已通过独立 E2 证伪。
- 当前集成候选 `npm run check`、19/19 pretest、482/482 主测试、Snapshot 24/24、Lease 21/21 通过。
- 真 App Server Process Chaos 已完成 Team Workflow Return 窄窗口 1 个 seed，可称“窄范围 E3 Process Check”；不能称 GATE-40 完成。
- 当前可称为“系统化本地工程原型”；主体结论仍为 E2，仅明确记录的真进程窗口属于 E3。

### 3.2 尚未达到

- Dynamic 尚未完成真实双 App Server 的全操作边界 E3；E2 闭环不能替代跨进程结论。
- Process Chaos 标准矩阵仅完成 1/40；Dynamic Return、Tool、副作用未知、Workflow stage commit 与 fenced release 等窗口尚未覆盖。
- Chaos 的全局测试时钟会连带快进 stale-lock，报告元数据与哈希链仍不完整。
- Scheduler queue 仍依赖内存，Runtime 仍以单 JSON 全量快照为主。
- 专家团角色和固定团队 ID 仍硬编码，Workflow 的 Skill 仍没有形成可配置 Role Pack。
- 缺 CI、正式安装发布、真机 UI E2E、真实 Provider 受控样本、对照/消融统计和外部复核。

因此当前不能称“完整复刻 Codex”“生产级多智能体平台”或“论文已经完成”。

## 5. 负结果与失败发现

### NEG-001：可选 ownership 造成生产闭环假象

- 观察：Dynamic Engine 接口允许可选 ownership；生产组装没有注入。
- 进一步观察：`provideFeedback()`、`cancel()` 未走 ownership；Return claim 可能早于 AgentLoop 取得 Lease。
- 风险：组件 Lease 测试全绿仍不能证明生产 Dynamic 状态全受 fencing 保护。
- 研究价值：说明“机制存在”与“机制覆盖所有 commit boundary”是两个不同变量。
- 下一步：用 TC-DYNLEASE-001～014 先构造可失败的生产组合测试，再修改接线。

### NEG-002：现有 Runtime-E2E 的方法效度不足

- 观察：测试使用生产 Store/WAL/真实 JSON，但 Lease 场景直接使用 `PersistentRuntimeLeaseStore`；进程退出是 `SimulatedProcessExit`。
- 风险：测试可证明组件行为和部分文件恢复，不能证明 App Server kill/restart 后的生产调用链。
- 研究价值：促使实验门禁拆分为 Implementation Check、Production Assembly Check 和 Process Chaos Check。
- 下一步：按 TC-CHAOS-001～008 建立真实子进程 Harness。

### NEG-003：容量数字不能从 Task 数推导 Agent 并发

- 观察：任务、Run、Agent、Provider 调用和并发在系统中不是同一个量。
- 风险：用“5000 Task”包装成“承载 5000 Agent”属于错误外推。
- 下一步：固定指标定义，按 spike/steady/soak/recovery drain 逐级测得绑定机器和 commit 的安全容量。

### NEG-004：实例级 generation 不能代表状态视图身份

- 观察：第一版 Snapshot CAS 能拒绝一次 stale save，但 `load()` 后丢弃新状态会刷新 persistence 实例 generation，使旧 Store 重新获得写权限。
- 进一步反例：第二版 wrapper capability 若在校验后重新读取公开属性，可被 alternating getter 在内存 TOCTOU 窗口注入旧 Store。
- 修复证据：generation 绑定完整 state wrapper；十个 Store/数组引用一次捕获并从私有 identity 序列化；独立攻击矩阵 7/7。
- 研究价值：说明磁盘 CAS 线性化正确，不代表 API capability 与内存快照身份自然正确。

### NEG-005：真实进程 Harness 不等于完整 Process Gate

- 观察：Harness 真实启动、kill/restart 和重载成立，但全局 `Date` 偏移同时改变 Lease TTL、stale-lock 年龄和锁超时；最初的 30 秒耗时还包含未清理 timer。
- 修复证据：timer 三路径已清理，独立子进程探针与 `return_god=1` 断言通过。
- 保留缺口：全局时钟隔离、报告环境/fencing/WAL/哈希字段和剩余 39/40 窗口未完成。
- 研究价值：实验系统必须区分“真实进程证据”“故障点控制变量”和“完整覆盖率”。

负结果不得在后续版本删除；若被修复，应追加“修复证据”和新状态，保留原始发现。

## 10. 复试说辞

### 10.1 30 秒版本

我在做一个长程多智能体任务的可恢复执行原型 God-Agent。项目有单 Agent 多 Chat 和父子 Agent 两条链，我把研究重点放在崩溃恢复，而不是界面仿制：用 WAL 记录模型和工具调用事实，用 Lease/Fencing 拒绝旧 Owner，用 Snapshot generation/state capability 阻止旧状态覆盖，用 Return Receipt 约束父子结果消费。目前 Dynamic 生产接线和 Snapshot CAS 已完成 E2，真实 App Server kill/restart 只完成 Team Return 窄窗口 1/40；所以我能展示研究方法和可复现反例，不能把它包装成完整生产系统。

### 10.2 2 分钟版本

我的课题来自一个实际问题：Agent 执行长程软件任务时，不只是生成文本，还会调用模型、写文件、运行工具并让多个子 Agent 协作。如果进程恰好在“外部动作已经发生、结果还没保存”时崩溃，简单重试可能造成重复副作用；如果两个实例同时恢复同一任务，还可能互相覆盖。

我从零搭建了 God-Agent 研究原型，把执行过程拆成 Thread、Job、Task、Run 和 Invocation。模型与工具调用通过 WAL 保存提交前、结果已收和最终提交等事实；Job 使用 Lease 和单调 Fencing Token，使旧 Owner 即使恢复运行也不能迟到写入；父子协作使用 Return claim/consume Receipt，让父 Agent 根据持久事实继续。

我没有把测试数量直接当成科研结论。全盘审计先发现 Dynamic ownership 没有覆盖生产 commit boundary；修复后，独立审计又连续构造出 Snapshot CAS 的两类反例：`load()` 给旧 Store 续票，以及 alternating getter 在校验和序列化之间注入旧状态。我把 generation 改为绑定完整 state capability，并从一次捕获的私有稳定引用生成快照，这些反例才转绿。随后真实 Process Harness 启动并强杀 App Server，通过公共 RPC 与原始 JSON 验证恢复，但严格只计为 Team Return 的 1/40；全局时钟隔离、其余 39 个窗口和完整报告哈希链仍未完成。下一步是补 Dynamic 双实例与八窗口矩阵，再做 full/no-WAL/no-Lease 消融和统计，而不是提前宣称论文或生产级完成。

### 10.3 追问回答骨架

- **为什么不用数据库事务直接解决？** 数据库事务只能覆盖本地状态，无法回滚已经发出的模型请求和外部工具副作用；因此还需要 Invocation ID、WAL、可查询结果或 `outcome_unknown` 人工处置。
- **Lease 已经能互斥，为什么还要 Fencing？** Lease 过期后旧进程可能仍在运行；Fencing Token 让存储层拒绝旧 epoch 的迟到提交。
- **这是不是 exactly-once？** 不是端到端 exactly-once。本地可做到幂等提交和拒绝旧 Owner，但不可查询的外部副作用仍可能未知，只能停止自动重放。
- **400 多个测试说明什么？** 说明组件和既定集成条件下有较宽的回归覆盖；不说明生产双实例、真实 Provider 或大规模容量已经成立。
- **你的创新在哪里？** 当前只能说是把 WAL、Fencing、Return Receipt 和 Process Chaos 系统化组合并针对父子 Agent 定义可验证不变量；是否构成论文创新要经过相关工作检索、对照实验和导师评审。
- **最大的失败是什么？** 第一版 generation CAS 仍能被“丢弃 reload 后保存旧 Store”绕过，第二版又暴露内存 TOCTOU；这说明磁盘原子性、API capability 和状态身份是三个不同问题。我保留了负结果，并用独立反例驱动到第三版。

## 15. 科研训练式沟通协议

后续围绕 God-Agent 的讨论默认采用科研训练模式。目的不是堆砌术语，而是让每次产品决策都转化为问题定义、证据判断和学术表达训练。

### 15.1 交流规则

1. 首次出现专业术语时，同时说明严格定义、通俗解释和 God-Agent 中的实例。
2. 每项结论必须标明它属于研究假设、源码观察、测试证据、实验结果还是外部文献结论。
3. 对“稳定、可靠、高并发、创新、生产级”等强表述，必须追问指标、对照、样本、边界和证据等级。
4. 发现概念混用时直接纠正，例如区分 Task/Run/Agent/并发，区分幂等、at-most-once、at-least-once 和 exactly-once。

### 17.2 新增负结果与修复状态

#### NEG-006：非确定临时路径污染 Runtime-E2E 错误投影（已修复，历史保留）

#### NEG-010：Process fault point 持久化等待间歇性超时（已修复，总控独立复验通过）

- 原始现象：Artifact 独立验收首次运行 Process Chaos 专项时仅 1/2，通过用例中的正向流程约 22.4 秒后失败。
- 错误原文：`Timed out waiting for persisted process-chaos fault point`。
- 复跑现象：立即执行同一专项得到 2/2。
- 根因：Harness 在 Provider 刚收到 `return_god` 请求后才开始每 10ms 读取和解析约 8MB 的 `runtime-state.json`；此时约 2MB 响应尚未完成发送，高频读取又与 Windows 原子写盘争用，导致 20 秒窗口偶发看不到已持久化 fault point。
- 修复机制：执行前注册状态观察器；用 `fs.watch` 事件驱动观察并以 250ms 低频读取兜底；Provider 等待点绑定 `response.end` flush 回调；fault point 总窗口调为 45 秒、Provider response 窗口调为 30 秒；超时诊断携带 `fileEvents`、`readAttempts`、最后 Job/Return/Invocation 以及读/监听错误。
- 修复范围：仅修改 `process-chaos-harness.ts`，没有改变正式科研矩阵仍为 1/40 的口径，也没有引入真实 Provider。
- 修复后证据：员工连续四轮执行专项均 2/2，`npm run check` 通过，且没有遗留 App Server 进程。
- 总控独立复验：Process Chaos 专项 2/2 通过，正向用例约 32.5 秒，无遗留 App Server 进程。
- 当前状态：已修复并通过总控单轮、Frozen/Clean 语义投影复验。证据只覆盖参考环境与窄范围窗口，不得升级为跨 Windows/Node 组合普适稳定。

#### NEG-012：Clean Process Manifest 的 UTC 日期类型转换（操作脚本已纠正）

- 原始现象：同机干净副本中的 Process Manifest 首次 create 被 canonical UTC ISO 校验拒绝。

- 修正后结果：Clean Process Manifest create/verify 通过。
- 裁决：这是操作脚本的类型转换问题，不是 Agent Runtime、Process 恢复协议或 Manifest 校验器缺陷；校验器拒绝非规范输入符合预期。
- 科研要求：首次拒绝与人工修正必须同时保留，不能只归档成功结果；后续自动化脚本应直接保留字符串或显式规范化日期。

### 18.3 关键反例与根因判断

#### NEG-013：同一 Thread 无单活 Turn

- 现象：Lifecycle 创建 Turn 时只检查 Thread active，没有拒绝已有 `in_progress` Turn。
- 风险：同一 Chat 的两个 Turn 可并发，Context Builder 会跳过未完成前序 Turn，语义取决于竞态时序。
- 裁决：多 Chat 并行的 E2 证据不能证明同一 Chat 线性执行。
- 计划：RT95-101；默认单活并建立 queue/reject/cancel-and-replace 明确策略。

#### NEG-014：Job Lease 与全局 Snapshot CAS 粒度冲突

- 现象：Lease 按 Job，但持久化写入仍覆盖全局 Snapshot。
- 风险：两个 App Server 分别合法持有不同 Job Lease 时仍可能 generation 冲突。
- 裁决：当前证明了同 Job 所有权互斥，没有证明不同 Job 的真正多进程隔离。
- 计划：RT95-103；Job 分区状态、Journal、Proof 和 Lease 对齐，并保留 Snapshot v7 兼容迁移。

#### NEG-015：动态生产链不能先冻结完整 Task Graph

- 现象：Task 在 `run_agent` 执行时逐个创建，生产 Schema 缺少完整 scope/nonGoals/requiredOutputs/acceptance/budget/side-effect contract。
- 风险：同一模型轮新 Task 无稳定 ID 可互相引用，Runtime 无法证明 Requirement 没有漏拆。
- 裁决：组件存在 DAG，不等于生产动态链存在完整 Graph Pre-Commit。
- 计划：RT95-201～205；采用 `Draft → Validate → Atomic Commit → Dispatch`。

#### NEG-016：不存在持续 Supervisor Loop

- 现象：父模型发出一批 Child 后等待 `Promise.all`；Child 增量事件主要进入 UI，不进入父控制循环。
- 风险：无法增量解锁、主动指导、运行中重规划和从持久事实恢复完整监督。
- 裁决：当前是批量委派，不是持续监督型父子 Runtime。
- 计划：RT95-301～307；事件驱动持久 Supervisor，模型只在决策点被唤醒。

#### NEG-017：Heartbeat 只是 Store 能力

- 现象：Task 有 heartbeat 字段和 Store 方法，但生产执行器没有周期调用。
- 风险：不能可靠区分慢、阻塞和失联，也不能按副作用等级安全替换。
- 计划：RT95-305～306。

#### NEG-018：摘要 Review 与 Requirement 完成证明断裂

- 现象：Reviewer 主要审 Worker Summary，缺 criterion→Artifact/Test/Oracle 映射，也没有 Completion Proof 对象。
- 风险：Worker 自报成功、零 Task 或漏拆验收项仍可能被错误裁决完成。
- 裁决：当前 Review/Return 小闭环存在，Requirement 级完成闭环不存在。
- 计划：RT95-401～407。

## 19. W0 科研闭环实验日志

### 19.1 研究问题与假设修正

本轮首先发现原 `falseCompletion` 构念把“Runtime 在线完成决策是否安全”与“终态后业务是否真的完成”混为一谈。关键反例是：Runtime 当时的 Proof 全部自洽，但 terminal 后独立 Oracle 证明业务仍未完成；旧规则会漏记最危险的隐蔽假完成。

修正为两个不可互推的构念：

- `completionDecisionValidity`：只使用完成决策边界之前 Runtime 可见的 Evidence、Proof、blocking contradiction 和 outcome unknown；
- `falseCompletion`：terminal 后由独立 Ground Truth 或 criterion Oracle 回溯标记，Oracle unavailable 时为 missing。

非 Effect criterion 使用 `caseId + criterionId + requirementRevision` 进行终态后 join；Ground Truth 在 terminal 前进入 Runtime Context、Prompt、Tool、Proof 或恢复决策时，该 case 直接 invalid。

## 20. 2026-08-20：计划详细度被驳回后的科研闭环纠偏

### 20.1 新增负结果

#### NEG-019：测试数量和计划标题制造了“可执行性错觉”

观察：项目已经列出 100 个工程 WP、150 个顶层 TC 和 66 个科研/SOP 门禁，但用户验收认为计划和测试仍远远不够。

量化复核：

- 100 WP 全部 `NotVerified`、64 个 P0、Evidence 全空；
- 150 TC 全部 `Designed`、122 个 P0、顶层 Evidence 全空；
- 只有 17/150 顶层 TC 挂候选变体；122 个 P0 中 106 个没有任何候选变体；
- 46 个 W0 变体全部是非生产组装的 E2 组件候选；
- 66 个 Research/SOP 项的 command、Raw、Evidence、executor 和 reviewer 均为空。

结论：此前解决了“分母不清”和“伪 Verified”，但没有解决“新执行者能否仅凭合同复现”。测试条目数量、测试声明数量和一次全绿不能替代执行合同密度。

Claim 影响：W0 仍可称测量合同小闭环；不得称 SOP 已能复现 RT95、科研已闭环或 95% 计划已经可直接完成。

#### NEG-020：研究问题和假设身份不一致

观察：D04 第 2 节使用 RQ1～RQ4，18.6 又使用一个总 RQ 与 H-RT95-1～4，D11/EXP-RT95-001 要求 RQ1～RQ6。三套编号和范围不一致。

风险：同一实验可能事后挂到不同问题；Graph、Namespace 或 Quota 的因果 Claim 没有对应的单变量消融；预注册后再补实验会引入选择性报告。

修复原则：正式预注册前必须冻结一个机器可读 RQ/H Ledger。建议只把最有数据基础的 RQ1～RQ4作为主论文问题，RQ5/RQ6 暂列 secondary/descriptive；没有消融和阈值时不写因果结论。

#### NEG-021：组级追踪表漏掉三个 P0，Wave 漏掉 B17

观察：D11 附录 D 的范围映射展开后只覆盖 147/150，漏 TC-035、TC-036、TC-039；附录 B 漏 B17“模型决策点唤醒”。

影响：即使按旧表全部执行，也可能留下 Task claim、文件 claim 和 unknown 人工裁决三个 P0 空洞；Supervisor 的“确定性机制何时唤醒模型”也没有明确实施 Wave。

修复建议：TC-035→B18/C08/B27；TC-036→B10/D04/D10；TC-039→B26/C04/E11；B17 primaryWave=W5。最终映射仍需 ADR 和机器 Validator 审核。

#### NEG-022：补强计划第一次交叉审查仍不可执行

三名独立 Reviewer 首轮均返回 `ReviewerReturned`，主要反例：

- 文档写成“在线性化点前 reject”，实际会产生双 Server read-check TOCTOU；
- 只有 Job partition，没有 Thread partition，无法同时证明同 Thread 单活和跨 Thread 真并行；
- v7 迁移目标漏了 Global/Thread/无 Job 对象和 Lease fencing 历史；
- W1 测试清单混入 W2 Cancel/ACTIVE、W6 Wait 和 W9 Final Receipt；
- reject 让 A03 暂不得分，但 A15/A16 硬依赖 A03，导致 A 域 15/16 目标不可达；
- CaseVariant 预填 Evidence/Proof、正式样本允许模糊 Pilot 后调整，存在伪证据和 optional stopping 风险。

修复：Thread admission 改为同一 compare-and-commit；布局扩为 Global/Thread/Job 三域；Lease 校验与 HEAD swap 放入同一 fenced critical section；A03 改为 W7 显式持久 enqueue、W10 复验；未来 Wave 变体移出 W1；预期产物与运行后 Evidence 分离；正式 n 在 confirmatory run 前冻结。

科研意义：详细文档也会携带错误不变量。计划必须像代码一样接受反例攻击和独立 Review，不能因为篇幅增加就宣称可执行。

### 20.2 “先形成科研闭环”的两层含义

用户要求先把科研形成闭环，再在其上迭代。必须区分：

1. **方法闭环（现在可完成）**：RQ/H、变量、Baseline、消融、故障、Seed、样本量、Oracle、Raw Schema、统计、反例、Claim 和复现 SOP 全部预注册；
2. **证据闭环（必须等待 Runtime 机制）**：按冻结协议执行 Dynamic E3、正式重复、统计、外部基线和无指导复现，最后形成 Research Completion Proof。

不能为了“下周前闭环”把方法闭环说成论文证据闭环。离职前最高价值动作是把方法闭环和执行 SOP 冻结到新 Chat 可接手，然后沿 W1～W12 逐项填真实 Evidence。

### 20.3 建议冻结的 RQ1～RQ6 结构

下表是预注册候选，不是当前已冻结事实：

| RQ | 问题 | 主要自变量 | 主要因变量 | 核心反例 |
|---|---|---|---|---|
| RQ1 | WAL、稳定 Invocation ID 与副作用分类能否降低重复调用并正确暴露 unknown？ | full/no-model-WAL/no-tool-WAL/no-human-resolution | duplicate effect、known/unknown、false completion、classifier FNR | non-replayable 被盲重试或 unknown 被隐藏 |
| RQ2 | Job Lease/Fencing 与 Job 分区能否消除双 Owner、旧提交和跨 Job 冲突？ | full/no-fencing、global/partition、takeover fault | double commit、stale-token accept、cross-job conflict、RTO | 接受一个旧 token、A 污染 B、全局 generation 阻塞 A/B |

| 字段 | 含义 |
|---|---|

### 20.6 科研执行顺序与停止条件

1. 先完成 EXP-001～010/013/017～023 的方法合同和 Baseline 可执行性，不先跑大矩阵；
2. 优先补 W1/W2 的 122 个 P0 中缺失的 `caseVariant`；
3. 顺序固定为 Dynamic E3 → GATE-40 功能覆盖 → Pilot → EXP-006 样本量 → 正式 paired runs；
4. 统计脚本只读 Raw 自动生成表图；
5. 完成内部结果后再进行 R4 外部无指导复现和 Claim 审稿。

任一双活、旧 fencing token 提交、non-replayable 盲重放、false completion、跨 Job 泄漏、Artifact 变化无法解释、Instrumentation 丢事件、Oracle 冲突、环境/Commit/Fixture 偏离预注册、意外真实 Provider、残留资源或队列不收敛，立即停止该条件，保存现场并降级 Claim。
