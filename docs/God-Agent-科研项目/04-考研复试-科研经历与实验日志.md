## 1. 课题定义

暂定课题：**面向长程多智能体软件任务的可恢复执行与副作用安全机制研究**。

God-Agent 是研究载体。项目同时包含 Codex 式单 Agent/多 Chat 链和动态父子 Agent/角色专家团链，研究重点不是界面相似度，而是模型、工具和多角色协作遇到崩溃、并发接管和结果未知时，Runtime 如何保存事实、拒绝旧 Owner、恢复调度并避免盲目重复副作用。

## 2. 研究问题

- `RQ1`：WAL 与稳定 Invocation ID 能否降低崩溃恢复中的重复模型/工具调用？
- `RQ2`：Job Lease 与 Fencing 能否阻止双实例和旧 Owner 的并发状态提交？
- `RQ3`：Return Receipt 与父 continuation 协议能否降低父子 Agent 的丢 Return、重复消费和父级停滞？
- `RQ4`：上述机制的可靠性收益会带来多少延迟、吞吐、存储和恢复开销？

这些是待实验回答的问题，不是当前结论。

## 3. 当前客观基线

### 3.1 已有能力

- 本地 CLI/Electron 主链、Chat/Turn 生命周期和执行路由已有实现。
- Model/Tool WAL、`outcome_unknown`、人工处置、Lease Store/Fencing、Return/Receipt、固定软件团队 Workflow 已有代码和自动化测试。
- Dynamic Engine production Lease、取消线性化、迟到 Model/Tool 栅栏和 Snapshot v7 generation/state-capability CAS 已通过独立 E2 证伪。
- 当前集成候选 `npm run check`、19/19 pretest、482/482 主测试、Snapshot 24/24、Lease 21/21 通过。
- 真 App Server Process Chaos 已完成 Team Workflow Return 窄窗口 1 个 seed，可称“窄范围 E3 Process Check”；不能称 GATE-40 完成。
- 当前可称为“系统化本地工程原型”；主体结论仍为 E2，仅明确记录的真进程窗口属于 E3。

### 3.2 尚未达到

- Dynamic 尚未完成真实双 App Server 的全操作边界 E3；E2 闭环不能替代跨进程结论。
- Process Chaos 标准矩阵仅完成 1/40；Dynamic Return、Tool、副作用未知、Workflow stage commit 与 fenced release 等窗口尚未覆盖。
- Chaos 的全局测试时钟会连带快进 stale-lock，报告元数据与哈希链仍不完整。
- Scheduler queue 仍依赖内存，Runtime 仍以单 JSON 全量快照为主。
- 专家团角色和固定团队 ID 仍硬编码，Workflow 的 Skill 仍没有形成可配置 Role Pack。
- 缺 CI、正式安装发布、真机 UI E2E、真实 Provider 受控样本、对照/消融统计和外部复核。

因此当前不能称“完整复刻 Codex”“生产级多智能体平台”或“论文已经完成”。

## 5. 负结果与失败发现

### NEG-001：可选 ownership 造成生产闭环假象

- 观察：Dynamic Engine 接口允许可选 ownership；生产组装没有注入。
- 进一步观察：`provideFeedback()`、`cancel()` 未走 ownership；Return claim 可能早于 AgentLoop 取得 Lease。
- 风险：组件 Lease 测试全绿仍不能证明生产 Dynamic 状态全受 fencing 保护。
- 研究价值：说明“机制存在”与“机制覆盖所有 commit boundary”是两个不同变量。
- 下一步：用 TC-DYNLEASE-001～014 先构造可失败的生产组合测试，再修改接线。

### NEG-002：现有 Runtime-E2E 的方法效度不足

- 观察：测试使用生产 Store/WAL/真实 JSON，但 Lease 场景直接使用 `PersistentRuntimeLeaseStore`；进程退出是 `SimulatedProcessExit`。
- 风险：测试可证明组件行为和部分文件恢复，不能证明 App Server kill/restart 后的生产调用链。
- 研究价值：促使实验门禁拆分为 Implementation Check、Production Assembly Check 和 Process Chaos Check。
- 下一步：按 TC-CHAOS-001～008 建立真实子进程 Harness。

### NEG-003：容量数字不能从 Task 数推导 Agent 并发

- 观察：任务、Run、Agent、Provider 调用和并发在系统中不是同一个量。
- 风险：用“5000 Task”包装成“承载 5000 Agent”属于错误外推。
- 下一步：固定指标定义，按 spike/steady/soak/recovery drain 逐级测得绑定机器和 commit 的安全容量。

### NEG-004：实例级 generation 不能代表状态视图身份

- 观察：第一版 Snapshot CAS 能拒绝一次 stale save，但 `load()` 后丢弃新状态会刷新 persistence 实例 generation，使旧 Store 重新获得写权限。
- 进一步反例：第二版 wrapper capability 若在校验后重新读取公开属性，可被 alternating getter 在内存 TOCTOU 窗口注入旧 Store。
- 修复证据：generation 绑定完整 state wrapper；十个 Store/数组引用一次捕获并从私有 identity 序列化；独立攻击矩阵 7/7。
- 研究价值：说明磁盘 CAS 线性化正确，不代表 API capability 与内存快照身份自然正确。

### NEG-005：真实进程 Harness 不等于完整 Process Gate

- 观察：Harness 真实启动、kill/restart 和重载成立，但全局 `Date` 偏移同时改变 Lease TTL、stale-lock 年龄和锁超时；最初的 30 秒耗时还包含未清理 timer。
- 修复证据：timer 三路径已清理，独立子进程探针与 `return_god=1` 断言通过。
- 保留缺口：全局时钟隔离、报告环境/fencing/WAL/哈希字段和剩余 39/40 窗口未完成。
- 研究价值：实验系统必须区分“真实进程证据”“故障点控制变量”和“完整覆盖率”。

负结果不得在后续版本删除；若被修复，应追加“修复证据”和新状态，保留原始发现。

## 10. 复试说辞

### 10.1 30 秒版本

我在做一个长程多智能体任务的可恢复执行原型 God-Agent。项目有单 Agent 多 Chat 和父子 Agent 两条链，我把研究重点放在崩溃恢复，而不是界面仿制：用 WAL 记录模型和工具调用事实，用 Lease/Fencing 拒绝旧 Owner，用 Snapshot generation/state capability 阻止旧状态覆盖，用 Return Receipt 约束父子结果消费。目前 Dynamic 生产接线和 Snapshot CAS 已完成 E2，真实 App Server kill/restart 只完成 Team Return 窄窗口 1/40；所以我能展示研究方法和可复现反例，不能把它包装成完整生产系统。

### 10.2 2 分钟版本

我的课题来自一个实际问题：Agent 执行长程软件任务时，不只是生成文本，还会调用模型、写文件、运行工具并让多个子 Agent 协作。如果进程恰好在“外部动作已经发生、结果还没保存”时崩溃，简单重试可能造成重复副作用；如果两个实例同时恢复同一任务，还可能互相覆盖。

我从零搭建了 God-Agent 研究原型，把执行过程拆成 Thread、Job、Task、Run 和 Invocation。模型与工具调用通过 WAL 保存提交前、结果已收和最终提交等事实；Job 使用 Lease 和单调 Fencing Token，使旧 Owner 即使恢复运行也不能迟到写入；父子协作使用 Return claim/consume Receipt，让父 Agent 根据持久事实继续。

我没有把测试数量直接当成科研结论。全盘审计先发现 Dynamic ownership 没有覆盖生产 commit boundary；修复后，独立审计又连续构造出 Snapshot CAS 的两类反例：`load()` 给旧 Store 续票，以及 alternating getter 在校验和序列化之间注入旧状态。我把 generation 改为绑定完整 state capability，并从一次捕获的私有稳定引用生成快照，这些反例才转绿。随后真实 Process Harness 启动并强杀 App Server，通过公共 RPC 与原始 JSON 验证恢复，但严格只计为 Team Return 的 1/40；全局时钟隔离、其余 39 个窗口和完整报告哈希链仍未完成。下一步是补 Dynamic 双实例与八窗口矩阵，再做 full/no-WAL/no-Lease 消融和统计，而不是提前宣称论文或生产级完成。

### 10.3 追问回答骨架

- **为什么不用数据库事务直接解决？** 数据库事务只能覆盖本地状态，无法回滚已经发出的模型请求和外部工具副作用；因此还需要 Invocation ID、WAL、可查询结果或 `outcome_unknown` 人工处置。
- **Lease 已经能互斥，为什么还要 Fencing？** Lease 过期后旧进程可能仍在运行；Fencing Token 让存储层拒绝旧 epoch 的迟到提交。
- **这是不是 exactly-once？** 不是端到端 exactly-once。本地可做到幂等提交和拒绝旧 Owner，但不可查询的外部副作用仍可能未知，只能停止自动重放。
- **400 多个测试说明什么？** 说明组件和既定集成条件下有较宽的回归覆盖；不说明生产双实例、真实 Provider 或大规模容量已经成立。
- **你的创新在哪里？** 当前只能说是把 WAL、Fencing、Return Receipt 和 Process Chaos 系统化组合并针对父子 Agent 定义可验证不变量；是否构成论文创新要经过相关工作检索、对照实验和导师评审。
- **最大的失败是什么？** 第一版 generation CAS 仍能被“丢弃 reload 后保存旧 Store”绕过，第二版又暴露内存 TOCTOU；这说明磁盘原子性、API capability 和状态身份是三个不同问题。我保留了负结果，并用独立反例驱动到第三版。

## 15. 科研训练式沟通协议

后续围绕 God-Agent 的讨论默认采用科研训练模式。目的不是堆砌术语，而是让每次产品决策都转化为问题定义、证据判断和学术表达训练。

### 15.1 交流规则

1. 首次出现专业术语时，同时说明严格定义、通俗解释和 God-Agent 中的实例。
2. 每项结论必须标明它属于研究假设、源码观察、测试证据、实验结果还是外部文献结论。
3. 对“稳定、可靠、高并发、创新、生产级”等强表述，必须追问指标、对照、样本、边界和证据等级。
4. 发现概念混用时直接纠正，例如区分 Task/Run/Agent/并发，区分幂等、at-most-once、at-least-once 和 exactly-once。
5. 每个阶段至少安排一次导师式追问，要求口头解释机制、反例、控制变量和局限。
6. 复试说辞必须能回指 Requirement、Test、Experiment 或 Evidence ID；无法回指的内容降级为计划。

### 17.2 新增负结果与修复状态

#### NEG-006：非确定临时路径污染 Runtime-E2E 错误投影（已修复，历史保留）

- 原始现象：Runtime-E2E GATE-30 首次和后续均出现过确定性检查失败，中间也出现过通过。
- 最小差异：结构化 diff 只命中 `cases[100]`、`cases[101]` 的 `recoveryResult`。
- 根因：`SnapshotConflictError.message` 带入 `mkdtemp` 的 `caseDirectory` 本机绝对路径，使同一固定 seed 的错误投影随临时目录变化。
- 修复：只把本次 case 目录替换为 `<case-directory>`；没有删除 `recoveryResult` 或弱化失败断言。
- 保留证据：错误代码、错误类型、expected/found generation、相对状态文件名、`taskSuccess=false`、Failure、Unknown Outcome、Evidence、重复副作用和安全/恢复指标均继续参与报告或断言。
- 修复后证据：员工 D 专项 10/10、GATE-30 和 check 通过；总控连续两次 GATE-30 通过；员工 C 另一次独立 GATE-30 通过。
- 当前边界：这是参考环境内已修复的确定性缺陷，不证明所有 Windows/Node 组合均稳定；失败日志、修复测试和通过输出均应进入新 Artifact。

#### NEG-007：Windows Process 写盘曾出现 `EPERM` rename（环境风险保留）

- 原始现象：一次 Process 运行在 Windows rename 环节失败，错误为 `EPERM`；后续复跑通过。
- 当前判断：证据不足以把它归为稳定 Runtime 缺陷，也不能因后续通过而删除。
- 风险：杀进程、文件句柄释放、杀毒/索引软件或 Windows 原子替换时序可能影响干净环境复现。
- 后续：冻结时保存失败原文、环境版本和复跑结果；第三方复现若再现，建立独立最小诊断，不以自动重试掩盖。

#### NEG-008：Process `--output` 目录层级误用（SOP 已纠正）

- 原始现象：命令把 `process-chaos-<seed>` 子目录传给 `--output`，Harness 再创建同名 seed 子目录，产生双层目录。
- 根因：调用方误把 case 目录当成父输出目录。
- 当前状态：SOP 已明确 `--output` 接受父目录，seed 子目录由 Harness 创建。
- 裁决：这是 SOP/命令误用，不是 Runtime 缺陷；仍保留以防复核者重复踩坑。

#### NEG-009：Process raw state 仍含本机绝对计划路径（v0.1 采用公开排除）

- 已解决部分：`process-chaos-report.json` 的 `statePath` 与 `rawReportPath` 已固定为安全相对路径，并受运行时 Schema 和 JSON Schema 双重约束。
- 未解决部分：`runtime-state.json` 保存的生产状态仍包含本机绝对计划路径。
- 风险：直接公开会泄漏机器路径；简单字符串删除又可能破坏原始证据与哈希可验证性。

#### NEG-010：Process fault point 持久化等待间歇性超时（已修复，总控独立复验通过）

- 原始现象：Artifact 独立验收首次运行 Process Chaos 专项时仅 1/2，通过用例中的正向流程约 22.4 秒后失败。
- 错误原文：`Timed out waiting for persisted process-chaos fault point`。
- 复跑现象：立即执行同一专项得到 2/2。
- 根因：Harness 在 Provider 刚收到 `return_god` 请求后才开始每 10ms 读取和解析约 8MB 的 `runtime-state.json`；此时约 2MB 响应尚未完成发送，高频读取又与 Windows 原子写盘争用，导致 20 秒窗口偶发看不到已持久化 fault point。
- 修复机制：执行前注册状态观察器；用 `fs.watch` 事件驱动观察并以 250ms 低频读取兜底；Provider 等待点绑定 `response.end` flush 回调；fault point 总窗口调为 45 秒、Provider response 窗口调为 30 秒；超时诊断携带 `fileEvents`、`readAttempts`、最后 Job/Return/Invocation 以及读/监听错误。
- 修复范围：仅修改 `process-chaos-harness.ts`，没有改变正式科研矩阵仍为 1/40 的口径，也没有引入真实 Provider。
- 修复后证据：员工连续四轮执行专项均 2/2，`npm run check` 通过，且没有遗留 App Server 进程。
- 总控独立复验：Process Chaos 专项 2/2 通过，正向用例约 32.5 秒，无遗留 App Server 进程。
- 当前状态：已修复并通过总控单轮独立复验；仍待 baseline Commit、三层 Artifact/Manifest、同机干净副本复现和最终冻结。当前证据只覆盖列明参考环境与窄范围窗口，不得升级为跨 Windows/Node 组合普适稳定。
