# God-Agent 分阶段实施计划

> 文档编号：D02
> 状态：Accepted
> 版本：v1.0.0
> 计划基线：`main@928fe38afa6d038e7fafbd6ff1c54c3c35d58793`
> 总原则：先闭合可靠性，再建设专家团；先获得证据，再包装复试和论文

## 1. 计划目标

本计划把 God-Agent 从“功能和测试较完整的本地原型”推进到“可用于角色专家团扩展、复试演示和论文实验的可靠研究底座”。

计划不以新增页面数量衡量进度，而以以下结果衡量：

- 状态所有权是否唯一。
- 崩溃后是否能确定恢复或明确阻断。
- Tool/Model/Return 是否出现重复副作用。
- 专家角色是否可配置而不是硬编码。
- 实验是否经过生产组装并可由他人复现。
- 文档陈述是否和实际证据一致。

## 2. 总体阶段

| 阶段 | 目标 | 预计周期 | 退出标准 |
|---|---|---:|---|
| Phase 0 | 修复 Dynamic Engine Lease 生产闭环 | 3–5 天 | 生产组合 E2 全操作无无主提交；双实例 E3 待补 |
| Phase 1 | 建立真正 Process Runtime-E2E | 4–7 天 | 子进程 kill/restart GATE-40 全绿 |
| Phase 2 | 收敛持久化和调度恢复 | 7–10 天 | 分区/索引/备份和队列恢复门禁通过 |
| Phase 3 | 建设 Role Pack 与 Team Template | 7–12 天 | 至少三类专家团模板可配置运行 |
| Phase 4 | Tool/Skill/MCP 资源隔离 | 5–8 天 | 每 Job 权限、配额、取消和审计生效 |
| Phase 5 | Electron 真机 E2E、CI、发布 | 5–10 天 | 安装包和关键 UI E2E 可重复 |
| Phase 6 | 科研实验与论文材料 | 2–4 周 | 冻结数据、统计分析、复现包和初稿 |

预计总工期为 7–11 周。该时间是单人连续开发估计，不包含导师修改、真实 Provider 审批和投稿审稿周期。

## 3. 执行规则

每个切片都必须明确：

1. 目标与非目标。
2. 生产文件和测试文件所有权。
3. 需要保持的状态不变量。
4. 最小实现。
5. 专项、全量和故障验证。
6. 回滚点与停止条件。
7. 科研证据和文档更新。

不得把多个 P0 状态机重构塞进一个无法独立验证的提交。默认顺序是：契约测试 → 最小接线 → 双实例测试 → 全量回归 → 文档和实验记录。

## 4. Phase 0：Dynamic Engine Lease 生产闭环

### 4.1 目标

保证 Dynamic Engine 的 `start`、`resume`、`recover`、`provideFeedback`、`cancel`、Return claim/consume、父 continuation、Model commit 和 Tool commit 全部处于同一个 Job Lease/Fencing 上下文。

### 4.2 已知根因

- Dynamic Engine 声明了可选 `ownership`，生产组装没有注入。
- `provideFeedback` 和 `cancel` 没有经过 `withOwnership`。
- Return claim 发生在 AgentLoop 内层取得 Lease 之前。
- `withActiveFencedCommit` 在没有活动 Lease 时会直接提交，因此不能靠 persistence 自动补救。
- 现有测试只覆盖 Dynamic Engine 或 Lease Coordinator，各自没有覆盖生产组合。

### 4.3 切片

#### P0-S1：冻结所有权契约

目标：定义 Engine 层拥有 Job Lease，AgentLoop/Coordinator 只复用同 Job 的嵌套上下文。

计划文件：

- `src/execution/dynamic-agent-execution-engine.ts`
- `src/runtime/execution-lease-coordinator.ts`
- `src/app-server/main.ts`
- `tests/dynamic-agent-execution-engine-test.ts`
- `tests/execution-lease-coordinator-test.ts`

实现要求：

- ownership 不能静默缺失；生产模式缺少 ownership 应启动失败或显式降级并禁止可靠性声明。
- 同 Job 嵌套 Lease 复用原 context，不重复 acquire。
- 不同 Job 嵌套立即拒绝。
- waiting 状态使用可恢复错误/等待反馈，不标记为终态失败。

验证：`TC-DYNLEASE-001` 至 `TC-DYNLEASE-006`。

停止条件：如果无法保证所有持久提交复用同一 AsyncLocal Lease，则不进入下一切片。

#### P0-S2：包裹全部 Dynamic 状态变更

目标：消除无所有权状态写入。

实现要求：

- `start/resume/recover/provideFeedback/cancel` 全部进入 `withJob`。
- Return claim、consume、retry 和父级 Job 状态必须在 active fenced commit 内持久化。
- cancel 与正在运行的 Model/Tool 竞态有唯一裁决。
- startup fact-only recovery 仍不得发起模型调用。

验证：旧 Owner 在每个边界被接管后继续提交，拒绝率必须为 100%。

#### P0-S3：生产组装接线

目标：App Server 构造的 Dynamic Engine 必须获得真实 `ExecutionLeaseCoordinator`。

实现要求：

- 不新增第二套 Lease Coordinator。
- Dynamic、AgentLoop、RuntimeCoordinator 和 Team Workflow 共享同一实例。
- 状态文件和 Lease 文件仍位于本机状态目录，不进入仓库。
- App Server 启动恢复遇到被其他进程持有的 Job 时继续启动并报告等待，不因一个 Job 退出整个进程。

#### P0-S4：双实例集成测试

目标：两个真实生产组装竞争同一个 Job。

验证场景：同时 start、同时 recover、反馈与恢复竞争、cancel 与 Model 返回竞争、旧 Owner 迟到 Model/Tool/Return/Stage commit。

退出标准：

- 1000 轮只有一个合法 Owner。
- 所有 commit boundary 迟到写拒绝率 100%。
- 重复 Model 调用和 Tool 副作用均为 0（确定性本地 Provider/Tool 条件）。
- waiting 的实例不污染 Job 状态。
- `npm run check`、Lease 专项、Dynamic 专项、App Server 集成和 `npm test` 全绿。

### 4.4 回滚点

每个切片单独提交。若生产接线导致行为回归，只回滚当前切片，不移除已经验证的 Lease Store/WAL。禁止通过关闭测试或退回无 fencing persistence 解决。

## 5. Phase 1：Process Runtime-E2E GATE

### 5.1 目标

把当前“生产类 + 内存编排”的 Implementation Check 升级为“真实 App Server 子进程 + 文件状态 + kill/restart”的 Process Check。

### 5.2 必须修正的方法问题

- 报告不能只靠硬编码 `runtimeClasses` 名称证明生产路径。
- Lease 用例必须通过 `ExecutionLeaseCoordinator`，不能只 acquire Lease 后直接改 Store。
- 崩溃必须实际终止子进程，不能只抛 `SimulatedProcessExit`。
- baseline 与消融必须调用同一生产入口，只通过依赖注入关闭 WAL/Lease/Recovery。

### 5.3 切片

#### P1-S1：测试控制协议

新增仅测试环境可用的故障注入点：

- `before_model_submit`
- `after_model_response_before_persist`
- `before_tool_effect`
- `after_tool_effect_before_result_persist`
- `after_return_claim_before_parent`
- `after_parent_before_return_consume`
- `before_workflow_stage_commit`
- `after_fenced_commit_before_release`

故障点必须默认关闭，不得进入公开生产 RPC，也不得接受未认证远程输入。

#### P1-S2：子进程 Harness

- 启动两个 App Server 子进程，共享隔离临时状态目录。
- 通过 JSON-RPC 创建 Thread、Requirement、Job 和 Turn。
- 等待故障点确认写盘后强制终止进程。
- 由第二进程在 Lease 到期后恢复。
- 从公开 RPC 和状态文件独立验证结果。

#### P1-S3：GATE-30

六类各 5 条：Model、Tool、Dynamic Return、Workflow、Snapshot、双实例 Lease。

退出标准：baseline 30/30；重复 Model/Tool 为 0；所有未知副作用进入 outcome_unknown；每条至少一次真实子进程重启和真实 JSON load。

#### P1-S4：GATE-100 和消融

固定 fixture、seed、分片和变体：full、no-model-wal、no-tool-wal、no-recovery、no-lease、no-human-resolution。

输出：JSONL 原始结果、CSV 汇总、Schema 校验、最小 repro、环境清单、commit 和配置摘要。

### 5.4 停止条件

- Harness 无法区分进程实际退出和异常捕获。
- 测试通过需要读取真实 Key。
- baseline 与消融使用不同业务路径。
- 失败报告不能单条重现。

## 6. Phase 2：持久化与调度恢复

### 6.1 目标

解决单 JSON 全量快照和内存 Scheduler 队列在专家团规模下的扩展风险。

### 6.2 切片

#### P2-S1：先测量再重构

- 采集 Snapshot 大小、序列化耗时、rename 耗时、每 Job/Task/Return 扫描次数。
- 用 CPU profile 证明热点，禁止凭感觉改存储。

#### P2-S2：直接索引

- Job → Task/Return/Run/Evidence 索引。
- idempotencyKey → Return/Invocation 索引。
- 终态/活动对象分离索引。
- 保持 v1-v6 快照读取兼容。

#### P2-S3：分区或增量协议

优先方案：每 Job 分区快照 + 小型全局目录；必要时增加 append-only event journal。必须保留原子提交点、校验和和恢复扫描。

#### P2-S4：备份与修复

- 最近 N 个已验证快照。
- 启动校验失败时只读恢复模式。
- 明确的 `verify`、`repair`、`export` 命令。
- 不自动覆盖损坏源文件。

#### P2-S5：Scheduler 恢复

- 持久化等待原因、deadline、依赖和公平性信息。
- 重启后由事实重建 queue，而不是直接丢弃。
- 不自动重放未知 child attempt。

### 6.3 退出标准

- 10 万级历史对象下查询不依赖全表扫描。
- 30 分钟 short-soak 无持续吞吐塌陷，结束后全部 Return drain。
- 人工截断/损坏后可恢复最近一致版本。
- 旧快照迁移和全量回归全部通过。

## 7. Phase 3：角色专家团通用底座

### 7.1 目标

把硬编码软件团队升级为版本化、可复用、可审计的专家团系统。

### 7.2 数据模型

#### Role Pack

- `id`、`version`、`name`、`description`
- System instructions 与输出合同
- 默认模型和 reasoning effort
- Tool/Skill/MCP allowlist
- 文件 Scope、资源预算、重试策略
- 可承担阶段、禁止职责、升级兼容规则

#### Team Template

- `id`、`version`、支持的 execution kind
- Role 节点与 DAG 依赖
- 串行、fan-out/fan-in、Review、投票、仲裁节点
- 输入/输出合同
- 失败、反馈、超时、取消和最终交付策略
- 总预算和每角色预算

### 7.3 首批模板

1. `software-delivery-v3`：产品、架构、工程、测试、负责人。
2. `research-review-v1`：检索、方法、实验、统计、审稿人。
3. `decision-panel-v1`：多专家独立建议、反方审查、裁决者。

### 7.4 关键约束

- Job 创建时冻结 Role Pack/Team Template 精确版本。
- 运行中修改模板不影响已启动 Job。
- 每个阶段 Skill 经过 Role、Template、Job 三层交集。
- 专家团不能绕过 Requirement 确认门和文件 Scope。
- 投票不是多数文本投票；必须有证据、置信度、反例和裁决规则。

### 7.5 退出标准

- 三个模板不修改 Coordinator 源码即可加载运行。
- 每种拓扑完成正常、阻塞、返工、崩溃恢复和预算耗尽测试。
- Team Template 升级和旧 Job 恢复兼容。
- UI 能显示真实角色、依赖、状态和证据来源。

## 8. Phase 4：Tool/Skill/MCP 隔离与预算

### 8.1 目标

共享能力不产生越权、资源争用或一个 Job 拖垮全局的问题。

### 8.2 实施内容

- 统一 `CapabilityGrant`：来源、版本、允许范围、风险、预算和过期时间。
- 每 Job Tool 调用数、MCP 并发、输出字节、墙钟、Token 和费用预算。
- 每次调用记录 Job/Run/Task/Invocation 归属。
- MCP Server 崩溃只影响相关调用；连接可复用时仍按调用隔离权限。
- 固定 Workflow 按阶段启用明确 Skill，而不是全部禁用或全部通配。
- 高副作用 Tool 继续使用二次确认和 outcome_unknown。

### 8.3 退出标准

- 两个 Job 使用同一 Tool/MCP 时结果、预算和取消不串线。
- 单 Job 超限只终止该 Job 的新调用。
- Skill/Tool/MCP 权限扩大被启动前校验拒绝。

## 9. Phase 5：Electron、CI 与发布

### 9.1 Electron 真机 E2E

必须覆盖：启动/握手、创建 Chat、发送、流式过程、切换 Chat、取消、重启恢复、父子 Return、反馈、outcome_unknown、浏览器标签、窗口缩放和历史树。

补充视觉门禁：标准宽度、窄窗口、长代码、长中文、错误/反馈状态、主题与 DPI。

### 9.2 CI

PR 必须运行：

- `npm ci`
- `npm run check`
- `npm test`
- `npm run test:electron`
- `npm run test:lease`
- `npm run test:runtime-e2e`
- `npm run electron:build`
- 依赖、安全、敏感文件和打包范围检查

P0 用例禁止跳过。容量和长时实验分为 nightly，不阻塞普通小改动但失败必须告警。

### 9.3 发布

- 收敛 npm/electron 文件清单。
- Windows 安装包先行，再评估 macOS。
- 版本、迁移、回滚、日志导出和隐私说明。
- 正式发布前处理签名、自动更新、许可证和第三方归属。

## 10. Phase 6：科研实验与论文材料

### 10.1 实验顺序

1. 冻结系统版本和威胁模型。
2. 预注册 RQ、假设、指标、样本量和排除规则。
3. 完成 Process GATE-30 调试。
4. 运行 GATE-100 和消融。
5. 运行 30 分钟和 2 小时稳定性实验。
6. 在明确预算下运行真实 Provider 小样本验证。
7. 统计分析、负结果、局限和外部复核。
8. 生成技术报告、复试 Demo、论文初稿。

### 10.2 论文门槛

未完成以下条件不得标记“可投稿”：

- P0 Lease 与 Process GATE 全部 Verified。
- 原始数据、环境、commit、脚本和哈希完整。
- 至少一个外部基线或可解释对照。
- 多 seed/重复运行和置信区间。
- 负结果、威胁和局限写入正文。
- 导师确认研究问题、贡献、作者顺序和目标刊会。

## 15. Research Artifact v0.1 离职前收口计划（RRA-05，2026-08-20）

本节是面向离职前科研资产保护的追加计划，不覆盖本文原有 Phase 0–6 顺序和历史进度。当前优先级是先把已有可靠性成果收口为 **R2 最小科研可复制包**，再决定是否继续扩展实验；不得把本节解释为 R3、R4、完整 GATE-40 或生产交付计划。

### 15.1 阶段目标与停止边界

| 等级 | 计划含义 | 当前状态 |
|---|---|---|
| R0：文字可读 | 需求、方案、摘要可阅读 | 已达到 |
| R1：作者可重跑 | 原作者可在当前机器复跑 | 已达到；Frozen Artifact 已形成并 verify |
| R2：干净环境可复现 | 未参与开发者仅按仓库说明，在无旧结果载荷的新环境得到可核对结果 | 同机 `git archive` 干净副本门禁已通过；外部第三方无指导复现仍未完成 |
| R3：实验可重复 | 固定重复次数、统计方法和置信区间 | 不在 v0.1 完成声明内 |
| R4：外部独立复现 | 外部人员无口头指导完成并反馈 | 不在 v0.1 完成声明内 |

中央大脑 / Central Control Runtime、完整 Supervisor、完整专家团和完整 GATE-40 均为本轮非目标。真实 Provider 调用、端到端 exactly-once、生产可用、完整 E3/E4 和论文可投稿也不属于本轮允许声明。

### 15.2 RRA-01 至 RRA-04 集成模块

| 模块 | 集成交付 | 不得越过的边界 |
|---|---|---|

### 15.3 强制实施顺序与门禁

必须按以下顺序执行，前一阶段未形成可审计证据时不得跳到后一阶段：

```text
代码 / 测试 / 文档验收
  -> baseline Commit
  -> 以 baseline SHA 生成 Artifact 与 Manifest
  -> 同机干净源码副本复现
  -> 科研诚信审查
  -> artifact Commit
  -> Push / 更新 PR
```

| 顺序 | 阶段 | 必须完成的工作 | 退出门禁 |
|---:|---|---|---|
| 1 | 代码 / 测试 / 文档验收 | 完成 RRA-01～RRA-04；同步核心需求、计划、SOP 和 Claim–Evidence；保留全部失败和限制 | 所有入口与文档一致；G0/G1 通过；无越权文件、无真实 Provider 调用；路径非确定性负结果仍可追踪 |
| 2 | baseline Commit | 由总控提交已经通过阶段 1 的源码、测试和文档，获得唯一 40 位 baseline SHA | 明确文件清单；不包含临时结果、敏感路径、Key 或缓存；该 Commit 只冻结复现基线，不代表 Artifact/R2 完成 |
| 3 | Artifact 生成与完整性 | 以 baseline SHA 分别保存 Model、Runtime-E2E 的原始 JSON/CSV/repro/日志和环境记录；Process 公开包只纳入 `process-chaos-report.json`、`runtime-leases.json`、命令、环境和限制；建立 Manifest 与 SHA-256 | 三层分别 `create`/`verify`；篡改、缺失、多余文件负向检查非 0；raw `runtime-state.json` 因本机路径被明确排除并导致对应 Claim 降级 |

### 19.2 W1 决策包

#### 19.2.1 W1-A：同 Thread 顺序

推荐冻结为 **server-authoritative reject**，但禁止“先读 owner、再创建”的 TOCTOU 实现。`turn/start` 必须在同一个 Thread-partition 原子 compare-and-commit 中完成：`clientRequestId` 去重、active owner 比较、Turn+首个 User Item+admission receipt 最小事实写入和 owner generation CAS。成功请求线性化于 CAS 成功；冲突请求线性化于同一 CAS 的失败分支并返回结构化 `thread_turn_conflict`。Job 在后续确认执行时创建，不塞进 Thread admission 的跨域事务。

明确区分：

- 新 Turn：W1 中 active owner 存在时 reject；
- Guidance/Steering：未来走 W6 持久 Mailbox，不得用第二个 Turn 冒充；
- 人类 Wait 回复：未来走 `wait/reply`，绑定 waitId/jobId/planRevision；
- CLI 内存 FIFO：只称易失客户端缓冲，不计持久队列和恢复能力；
- cancel-and-replace：在完整 CancelSpec、fencing 和副作用 unknown 裁决前禁用。

严格 reject 是 W1 默认准入策略；A03 持久顺序队列延后到 W7，与 Persistent Scheduler 一起实现为显式 `turn/enqueue`/TurnRequest 语义，不能让第二个 `turn/start` 静默变成排队请求。W1 只实施 A01/A02/A04；A03 在 W7 primary implementation、W10 integration verification，使 A15/A16 的最终依赖仍可达。

W1-A 的最小实现切片：

| Slice | 目标 | 主要生产触点 | 必须测试 | 回滚点 |
|---|---|---|---|---|
| A1 | 冻结 conflict API、Thread partition、owner/generation、clientRequestId 和终态集合 | `turn-start.ts`、`lifecycle-store.ts`、`handlers.ts` | Schema 正反例、legacy 调用兼容 | 仅保留明确 reject |
| A2 | 在同一 Thread generation 内原子比较 owner 并提交 Turn/User Item/admission receipt | Lifecycle/Thread partition | 同 Thread 5 seed×200，恰好 1 success/1 conflict | 关闭新入口，禁止第二 Turn |
| A3 | 同一 Thread commit 提交 terminal+owner release；定义 ack 丢失重试 | `turn-run.ts`、Thread partition | start/terminal、kill、重复 requestId | 不确定窗口返回 `recovery_required`，从持久事实 reconcile |
| A4 | App Server/Electron/CLI 只做明确错误投影 | handlers/client/UI | 不同 Thread 并行；旧客户端不误判成功 | UI 提示退化，不改变服务端语义 |

`clientRequestId` 至少冻结：格式/长度、scope=`threadId+clientRequestId`、请求 payload digest、保留期和成功 receipt。同 ID+同 digest 返回原结果；同 ID+不同 digest 返回 `idempotency_conflict`，且不能覆盖旧 receipt。

以上语义在机器可读 `ADR-W1-TURN-001` 写明 revision/digest/owner/reviewer/status 并进入 Accepted 前仍是推荐，所有依赖变体保持 `BlockedByDecision`。

#### 19.2.2 W1-B：Job 分区持久化

近期推荐 **不可变 Job generation Snapshot + 原子 HEAD Manifest**，不直接重写为 Event Sourcing：

```text
runtime-v2/
  ACTIVE.json
  global/
    profiles/
    configs/
    indexes/
  threads/<shard>/<threadKey>/
    identity.json
    HEAD.json
    state/<generation>.json
    admission/<clientRequestId>.receipt.json
  jobs/<shard>/<jobKey>/
    identity.json
    HEAD.json
    commits/<generation>.manifest.json
    state/<generation>.json
    journal/<generation>.jsonl
    lease/state.json
    lease/claims/
  migrations/<migrationId>/...
```

关键约束：

1. `threadKey/jobKey` 分别由 canonical ID 的 SHA-256 派生，禁止直接把用户 ID 当路径；
2. payload 与 manifest 先写为不可变文件，最后原子替换 `HEAD`；`HEAD` 是 Job commit 线性化点；
3. generation 是 `(layoutEpoch, jobGeneration)`，不得与 Lease fencing token 或 Event generation 混用；
4. 普通 Job commit 不写全局 ACTIVE/central manifest；否则重新制造全局锁；
5. `turn/start` 在 Job 创建前发生，因此 Thread admission 必须使用独立 Thread partition；继续写旧全局 Snapshot 就不能证明跨 Thread 真并行；
6. **Lease Store 也必须按 Job 分区**。只拆 Snapshot、不拆 Lease 不能证明跨 Job 并行；
7. W1 journal 只作审计和恢复诊断，不宣称 Event Journal 已成为权威；
8. Completion Proof/Final Receipt 在 W1 必须保持 absent/unimplemented，不用预留目录冒充实现；
9. v7 迁移执行属于 W2。W1 只完成纯只读 Reader、dry-run 规划和兼容 ADR。

per-Job fenced commit 使用固定临界区：

```text
acquire per-Job lease transaction lock
→ verify layoutEpoch/resource/owner/token/version/expiry
→ acquire per-Job HEAD lock（禁止反向取锁）
→ compare parentGeneration
→ write and verify immutable payload + manifest
→ immediately before HEAD swap re-check the same Lease/token/expiry and clock
→ atomic HEAD CAS
→ release HEAD lock
→ release Lease transaction lock
```

Commit 超过 Lease deadline 必须失败；不能因为进入 callback 时 token 有效，就允许过期 owner 替换 HEAD。

W1-B 小切片：

| Slice | 目标 | 输出 | 状态上限 |
|---|---|---|---|
| B1 | 安全 Job path、不可变 generation、HEAD CAS、v7 pure reader/dry-run | 分区合同、Store 组件、攻击 Fixture | E2 component candidate |
| B2 | per-Job Lease/Fencing 与固定锁顺序 | 同 Job 单 Owner、跨 Job 不共用全局 Lease 锁 | E2 integration candidate |
| B3 | Migration plan/marker/backup 合同 | 只做 global/thread/job 目标域与 v7+Lease source 的 dry-run 规划，不切权威 | NotVerified / ADR candidate |
| B4 | 经 Reviewer 后接一个生产 mutation 的 partition path | 真实 Authority/Event 垂直切片 | E2 production candidate |

#### 19.2.3 W1-C：一个真实生产 mutation 垂直切片

只选择一个 Job scoped mutation，贯穿：

```text
RPC/Engine command
→ Authority Registry owner
→ Correlation/Event Envelope
→ 当前 Lease/Fencing 校验
→ per-Job State/HEAD commit
→ 只读 Projection
→ Raw Evidence
```

完成条件不是“新类能保存”，而是测试走 App Server 生产组装入口；重复、旧 generation、旧 fencing token 和错误 Job correlation 全部 fail-closed。切片没有通过前，不批量迁移 Store。

#### 19.2.4 W1-D：退出门禁

- 同 Thread 零双活；
- 不同 Thread/Job 可独立并行提交；
- 同 Job 双 App Server 只有一个 owner；
- 失败 admission 或 Job commit 不向其他 Thread/Job 发送 Abort 或写入事实；现有 cancel/late-result 只作 legacy regression，完整 CancelSpec 与迟到栅栏属于 W2；
- Job A 暂停、冲突或损坏时 Job B 可继续；
- v7 pure reader 不改源字节；
- 旧 Snapshot CAS 保留为 negative control；
- 每轮清理 PID、端口、锁和临时目录；
- 任一安全失败立即停止，不用重跑覆盖。
