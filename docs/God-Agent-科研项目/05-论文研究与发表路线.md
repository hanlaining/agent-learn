# God-Agent 论文研究与发表路线

> 文档编号：D05
> 状态：Proposed / Living Document
> 版本：v1.0.0
> 当前事实基线：`main@928fe38afa6d038e7fafbd6ff1c54c3c35d58793`
> 面向读者：第一次做计算机论文的学生
> 原则：先形成可证伪问题和可复现实验，再选择刊会；不买结果、不造引用、不代写

## 1. 建议论文方向

暂定题目：**面向长程多智能体软件任务的崩溃一致性与副作用安全恢复机制**。

英文工作标题可暂写为：*Crash-Consistent and Side-Effect-Safe Recovery for Long-Running Multi-Agent Software Tasks*。

题目在相关工作检索和导师评审前只是工作标题。论文研究对象是 Runtime 协议，而不是“做了一个像 Codex 的产品”；God-Agent 是实现与实验平台。

## 2. 研究问题与可证伪假设

| RQ | 研究问题 | 预注册假设 | 推翻/证据不足条件 |
|---|---|---|---|
| RQ1 | WAL + 稳定 Invocation ID 能否降低崩溃后的重复调用？ | `H1`：在固定故障窗口下，full 相比 no-WAL 显著降低重复 Model/Tool 次数 | 差异不显著、结果依赖特定 fixture、未知结果仅被隐藏 |
| RQ2 | Lease + Fencing 能否阻止双实例和旧 Owner 提交？ | `H2`：在双实例竞争与接管后迟到提交中，full 的非法提交接受率为 0 | 任一 commit boundary 接受旧 token 或测试未走生产路径 |
| RQ3 | Return Receipt 能否减少父子协作丢失、重复消费和停滞？ | `H3`：full 相比 no-receipt 提高最终收敛率并降低重复 continuation | 收敛率无改善、开销过大或仅在固定拓扑成立 |
| RQ4 | 可靠性机制带来的成本是多少？ | `H4`：在预注册安全负载范围内，full 的延迟/吞吐/存储开销处于导师确认阈值 | 超阈值、恢复积压不收敛、2 小时内资源持续增长 |

阈值必须在正式实验前根据 pilot 和应用场景确定，不能在看到结果后修改为“刚好通过”。如果假设不成立，论文仍应如实报告负结果。

## 3. 预期贡献（尚未完成）

以下只能写成“拟贡献”，完成需要 D03/D04 证据：

1. 一套面向 Agent Runtime 的边界化威胁模型：区分本地状态提交、模型请求、工具副作用、Return 消费和旧 Owner 迟到写入。
2. 一个组合协议：Model/Tool WAL、Job Lease/Fencing、Return Receipt 和 `outcome_unknown` 人工处置。
3. 一套生产组装的真实 Process Chaos 方法：对八个关键窗口做 kill/restart，而不是只抛模拟异常。
4. 一个包含 full、消融、容量和恢复开销的可复现实验包。

“首次”“首个”“领先”之类表述只有在系统性相关工作检索和导师核实后才能使用。

## 4. 相关工作检索框架

### 4.1 必查类别

- 分布式系统：Lease、Fencing Token、Leader failover、Split-brain。
- 事务与消息：WAL、Outbox/Inbox、幂等消费者、至少一次/至多一次语义。
- Workflow/Actor Runtime：持久执行、Saga、Checkpoint、Deterministic replay。
- LLM/Agent：Tool use、multi-agent orchestration、long-horizon agents、memory/recovery。
- 软件工程 Agent 评测：任务 fixture、可复现 benchmark、失败分类。
- Chaos Engineering：进程故障注入、线性化点、恢复正确性。
- Human-in-the-loop：不确定结果处置、审计和并发决策。

### 4.2 检索与筛选流程

1. 用 Google Scholar、DBLP、ACM Digital Library、IEEE Xplore 和 arXiv 组合关键词检索。
2. 先读近 5 年综述/高引用论文，再向前后引用追踪；经典分布式协议不受 5 年限制。
3. 表格记录题名、作者、年份、出处、DOI/正式 URL、研究问题、系统假设、故障模型、实验和局限。
4. DOI、作者、会议/期刊和页码至少用两个可信来源核对。
5. 将“直接对比系统”“理论依据”“邻近工作”分列，避免把背景论文写成基线。

当前文档不填具体引用，是为了避免在未联网核实前生成不存在或信息错误的文献。正式写作使用 Zotero/BibTeX，引用条目必须可点击回到出版方或 DOI。

## 5. 实验对象与控制变量

### 5.1 实验版本

- `full`：WAL + Lease/Fencing + Return Receipt + recovery + human resolution。
- `no-model-wal`：只关闭模型 WAL，其他相同。
- `no-tool-wal`：只关闭工具 WAL，其他相同。
- `no-lease`：关闭 Job ownership/fencing，保留其余机制。
- `no-receipt`：Return 不使用 claim/consume Receipt。
- `no-recovery`：崩溃后只报告失败，不自动基于事实恢复。
- `no-human-resolution`：未知结果不能通过带版本处置恢复。

消融开关仅限实验注入，并保证所有组走相同 App Server 公共入口、业务 fixture 和持久化层。不得为 baseline 写一个更弱或不同路径的演示程序。

### 5.2 Fixture 分层

| 层 | 内容 | 目的 |
|---|---|---|
| F1 | 单 Parent、2 Child、无外部副作用 | 验证状态协议最小闭环 |
| F2 | DAG、并行 Child、Review 和一次返工 | 验证 Return/依赖/父 continuation |
| F3 | 确定性 Model Stub + 幂等/非幂等 Tool | 分离远端不确定性与 Runtime 缺陷 |
| F4 | Role Pack 专家团、多阶段 fan-out/fan-in | 验证可配置拓扑与恢复 |
| F5 | 小预算真实 Provider 样本 | 观察真实网络/服务行为，不做大规模结论 |

所有实验组固定 fixture 版本、seed 集合、并发、预算、故障窗口、Lease TTL、机器和超时。若修改 fixture，创建新版本并重新运行所有比较组。

## 6. 实验设计

### EXP-RQ1-001：WAL 与重复副作用

- 在 Model/Tool 的提交前、结果返回后未持久化等窗口真实 kill Owner。
- 比较 full、no-model-wal、no-tool-wal。
- 主要指标：重复请求/副作用率、`outcome_unknown` 率、正确完成率。
- 次要指标：恢复时间、人工处置数、WAL 写放大。

### EXP-RQ2-001：Lease/Fencing 与双实例

- 两个 App Server 共享状态目录，同时 start/recover；接管后让旧 Owner 在 Return、Stage、Model、Tool、Cancel boundary 迟到提交。
- 比较 full 与 no-lease。
- 主要指标：双 Owner 率、旧 token 接受率、状态回退/覆盖次数。
- 每个边界至少 1000 次确定性竞争；并报告置信上界，不能把“观察为 0”写成绝对不可能。

### EXP-RQ3-001：Return Receipt 与任务收敛

- 使用 F1/F2/F4，注入 claim 后和父 continuation 后崩溃。
- 比较 full 与 no-receipt。
- 主要指标：最终收敛率、丢 Return、重复 consume、重复父 continuation、等待超时。

### EXP-RQ4-001：开销与容量

- 无故障 steady、spike、30 分钟、2 小时 soak、恢复后 drain。
- 比较 full 和对应消融，但不以关闭安全机制获得的更高吞吐作为产品目标。
- 指标：端到端/提交 P50/P95/P99、吞吐、CPU、RSS、Event Loop lag、状态体积、RTO。

## 7. 指标定义

| 指标 | 定义 | 分母/单位 |
|---|---|---|
| Duplicate Model Rate | 同 Invocation attempt 的额外不可重试 POST 数 | 每 1000 Invocation |
| Duplicate Tool Effect Rate | 同 Tool Invocation 的额外外部副作用数 | 每 1000 Invocation |
| Stale Commit Acceptance | 旧 fencing token 被存储接受次数 | 每 1000 迟到提交 |
| Return Loss/Duplicate | 应消费但未消费 / 多于一次消费 | 每 1000 Return |
| Completion Convergence | 预算内达到唯一合法终态的 Job | 百分比 |
| RTO | kill 至 Job 可安全继续或明确阻断 | 毫秒 |
| Recovery Drain | 重启至积压归零 | 秒 |
| Runtime Overhead | full 相对对照的延迟、吞吐、CPU、存储变化 | 百分比 |

模型质量、任务正确率和 Runtime 可靠性必须分开。若最终答案错误但协议正确收敛，不得计为模型任务成功；反之答案看似正确但发生重复副作用，也不得计为 Runtime 成功。

## 8. 重复、统计与报告

1. Pilot 只用于调试 Harness 和估计方差，不进入正式结论。
2. 正式实验预注册 seed、重复次数、主要指标、排除规则和停止条件。
3. 确定性竞争/故障率指标建议每条件至少 1000 次；性能条件至少 3–10 个独立 run，最终样本量由 pilot 方差和功效分析决定。
4. 二项结果报告比例与 95% 置信区间；“0 次失败”同时报告基于样本量的上界。
5. 延迟优先报告中位数、P95/P99、bootstrap 95% CI 和完整分布，不只报告均值。
6. 配对 fixture/seed 时使用配对检验；正态性不能假定时使用非参数方法，并报告效应量。
7. 多组比较做适当校正；同时保留原始 p 值、效应量与置信区间。
8. 性能实验报告机器噪声、预热、GC、后台进程和时间顺序；必要时随机化组别顺序。

统计方法在正式分析前请导师或具有统计经验者复核。显著性不等于工程重要性，必须同时报告预注册的实际意义阈值。

## 9. 复现包

正式复现包至少包含：

- 冻结 commit、版本 tag 和未修改依赖锁文件。
- 威胁模型、RQ、预注册方案和排除规则。
- 匿名化 fixture、seed、消融配置和故障注入点说明。
- 一键运行入口，但真实 Provider 默认关闭。
- 每次运行的 JSONL、Schema、日志、机器配置和 SHA-256 清单。
- 从 JSONL 生成 CSV、统计表和图的脚本。
- 失败最小复现与所有负结果。
- 安装/迁移说明、许可证、第三方归属、数据字典。
- 脱敏报告，以及无法公开材料的原因和替代获取流程。

复现脚本必须能从空白输出目录重建正文表图；手工编辑的 Excel/图片不能作为唯一来源。

## 10. 有效性威胁

### 10.1 内部有效性

- Harness 是否真的终止进程，而不是捕获异常。
- baseline 与消融是否意外走了不同代码路径。
- Fake Provider/Tool 是否过度确定，掩盖真实网络不确定性。
- 故障点是否改变时序，形成观察者效应。
- 单机文件锁与跨机器/网络存储语义不同。

### 10.2 构念有效性

- “任务完成”不等于答案正确，也不等于无重复副作用。
- Task 数不等于 Agent 数、Run 数或并发。
- 测试类名、日志自报和 UI 状态不等于生产路径实际执行。

### 10.3 外部有效性

- 单一 OS、机器、Node 版本、模型或 Tool 不能代表所有部署。
- 软件交付专家团不能代表医疗、金融等领域专家团。
- 本地 Runtime 的结论不能直接外推到云端分布式集群。
- 小预算 Provider 样本不能代表高并发服务质量。

### 10.4 结论有效性

- 多次测量可能不是独立样本。
- 低失败率需要足够样本才能给出有意义上界。
- 只展示成功 run、事后删异常值或更改阈值会夸大效果。

## 11. 伦理、安全与隐私

- 实验不上传未经授权代码、个人聊天、学校材料或敏感路径。
- API Key、Cookie、Token 不进入 Git、快照、日志或论文附件。
- 真实 Provider 设置费用和 Token 硬上限，记录但脱敏请求标识。
- Tool 故障实验只在隔离临时目录和无害命令上执行。
- 论文如使用用户数据、人工参与者或第三方评测，先咨询导师和学校伦理/数据要求。
- AI 可以辅助语言润色和代码检查，但作者必须核验事实、引用、实验和文字，并按目标刊会政策披露。

## 12. 论文结构建议

1. 摘要：问题、方法、实验、主要数字、限制；数字最后填写。
2. 引言：真实失败场景、研究空白、RQ 和贡献。
3. 背景与相关工作：分布式协议、持久 Workflow、Agent Runtime。
4. 威胁模型与系统模型：崩溃、Owner、Invocation、副作用和非目标。
5. 方法：WAL、Lease/Fencing、Return Receipt、人工处置及不变量。
6. 实现：God-Agent 的生产组装、故障注入和边界。
7. 实验设计：fixture、基线、消融、指标、统计和复现。
8. 结果：按 RQ 报告，成功和负结果同列。
9. 讨论：成本、适用条件、外部 Provider 的不可控边界。
10. 有效性威胁、伦理与限制。
11. 结论与未来工作。

写作顺序建议为：威胁模型 → 方法 → 实验方案 → Harness → 结果 → 相关工作 → 引言/摘要，避免先写宏大结论再找数据。

## 14. 正式投稿门槛

投稿前逐项打勾：

- [ ] Dynamic ownership 和所有 commit boundary 达到 E3。
- [ ] Process GATE-40/100 使用真实 App Server 子进程并可重复。
- [ ] full/消融使用同一生产入口、fixture 和预算。
- [ ] RQ、假设、主要指标、样本与排除规则已预注册。
- [ ] 正式重复次数、置信区间、效应量和负结果完整。
- [ ] 至少有一个合理外部系统基线，或充分解释为何只能做机制消融。
- [ ] 所有正文数字均可由原始 JSONL 自动重建。
- [ ] 相关工作条目逐项核验，无虚构引用。
- [ ] 外部复核者能在干净环境复现主要结果。
- [ ] 隐私、安全、许可证和 AI 使用披露符合目标出处要求。
- [ ] 导师确认研究问题、新颖性、作者顺序、通讯作者和目标刊会。

任一核心项缺失时，只发布技术报告或继续实验，不把“写完初稿”当作“可投稿”。

## 15. 作者、导师与学术规范

- 尽早寻找研究方向契合的校内导师，带着问题定义、负结果和可运行证据沟通，而不是只说“想发论文”。
- 作者资格按实质贡献确定：研究设计、实现、实验、分析和写作；提供设备或简单建议不自动构成作者。
- 在投入正式实验前书面确认作者顺序、数据归属、开源边界和投稿决策机制，后续贡献变化可以透明调整。
- 不一稿多投，不拆分同一实验制造多篇“灌水”，不伪造、篡改、选择性删除数据。
- 不购买署名、版面或引用，不找代写/代投；语言润色服务不能改变作者对内容负责。

## 16. 费用与掠夺性期刊检查

正规会议可能有注册、差旅费用，开放获取期刊可能有 APC，部分期刊无版面费；金额随出处和年份变化，必须以官网当期说明为准。**收费本身不等于不正规，承诺交钱快速录用则是强烈风险信号。**

投稿前检查：

- 出版方、会议主办方、程序委员会/编委身份能否从独立页面核实。
- 是否被本方向公认数据库收录，以及学校/导师是否认可；只看网站自称无效。
- 是否有清楚的同行评审、撤稿、伦理、版权、APC 和退款政策。
- 邮件是否以“保证录用、几天审完、购买引用/奖项”为卖点。
- 期刊名是否仿冒知名刊，域名和投稿系统是否属于正式出版方。
- 已发表论文的质量、审稿周期和作者反馈是否合理。
- 任何付款都在录用后按正式账单和学校流程办理，不向私人账户转账。

对可疑邀请先交导师和图书馆核验。拒绝“包发表”“代写”“内部渠道”；这些会让科研经历变成学术风险。

## 18. 当前裁决

当前适合做：建立研究问题、修复 P0、保存负结果、开发真进程实验、形成技术报告。

当前不适合宣称：已有论文创新结论、达到正式投稿、真实 Provider exactly-once、生产级容量或完整 Codex 能力。

下一次状态升级条件是 M1 和 GATE-40 通过并归档原始证据；在此之前，论文状态保持 `Proposed`。
