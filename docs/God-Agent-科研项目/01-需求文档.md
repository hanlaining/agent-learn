> 文档编号：D01
> 状态：Accepted
> 版本：v1.0.0
> 事实基线：`main@928fe38afa6d038e7fafbd6ff1c54c3c35d58793`
> 产品阶段：可靠研究原型 → 受控 Beta 底座

## 1. 背景与问题

长程 AI 软件任务通常同时涉及模型调用、工具副作用、多个角色协作、进程崩溃和人工反馈。普通聊天式 Agent 容易出现以下问题：

- 模型或工具已经执行，但结果尚未持久化，重启后产生重复调用。
- 父子 Agent Return 丢失、重复消费或父级不再继续。
- 两个应用实例同时恢复同一 Job，旧 Owner 迟到提交覆盖新状态。
- 固定团队能 Demo，但无法扩展为不同领域的专家团。
- 测试只证明模拟器，不证明生产组装。
- 项目过程缺少持续证据，难以转化为可信科研经历。

God-Agent 要解决的是“Agent Runtime 如何安全、可恢复、可审计地执行长程任务”，而不是只生成聊天回复。

## 2. 产品目标

### 2.1 核心目标

1. 提供 Codex 式单 Agent / 多 Chat 的本地执行体验。
2. 提供独立的动态父子 Agent 执行链。
3. 提供可配置的角色专家团 Workflow 执行链。
4. 通过 WAL、Lease/Fencing、Return Receipt 和人工处置降低重复调用与未知副作用风险。
5. 将代码、测试、故障实验和负结果沉淀为可复现科研证据。

### 2.2 非目标

- 不复制或声称获得 Codex 专有源码。
- 不承诺任何外部 Provider 的 exactly-once。
- 不在默认测试中读取 API Key、访问真实 Provider 或产生费用。
- 不把固定软件团队 Demo 直接包装成通用专家团。
- 不在没有真实数据时填造论文表格、成功率或性能结论。
- 当前阶段不追求多人云端协作、企业租户和大规模分布式集群。

## 3. 用户与使用场景

| 用户 | 主要任务 | 成功标准 |
|---|---|---|
| 个人开发者 | 在多个 Chat 中并行分析、修改、测试代码 | Chat 隔离、可取消、历史可恢复 |
| 项目负责人 | 让父 Agent 拆分子任务并验收 | 子任务可追踪、Return 不丢不重、失败可继续 |
| 专家团使用者 | 配置产品/工程/测试或其他领域角色 | 角色、阶段、工具和 Skill 可版本化配置 |
| 研究者/学生 | 研究崩溃恢复和副作用安全 | 实验固定、证据可复现、结论不过度 |
| 复试评审老师 | 快速理解贡献并检查真实性 | 演示可重复、源码与数据能相互印证 |

## 4. 系统边界

```text
Electron / CLI
  -> App Server 与协议边界
  -> ExecutionEngineRouter
     -> DynamicAgentExecutionEngine
     -> TeamWorkflowExecutionEngine
  -> 共享 Runtime Kernel
     -> Lifecycle / Context / Store / WAL / Lease
     -> Tool / Skill / MCP / Permission / Sandbox
     -> Metrics / Evidence / Research Reports
```

两条 Engine 可以共享基础设施，但不得共享未命名的活动状态；所有状态必须归属于明确的 Thread、Turn、Job、Task、Run 或 Invocation。

## 6. 非功能需求

### 6.1 可靠性

- `NFR-REL-001`：所有状态机转换必须显式拒绝非法前驱状态。
- `NFR-REL-002`：P0 测试失败必须阻止合并，不能标记 flaky 后跳过。
- `NFR-REL-003`：启动恢复默认不触发付费模型或未知副作用。
- `NFR-REL-004`：恢复循环、重试、Lease 获取和续租必须有界。
- `NFR-REL-005`：终态操作幂等，重复 cancel/resume/recover 不改变事实。

### 6.2 安全与隐私

- `NFR-SEC-001`：API Key、Authorization、Cookie、Token 和环境变量不得进入快照、日志、报告或 Git。
- `NFR-SEC-002`：用户原文、代码、路径和 Tool 结果属于敏感业务数据；本地状态不得默认公开。
- `NFR-SEC-003`：写文件、执行命令、高副作用 Tool 必须由权限与 Scope 同时授权。
- `NFR-SEC-004`：Renderer 不得直接获得 Node、文件系统或任意 IPC 能力。
- `NFR-SEC-005`：真实 Provider 实验必须有显式开关、模型白名单、请求数、Token、费用和超时上限。

### 6.3 性能与容量

- `NFR-PERF-001`：容量报告必须区分 Task、Run、Agent、并发和 Provider 延迟。
- `NFR-PERF-002`：测试至少包含 spike、steady、short-soak 和恢复后 drain。
- `NFR-PERF-003`：任何安全容量数字必须绑定机器、commit、配置、时长和 Provider 类型。
- `NFR-PERF-004`：P95、Event Loop、RSS、吞吐衰减和错误率任一超阈值即判退化。

### 6.4 可用性与可维护性

- `NFR-UX-001`：反馈/等待使用橙色语义，真实失败使用红色语义。
- `NFR-UX-002`：用户可以看到当前 Job、角色、阶段、下一步和阻塞原因。
- `NFR-MAINT-001`：核心契约必须有版本号和向后兼容测试。
- `NFR-MAINT-002`：README、四主文档和实现状态必须在同一 PR 更新。

### 6.5 科研可复现性

- `NFR-REP-001`：实验不允许只提交汇总；必须保留原始数据哈希和生成命令。
- `NFR-REP-002`：失败、负结果和不支持假设必须记录，不能只保留成功运行。
- `NFR-REP-003`：实验组与消融组使用同一 fixture、seed、预算和环境。
- `NFR-REP-004`：论文数字必须能从冻结 commit 一键重建。

## 7. 核心不变量

1. 一个 execution kind 在任一时刻只由一个 Engine 路由。
2. 一个 Job 在任一时刻只允许一个有效 Fencing Token 提交状态。
3. 过期/被接管 Owner 的任何迟到提交不得生效。
4. 一个 Model Invocation 的一次 attempt 最多发出一次不可重试 POST；未知结果不能伪装失败后自动重发。
5. 一个 Tool 副作用未知时禁止自动重放。
6. 一个 Return 只能产生一个消费 Receipt。
7. 父 Agent 只有在持久事实成立后才能最终交付。
8. Team Workflow Return 不得被 Dynamic continuation 消费，反之亦然。
9. 终态 Job 的完成证据不能因恢复而倒退。
10. 测试报告不能通过声明类名冒充实际调用生产路径。

## 8. 当前风险

| ID | 风险 | 影响 | 当前措施 | 后续动作 |
|---|---|---|---|---|
| RISK-001 | Dynamic Engine 未注入完整 ownership | 双实例可能无 fencing 改状态 | AgentLoop/部分 commit 已有 Lease | P0 修复全部 Engine 操作边界 |
| RISK-002 | Runtime-E2E 未经过完整生产组装 | 测试绿但集成缺口未暴露 | 有组件与实现检查 | 新增 App Server 双实例 Process Chaos |
| RISK-003 | 单 JSON 全量快照 | 长任务性能与损坏面扩大 | 原子 rename、版本迁移 | 分区/增量/备份 |
| RISK-004 | 固定专家角色硬编码 | 无法扩展跨领域专家团 | V2 Workflow 稳定 | Role Pack/Team Template |
| RISK-005 | 真实 Provider 能力未知 | 无法声明远端幂等 | outcome_unknown、离线 smoke | 小预算受控实测 |
| RISK-006 | 文档与 README 落后 | 复试陈述与源码矛盾 | 新建本套文档 | CI 检查文档基线 |

## 9. 需求变更规则

新增或修改需求必须包含：动机、范围、非目标、状态不变量、测试 ID、迁移方案、风险和证据等级。影响 P0 不变量的变更必须先更新本文件，禁止先改代码后补需求。
