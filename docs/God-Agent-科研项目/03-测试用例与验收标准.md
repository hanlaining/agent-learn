# God-Agent 测试用例与验收标准

> 文档编号：D03
> 状态：Accepted
> 版本：v1.0.0
> 事实基线：`main@928fe38afa6d038e7fafbd6ff1c54c3c35d58793`
> 核心原则：测试通过不等于生产闭环；报告必须说明实际走过的入口、进程、文件和 Provider

## 1. 测试目标

本文件回答“用什么证据才能证明需求完成”。测试不以用例数量为目标，而是验证 D01 的十条核心不变量在正常、并发、崩溃、恢复、取消、越权和资源耗尽条件下仍成立。

以下三种结论必须严格区分：

- **组件正确**：类或模块在隔离条件下通过，证据最高为 E2。
- **生产组装正确**：通过 App Server 公共入口、真实持久化和真实 Coordinator 运行，证据可到 E3。
- **真实外部效果正确**：涉及真实 Provider、系统命令或外部服务时，必须另有受控实验；本地 Fake 不能替代。

## 2. 测试层级与执行环境

| 层级 | 目的 | 必须使用 | 禁止替代 | 证据上限 |
|---|---|---|---|---|
| L1 单元 | 状态转换、校验、序列化 | 确定性 fixture/clock | 用端到端掩盖边界错误 | E2 |
| L2 组件 | Engine、WAL、Lease、Scheduler 契约 | 真实组件组合、隔离目录 | 只断言 mock 被调用 | E2 |
| L3 生产集成 | 验证 `main` 的真实依赖接线 | 公共 RPC、生产 Store/WAL/Coordinator | 测试直接 new 内部类冒充生产组装 | E3 |
| L4 双实例 | 验证所有权和 fencing | 两个 App Server、共享隔离状态目录 | 单实例内模拟两个 owner | E3 |
| L5 Process Chaos | 验证真实崩溃恢复 | 子进程、真实 kill/restart、真实 JSON reload | `SimulatedProcessExit` | E3 |
| L6 Electron E2E | 验证用户可见主链 | 打包/开发壳、真实 IPC/窗口 | 纯 DOM 单测 | E3 |
| L7 容量与稳定性 | 找到瓶颈和安全范围 | 冻结机器、commit、配置、时长 | 把 Task 数写成 Agent 并发 | E3 |
| L8 Provider 实验 | 验证外部行为和费用 | 显式开关、白名单、小预算 | 默认 CI 读取 Key | E3/E4 |

每次 L3 以上运行必须记录：OS、CPU、内存、Node/Electron 版本、commit、工作树是否干净、配置、seed、开始/结束时间、原始报告路径与 SHA-256。

## 3. 通用判定规则

1. P0 用例不得跳过、重试到绿或标记 flaky。
2. 同一用例重复运行时，任何一次核心不变量失败都判失败。
3. 超时必须区分“系统按设计拒绝”“资源预算耗尽”“测试 Harness 失联”。
4. 未知副作用只能进入 `outcome_unknown`，不能按普通失败自动重放。
5. baseline 与消融组必须走同一生产入口，只能通过受控配置关闭被研究机制。
6. 日志中的类名、布尔标记和测试自报不能证明实际路径；须保留 RPC 轨迹、进程 PID、状态文件变化或调用审计。
7. 真实 Provider 测试失败不得用扩大预算反复碰运气；先形成最小复现并停止计费。

## 4. P0：Dynamic Engine Lease

| ID | 对应需求 | 场景与操作 | 必须断言 | 层级 |
|---|---|---|---|---|
| TC-DYNLEASE-001 | FR-DYN-005 | `start` 获取 Job Lease 后创建/推进父任务 | 每次持久提交携带同一活动 fencing token | L2/L3 |
| TC-DYNLEASE-002 | FR-DYN-005 | `resume`、`recover` 分别进入 ownership | 缺 Lease 不提交；被占用只等待、不污染状态 | L2/L3 |
| TC-DYNLEASE-003 | FR-DYN-005 | `provideFeedback` 与恢复并发 | 只有有效 Owner 接受反馈并生成一个新 attempt | L4 |

| TC-DYNLEASE-005 | FR-LEASE-003 | 同 Job 的 Engine→AgentLoop 嵌套调用 | 复用 Lease context，不二次 acquire、不死锁 | L2 |
| TC-DYNLEASE-006 | FR-LEASE-003 | 持有 Job A 时嵌套执行 Job B | 立即拒绝并给出可诊断错误，A 不受污染 | L2 |
| TC-DYNLEASE-007 | FR-DYN-003 | Return claim→父 continuation→consume | 全链 fenced；只产生一个 Receipt 和一次最终交付 | L3/L5 |
| TC-DYNLEASE-008 | FR-LEASE-002 | 旧 Owner 在 Return boundary 迟到提交 | 100% 被拒，未生成重复 continuation | L4 |
| TC-DYNLEASE-009 | FR-LEASE-002 | 旧 Owner 在 Stage boundary 迟到提交 | 100% 被拒，阶段不倒退 | L4 |
| TC-DYNLEASE-010 | FR-LEASE-002 | 旧 Owner 在 Model commit 迟到提交 | 100% 被拒；远端结果按 WAL 事实处置 | L4/L5 |
| TC-DYNLEASE-011 | FR-LEASE-002 | 旧 Owner 在 Tool commit 迟到提交 | 100% 被拒；副作用未知时进入人工处置 | L4/L5 |
| TC-DYNLEASE-012 | FR-LEASE-002 | 旧 Owner 在 Cancel commit 迟到提交 | 100% 被拒，不能覆盖新 Owner 的终态 | L4 |
| TC-DYNLEASE-013 | FR-LEASE-001 | 两实例同时 `start`，1000 轮 | 每轮仅一个合法 Owner，无双推进 | L4 |
| TC-DYNLEASE-014 | FR-LEASE-003 | 两实例同时恢复同一非终态 Job | 一个恢复，另一个可观察等待；App Server 不退出 | L4/L5 |

P0 退出门槛：上述用例全绿；生产组装中 ownership 为必需依赖；`withActiveFencedCommit` 不允许在应受保护路径无 Lease 静默提交。

## 5. Process Chaos 故障矩阵

Harness 必须启动真实 App Server 子进程，共享一个新建的隔离临时状态目录；收到故障点落盘确认后强制结束 Owner 进程，等待 Lease 过期，再由第二进程通过公共 RPC 恢复。

| ID | kill 窗口 | 恢复后的唯一正确结果 |
|---|---|---|
| TC-CHAOS-001 | Model 请求提交前 | 允许安全发起一次请求 |
| TC-CHAOS-002 | Model 响应收到、结果持久化前 | 有远端幂等证据才查询/恢复，否则 `outcome_unknown`，禁止盲重放 |
| TC-CHAOS-003 | Tool 副作用执行前 | 允许安全执行一次 |
| TC-CHAOS-004 | Tool 副作用完成、结果持久化前 | 可查询工具才核验，否则 `outcome_unknown` |
| TC-CHAOS-005 | Return claim 后、父 continuation 前 | 新 Owner 继续一次，Receipt 唯一 |
| TC-CHAOS-006 | 父 continuation 后、Return consume 前 | 不重复父模型/最终交付，只补 consume |
| TC-CHAOS-007 | Workflow stage 计算完成、提交前 | 按 Invocation/Stage 事实恢复，不重复不可重放副作用 |
| TC-CHAOS-008 | fenced commit 完成、Lease release 前 | 新 Owner 看到已提交事实，不重复推进 |

每个窗口至少运行 5 个固定 seed 形成 GATE-40；完成调试后扩展到 GATE-100。每条报告必须包含旧/新 PID、kill 时间、Lease epoch/token、WAL 状态序列、调用次数和最终快照哈希。

## 10. 容量、稳定性与压爆测试

### 10.1 工作负载

| ID | 类型 | 建议初始配置 | 目的 |
|---|---|---|---|
| TC-LOAD-001 | Spike | 1→目标并发瞬时跃升，5 分钟 | 找排队、拒绝和崩溃边界 |
| TC-LOAD-002 | Steady | 目标并发持续 30 分钟 | 测稳定吞吐和延迟 |
| TC-LOAD-003 | Short-soak | 70% 目标并发持续 2 小时 | 找内存、句柄、队列累积 |
| TC-LOAD-004 | Recovery drain | 运行中 kill Owner，重启后清空积压 | 测恢复吞吐和重复副作用 |
| TC-LOAD-005 | Storage pressure | 1k/10k/100k 历史对象 | 测序列化、索引和恢复时间 |
| TC-LOAD-006 | Noisy neighbor | Job A 输出/Tool/MCP 压满，Job B 正常 | 验证预算和隔离 |

逐级阶梯为 1、2、4、8、16……并发；一旦触发停止条件，不继续扩大。每一级预热 2 分钟、测量至少 10 分钟并重复 3 次。若使用 Fake Provider，只能报告 Runtime 容量，不得外推模型服务容量。

### 10.2 指标

- 吞吐：完成 Task/Run/Job 每分钟，分母定义必须固定。
- 延迟：排队、模型、工具、提交、端到端的 P50/P95/P99。
- 正确性：重复 Model/Tool、双 Owner、丢 Return、非法状态转换。
- 恢复：RTO、积压 drain 时间、恢复成功率、未知结果数。
- 资源：RSS、Heap、CPU、Event Loop lag、句柄、状态文件体积。
- 退化：相对上一稳定台阶的吞吐下降和 P95 增幅。

停止条件：双 Owner或重复副作用 > 0；未捕获异常；RSS 连续三个窗口单调增长且 GC 后不回落；错误率 > 1%；P95 超基线 2 倍；恢复积压无法收敛。停止后保存现场，不以“压爆本就会失败”为由忽略正确性错误。

安全承载量定义为：同一机器、commit、配置下，连续三轮均未触发停止条件的最高一级；报告有效期随代码或机器变化而失效。

## 11. 真实 Provider 受控实验

默认测试、CI 和 Process Chaos **禁止**读取或调用真实 Provider。启用时必须同时满足：

1. `REAL_PROVIDER_EXPERIMENT=1` 之类的显式开关。
2. 模型白名单、最大请求数、Token、金额、并发和总时长。
3. 使用专用低额度凭据，凭据只来自进程环境且不落盘。
4. 运行前打印预计上限并由实验者确认；达到任一上限立即停止。
5. 保存脱敏 request ID、HTTP 类别、重试/查询轨迹和实际费用。
6. 不向 Provider 上传未授权源码、个人信息或历史对话。

首轮只验证 10–30 个调用的小样本协议行为，不用于得出性能普遍结论。

## 12. Go / No-Go 门槛

| 里程碑 | Go 条件 | 任一 No-Go 条件 |
|---|---|---|
| P0 Lease 完成 | TC-DYNLEASE 全绿；生产依赖必需；双实例 1000 轮无双 Owner | 任一状态写可无 Lease 静默发生 |
| Process GATE | GATE-40/100 全绿，八窗口都是真 kill/restart | 模拟退出、直接调 Store、路径自报 |
| 专家团底座 | 三模板不改 Coordinator 即可运行并恢复 | 角色/权限/拓扑仍硬编码 |
| Beta 演示 | Electron 主链、恢复、反馈、错误语义全绿 | 演示依赖手改状态或真实 Key |
| 论文实验 | 冻结版本、重复/消融/统计/原始数据/外部复核齐全 | 只有成功截图或单次汇总 |

## 14. 手工演示验收脚本

1. 在全新隔离状态目录启动应用，展示 commit 与 Provider 类型。
2. 新建两个 Chat 并行执行，取消其中一个，证明互不影响。
3. 创建一个父任务并产生至少两个有依赖的子任务，展示 Evidence 和 Return。
4. 让一个子任务进入等待反馈；确认橙色状态，提交反馈后父 Agent 继续。
5. 在指定安全故障点终止 App Server，重启并展示恢复轨迹、Lease Owner 和无重复调用计数。
6. 打开 `outcome_unknown` 示例，演示默认不重放与带版本的人工处置。
7. 导出脱敏证据包，现场从原始 JSONL 重建汇总。
8. 主动说明限制：当前 Provider 类型、未完成项、数据规模和结论边界。

演示成功不能替代自动化门禁；演示失败必须记录进 D04，而不是重启后只展示成功的一次。

## 15. 当前基线裁决

- 已知自动化基线：`npm run check`、19/19 pretest、454/454 主测试、73/73 Electron、7/7 Runtime-E2E 和 Electron build 在审计环境通过，属于 E2 与部分 E3 前置证据。
- 当前 Runtime-E2E 使用真实 JSON/Store/WAL，但 Lease 场景直接使用 Store、进程退出为模拟，不能计为 TC-CHAOS 通过。
- Dynamic Engine 生产 ownership 和全操作 fencing 尚未闭环，因此 TC-DYNLEASE P0 当前不得标记 Verified。
- 本文中的 TC 表是验收合同；除本节明确列出的历史基线外，均不代表已经执行。
