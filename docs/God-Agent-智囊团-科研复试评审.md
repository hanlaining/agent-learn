## 一、最终裁决

God-Agent 已经具备一个有辨识度的复试科研项目：它不是普通聊天壳，也不是简单调用大模型 API，而是围绕“长程 Agent 在崩溃、接管、重复投递和外部副作用结果未知时，如何保持状态可信”构造 Runtime、故障模型和证据链。WAL、Lease/Fencing、Return Receipt、Snapshot CAS 与 `outcome_unknown` 形成了完整且可追问的技术主线。

但如果采用严格科研评委口径，当前最准确的表述仍是：

> **强工程研究原型，复试题材优秀；正式科研闭环未完成，论文创新结论尚未成立，现场放行也尚无彩排证据。**

本评审给出三种不同分母，不能混为一个“总完成度”：

| 评价对象 | 当前分 | 裁决 |
|---|---:|---|
| 作为考研复试科研项目的静态内容 | **89/100** | 有竞争力；技术深度、失败场景、诚实边界和最小展示包明显高于普通 Demo |
| 作为可现场稳定交付的复试展示 | **79/100** | `Conditional Go`；PPT 数字已刷新并通过渲染检查，但 README 口径和真实彩排尚未闭环 |
| 作为可支持论文结论的科研证据闭环 | **69/100** | `No-Go`；与项目官方 95+ 总账的科研评分一致 |

六维加权综合分为 **80.35/100，取整 80/100**。这一综合分同时惩罚了“未完成正式实验”和“未执行彩排”，所以不能拿它替代单独的复试内容分或工程原型分。

### 放行结论

- **用于复试介绍项目：可以准备后使用。** 前提是完成数字统一、三轮计时彩排和一次非作者试讲。
- **声称科研闭环 95+：不允许。** 当前 GATE-40 仍是 local pilot，formal Verified 为 0，预注册未冻结。
- **声称论文创新已证明：不允许。** 缺外部系统同条件基线、正式统计、相关工作结论和独立复现。
- **声称生产级或 exactly-once：不允许。** Provider 仍为 `liveCalls=0`，production 为 `blocked`。

## 三、项目定位评审：93/100

### 已成立的优点（事实与裁决）

1. **问题不是伪命题。** “外部动作已发生但确认未持久化”是分布式系统和 Agent 工具调用中的真实危险窗口，适合在复试中用一个具体反例切入。
2. **定位已主动收窄。** README 将项目定义为“单机、本地文件持久化的系统化工程与科研原型”，并明确不是生产多租户平台和已完成论文。
3. **技术主线统一。** Model/Tool WAL、Lease/Fencing、Return Receipt、Snapshot CAS 和 `outcome_unknown` 都围绕“事实、所有权、提交边界和未知结果”服务，不是随意堆功能。
4. **适合复试追问。** 老师可以从操作系统、数据库、分布式系统、软件工程测试、科研方法和 AI 使用边界多角度追问，项目有足够深度承接。

### 扣分事实

1. **根 README 仍有版本漂移。** 审阅时根 `README.md` 的“当前验证基线”仍显示 `86/86`、主测试 `515/515`、Process Chaos `4/4`，而复试问答、Demo、PPT 和总账已使用 `106/106`、`657 pass + 1 skip`、Process Chaos `12/12`。
2. **数据仍由多份文档分别维护。** 本轮 PPT 已完成刷新，但若没有唯一事实源，下一轮测试抬升后仍可能再次出现 README、PPT 和讲稿错位。
3. **项目名容易造成误解。** “God-Agent”记忆点强，但也可能让老师先入为主地认为目标过大；必须始终附带“长程任务可靠性的本地 Agent Runtime 研究原型”副标题。

### 到 95 的补足条件（建议）

- 建立一个唯一的“对外事实快照”，README、PPT、Demo、问答、讲稿只引用它，不再各自手录数字。
- 一句话定位固定为：

  > God-Agent 是一个研究长程 Agent 在崩溃、接管和外部副作用不确定时如何安全恢复的本地 Runtime 原型；它不声称生产级或端到端 exactly-once。

- 所有材料增加统一的“证据等级与不能外推”页脚或讲稿句，保证评委听到的不是“数字很大”，而是“边界清楚”。

## 四、创新性评审：76/100

### 已成立的贡献

WAL、Lease、Fencing、Outbox/Receipt、CAS 都是经典机制，项目没有把它们冒充原创发明，这是正确的研究诚信边界。当前可以主张的项目贡献有三类：

1. **Agent 特定的边界映射。** 把 Model、Tool、Owner、Return、Proof 拆成不同提交边界，而不是把一次 Agent Run 视为一个不可分割黑盒。
2. **未知结果显式化。** 对不可查询、不可安全重放的外部副作用，选择 `outcome_unknown` 和人工裁决，而不是用自动重试伪造成功。
3. **完成语义拆分。** 区分 protocol handling、business completion、completion decision validity、false completion、unknown 和 evidence coverage，避免把单一成功率掩盖不同失败。

这些足以构成“有研究价值的设计贡献”和“可检验假设”，也足以成为复试亮点。

### 为什么还不是 95

- 相关工作目前主要是检索框架，尚无经过人工核验的系统性比较矩阵。
- 没有 LangGraph、Temporal 或其他合理外部系统在相同任务、Provider、预算、故障窗口和 Oracle 下的实测。
- 当前消融主要证明项目内 fixture 与接线的方向性，不能证明该组合优于简单持久队列或成熟 Durable Workflow。
- 指标拆分和 Claim 边界很有价值，但“首次”“首个”“显著优于”均没有证据。

### 到 95 的补足条件（建议）

1. 完成至少 20～30 篇一手文献的相关工作矩阵：研究对象、故障模型、提交边界、恢复语义、外部副作用、评测方法和限制逐项对齐。
2. 冻结一个明确的新颖性 Claim：不是“发明 WAL”，而是“Agent Model/Tool/Return/Proof 多边界组合协议及 unknown 决策有效性评测”。
3. 选择一个主要外部基线，优先做公平且可执行的比较；Temporal 可保留为机制讨论，避免同时移植多个庞大系统造成失控。
4. 同时加入一个简单内部基线，例如“稳定 ID + 普通重试”或“持久队列但无 fencing/receipt”，用于回答复杂组合是否真的必要。
5. 由导师或不参与实现的研究者对 Novelty Claim 和相关工作做一次签字式审查。

在外部基线和相关工作完成前，创新性分数建议封顶 **88**；不能靠增加代码量达到 95。

## 五、实验设计评审：82/100

### 已成立的优点

- 已区分 Model Check、Runtime Implementation Check 和 Process Check，避免用协议模拟替代生产接线。
- 已有固定 seed、故障窗口、消融 arm、Schema、Raw、Manifest、失败 repro 和 Claim–Evidence Matrix。
- 已考虑 Wilson 95% CI、零失败上界、率差、率比、配对设计、bootstrap 与多重比较。
- 统计报告固定 `significanceClaimed=false`，没有把统计函数存在写成显著性已经成立。
- 负结果和 flake 有保留政策，方法态度是可信的。

### 关键缺口

1. 预注册仍为 `draft`，没有 frozen digest，窗口列表未冻结。
2. 40 个候选 case 中只有 25 个可运行，15 个 blocked；formal 0。
3. local pilot 只适合调试 Harness，不能进入确认性结论。
4. 正式样本量依据、独立分析单元、排除/重跑/停止规则仍未形成冻结证据。
5. Oracle 独立性仍需证明；如果 Oracle 复用生产实现逻辑，可能出现实现与判定共同出错。
6. 当前真实 Provider 与真实外部副作用样本为 0，实验构念与真实网络条件仍有距离。

### 到 95 的补足条件（建议）

- 先冻结 RQ/H0/H1、主要终点、arm、seed、fault window、样本量、排除/重跑、停止规则、Oracle 和分析代码摘要，再运行正式数据。
- 接通剩余 15 个 blocked case；正式 Manifest 必须满足 `blocked=0`、`formallyVerified=40`、`completeGate40=true`、`independentReview=Reviewed`。
- 根据 pilot 方差和预期最小效应确定正式重复数，不把“40 个 case”误当作天然充分样本量。
- Oracle 与生产实现分离，并用已知错误 fixture 做 Oracle sensitivity test。
- Raw 先只追加保存，表格和图由只读脚本生成；任何排除都同时保留排除前后的分母。

## 六、论证闭环评审：69/100

### 已闭合的链条

当前已经形成：

> 失败场景 → 机制设计 → E2 自动化 → 窄范围真进程 pilot → Raw/Manifest → Claim 限制 → 负结果保留

这是一个扎实的内部工程研究闭环，也是项目最强的资产。

### 尚未闭合的链条

完整科研闭环应为：

> 冻结研究问题与假设 → 冻结实验方案 → 完整生产路径实验 → 正式重复 → 统计估计与效应量 → 内外部基线 → 真实 Provider/副作用 → 独立复现 → Claim 审稿 → 论文结论

当前主要断点是：

- 预注册未冻结；
- formal GATE-40 为 0，15 个 case blocked；
- Provider `liveCalls=0`；
- 没有真实可查询和不可回放外部副作用的受控实验；
- 没有公平外部基线；
- 没有第二环境/第二执行者无指导复现；
- 正式 RQ 结果、论文结果、相关工作和伦理审查仍是 `NotVerified`。

### 到 95 的硬门槛（建议）

以下六项缺一不可：

1. frozen preregistration digest；
2. GATE-40 formal 全部完成，并按样本量依据正式重复；
3. full 与消融的配对 Raw、95% CI、效应量、零失败上界和多重比较处理；
4. 小预算真实 Provider，以及至少一种可查询和一种不可安全重放的真实/等价外部副作用；
5. 一个公平外部系统基线和一个简单内部基线；
6. 第二执行者或第二环境按冻结 Artifact 完成无指导复现，并保留差异处理记录。

在 formal GATE-40、真实外部边界、外部基线和独立复现任一缺失时，科研闭环不应标为 95。

## 七、可复述性评审：84/100

### 已成立的优点

- `docs/God-Agent-考研复试高频追问与回答.md` 已覆盖定位、创新、WAL、Invocation ID、Lease/Fencing、unknown、exactly-once、Return Receipt、统计、外部基线、Provider、生产边界和 AI 辅助。
- 多数回答采用“结论—机制—证据—边界”结构，适合面对追问。
- 对“不是我发明 WAL”“没有 exactly-once”“没有外部基线”“AI 参与无法编造百分比”的回答诚实且成熟。

### 扣分事实

- 高频问答很完整，但术语和数字过密；现场背诵 106/658/24425/26908/111/119/25/15/11/3/93/90/69/47/68 容易出错。
- 尚无三轮计时、随机追问命中率、视频/观察记录和非作者试讲证据。

### 建议的三分钟口语主线

1. **20 秒：问题。** 外部副作用可能已发生，但确认在进程崩溃前没有持久化；盲目重试会造成二次真实效果。
2. **50 秒：机制。** WAL 记事实，Lease/Fencing 决定谁能提交，Return Receipt 保证父子结果可恢复消费，无法确认时停在 `outcome_unknown`。
3. **45 秒：证据。** 先说 E2 主体，再说 25 个 local pilot 和 15 个 blocked；强调 formal 0 与 `complete=false`。
4. **30 秒：创新边界。** 经典机制不是原创，贡献是 Agent 特定边界映射、完成语义拆分与可证伪实验方法。
5. **25 秒：限制与下一步。** 真实 Provider、完整正式矩阵、外部基线和独立复现尚未完成。
6. **10 秒：收口。** “我希望把本机通过升级成可比较、可复核、可复现的研究结论。”

主讲时只记四组数字：`657+1+0`、coverage `90.77/93.28`、GATE `25/0/15/formal 0`、Provider `0`。其余数字放附页，不要口头全部念出。

### 到 95 的补足条件（建议）

- 三轮完整计时彩排均在 `2:45–3:10`，无事实错误。
- 随机抽取至少 5 个问题，必须包含创新、exactly-once、统计、外部基线和 AI 边界；无提示正确率至少 90%。
- 完成一次非作者试讲；对方仅凭冻结材料能说清“一句话定位、一个失败窗口、四个机制、四个限制”。
- 每次问题都形成修改与复验闭环，不能只留“感觉不错”的主观记录。

## 八、展示材料评审：84/100

## 十、最可能的复试追问与建议回答边界

### “这些机制都是经典机制，你的创新是什么？”

建议回答：

> WAL、Lease、Fencing 和 Receipt 不是我发明的。我的项目贡献是把它们映射到 Agent 的 Model、Tool、Owner、Return 和 Proof 多个提交边界，并把业务完成、协议处理、误完成和 unknown 分开度量。我已经形成了可执行假设和部分本机证据，但学术新颖性还需要相关工作、公平基线和正式实验验证。

### “为什么不用 Temporal 或 LangGraph？”

建议回答：

> 如果目标是直接生产落地，我会优先评估成熟系统。自研的目的不是替代它们，而是把 Agent 特有的外部模型调用、不可查询工具副作用和父子 Return 的语义显式化。当前没有同条件外部实测，所以我只能比较研究关注点，不能说更可靠。

### “测试这么多，能证明什么？”

建议回答：

> 658 项主测试证明已定义断言没有静默回归，不是可靠性概率。当前主体仍是 Fake Provider 的 E2；GATE-40 只有 25 个 local pilot passed、15 blocked，formal 0，真实 Provider 调用也为 0。因此我把测试数当工程门禁，不当论文结论。

### “你实现 exactly-once 了吗？”

建议回答：

> 没有。项目能提供稳定本地调用身份、拒绝旧 Owner 提交、可恢复的 Return 消费和 unknown 安全停止；端到端效果是否唯一还依赖外部系统的幂等、查询和事务能力。

### “AI 做了多少？”

建议回答：

> AI 辅助过需求拆分、方案讨论、代码和测试草拟、文档与审计，但我没有可靠的逐行统计，所以不编造百分比。我承担问题定义、方案取舍、源码复核、实际验收、负结果保存、引用和最终责任；不能解释的部分不算作我的掌握。
