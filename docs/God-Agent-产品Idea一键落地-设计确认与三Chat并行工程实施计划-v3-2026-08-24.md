# God-Agent 产品 Idea 一键落地实施计划（v3）

> 任务标题：产品 Idea → 原稿/Mock 确认 → 三 Chat 并行工程落地
> 版本：v3
> 日期：2026-08-24
> 当前状态：已实现并完成本地验收

## 1. 用户真正需要的结果

用户输入一个产品 Idea 后，God 不能直接跳到写前端代码，也不能只返回一大段聊天文字。正确结果是：

1. 先把 Idea 整理成需求方案 Markdown；
2. 再由产品 Agent 设计产品原稿和 Mock 交互；
3. 用户查看并确认设计没有问题；
4. 确认后，工程阶段默认同时启动 3 个 Chat；
5. 三个 Chat 分别完成前端、后端、联调/测试保障；
6. 测试通过后，由 God 统一汇总交付。

## 2. 当前流程缺口

当前已有“产品 → 工程 → 测试 → 负责人”的父子 Agent 雏形，但存在四个缺口：

- 产品角色只描述需求、页面结构和验收条件，没有强制输出原稿和 Mock 交互；
- 需求确认和设计确认只有一个确认点，无法阻止工程过早写前端；
- 工程目前是一个笼统 `engineering_role`，没有细分前端、后端和联调保障；
- 工程默认不是 3 个并行 Chat，界面也无法分别展示各 Chat 的进度、文件和测试证据。

## 3. 目标流程草图

```text
用户输入产品 Idea
  ↓
God 父 Agent 澄清需求
  ↓
生成需求方案.md
  ↓
用户确认需求方案
  ↓
产品 Agent 设计原稿
  ├─ 页面结构
  ├─ 页面布局
  ├─ 用户操作路径
  ├─ 交互状态
  └─ 验收标准
  ↓
生成 Mock 交互预览
  ↓
用户打开预览并反馈
  ├─ 有问题 → 产品 Agent 修改原稿和 Mock
  └─ 没问题 → 用户确认设计
  ↓
God 冻结设计版本与设计稿哈希
  ↓
默认同时创建 3 个工程 Chat
  ├─ Chat 1：前端工程
  ├─ Chat 2：后端/API/数据工程
  └─ Chat 3：联调、测试、构建与运行保障
  ↓
三个 Chat 并行执行
  ↓
各 Chat Return 变更文件、测试证据和风险
  ↓
工程负责人联调验收
  ↓
测试 Agent 对照设计原稿和 Mock 独立验收
  ├─ 不通过 → 只返工对应 Chat
  └─ 通过 → 返回 God
  ↓
God 最终汇总
  ↓
交付代码、构建产物、方案.md、测试报告和使用说明
```

## 4. 三个工程 Chat 的职责

| Chat | 负责内容 | 文件边界 | 输出 |
|---|---|---|---|
| 前端工程 Chat | 页面、组件、交互、状态管理、响应式、前端测试 | 仅前端目录和前端测试文件 | 前端变更清单、截图/预览、测试结果 |
| 后端工程 Chat | API、数据库、业务逻辑、权限、服务端测试 | 仅后端目录和后端测试文件 | 接口契约、数据变更、测试结果 |
| 联调保障 Chat | 接口联调、构建启动、端到端测试、回归记录、运行说明 | 联调配置、测试和构建相关文件 | 联调结果、启动方式、回归报告 |

默认并行数为 `3`，但不是无条件制造 3 份重复工作：

- 没有后端的产品，后端 Chat 转为本地数据/状态工程；
- 没有复杂联调的产品，第三个 Chat 转为测试、构建和交付保障；
- 前端和后端可同时工作；联调 Chat 在接口和页面契约冻结后进入联调子阶段。

## 5. 必须建立的确认闸门

### 闸门一：需求确认

用户确认需求方案 `.md` 后，才允许创建产品设计任务。

### 闸门二：设计确认

产品原稿和 Mock 交互完成后，用户必须看到：

- 页面预览；
- 页面之间如何跳转；
- 点击、输入、提交、错误和空状态如何表现；
- 前端和后端需要哪些接口；
- 设计稿版本和修改记录。

用户确认设计前：

- 不允许创建可写前端 Chat；
- 不允许创建可写后端 Chat；
- 不允许运行工程修改命令。

### 闸门三：工程验收

三个工程 Chat 都必须返回变更文件、测试结果、风险说明和启动方式，工程负责人确认后，测试 Agent 才能做最终验收。

## 6. 需要调整的地方

### 6.1 Skill 层

调整 `skills/clarify-before-execute/SKILL.md`：

- 把“需求确认”和“设计确认”拆成两个独立阶段；
- 要求产品 Agent 生成原稿和 Mock，而不是只写文字方案；
- 明确设计确认前不能创建可写工程 Chat；
- 明确工程阶段默认并行 3 个 Chat；
- 要求每个 Chat Return 文件、测试、风险和启动方式。

### 6.2 Agent 角色层

调整 `src/agents/agent-profile.ts`：

- `product_role`：只做产品原稿、Mock、交互流程和验收标准；
- 新增 `frontend_engineering`：只做前端；
- 新增 `backend_engineering`：只做后端/API/数据；
- 新增 `integration_quality`：只做联调、构建、测试和运行保障；
- 保留 `software_team_lead`：负责拆分、监督、联调和验收，不替工程 Chat 重复写代码。

### 6.3 Workflow 层

调整 `src/execution/workflows/software-product-delivery.ts`：

```text
product_design
  → mock_preview
  → user_design_confirmation
  → frontend_engineering  ┐
  → backend_engineering   ├─ 并行
  → integration_quality   ┘
  → integration_review
  → quality_review
  → lead_acceptance
  → god_delivery
```

### 6.4 Runtime 调度层

调整 Workflow Coordinator / Team Execution Engine：

- 增加 fan-out：一次创建 3 个工程 Chat；
- 增加 fan-in：等待三个 Chat Return 后再进入联调验收；
- 默认 `engineeringChatCount = 3`，允许用户配置；
- 每个 Chat 使用独立任务合同、Attempt、Lease、Return 和文件白名单；
- 一个 Chat 失败时只返工该 Chat，不重复执行其他已通过 Chat；
- 同一文件不能被多个工程 Chat 同时写入。

### 6.5 桌面 UI 层

调整 `src/electron/renderer/App.tsx` 与桌面类型：

- 需求卡片：打开方案、确认需求；
- 设计卡片：打开原稿、预览 Mock、提出修改、确认设计；
- 工程面板：同时显示 3 个 Chat；
- 每个 Chat 显示当前阶段、修改文件、测试结果、风险和 Return；
- 返工按钮只作用于失败的 Chat；
- 未确认设计时，工程 Chat 必须显示“等待设计确认”，不能显示“正在修改前端”。

## 7. 分阶段执行顺序

### Slice A：需求与设计闸门

- 目标：完成“需求方案 → 产品原稿 → Mock → 用户确认设计”。
- 验证：用户没有确认设计时，工程 Chat 不可写入代码。
- 回滚点：恢复到只生成需求方案的旧流程。

### Slice B：三工程 Chat 并行

- 目标：设计确认后默认创建前端、后端、联调保障 3 个 Chat。
- 验证：3 个 Chat 同时出现在界面，任务合同和文件边界互不冲突。
- 回滚点：保留单工程 Chat 兼容模式，但默认值仍为 3。

### Slice C：Return、联调和返工

- 目标：三个 Chat 分别 Return，负责人汇总后进行联调和质量验收。
- 验证：单个 Chat 失败时只返工该 Chat，其他通过结果保留。
- 回滚点：停止新一轮返工，不丢失已保存的 Return 和证据。

### Slice D：新手交付

- 目标：不懂代码的用户可以按按钮完成“看方案、看原稿、看 Mock、确认设计、查看 3 个工程 Chat 结果”。
- 验证：用户不需要阅读源码即可找到方案、预览、测试报告和启动方式。
- 回滚点：只回退文案和展示，不影响 Runtime 状态。

## 8. 验收标准

- 产品 Idea 会先生成方案 `.md`，不会直接写前端；
- 产品 Agent 会先生成原稿和 Mock 交互；
- 用户能看到并反馈设计，设计修改会产生新版本；
- 用户确认设计后，默认同时创建 3 个工程 Chat；
- 前端、后端、联调保障职责和文件边界清晰；
- 三个 Chat 可以并行推进并分别 Return；
- 一个 Chat 失败不会导致其他 Chat 重跑；
- 测试 Agent 会对照设计原稿和 Mock 验收，而不是只看代码是否能编译；
- 最终交付包含代码、构建产物、方案 Markdown、设计原稿、Mock 预览、测试报告和使用说明。
