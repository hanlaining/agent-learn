## 三、轨道 A：科研证据闭环 69 → 90+

负责人：科研证据负责人、真实 Provider 授权负责人、外部 baseline 负责人、独立复现负责人。

### A1 固定 candidate 与证据目录

交付物：

- 唯一 candidate ID、commit、操作系统、Node/npm 版本；
- 配置哈希、数据集版本、数据分割、随机种子；
- Artifact manifest、文件字节数、SHA-256、生成时间；
- `Raw → derived → statistics → tables/figures → manuscript` 目录和反向定位。

验收：所有文件可从相对路径复核；不存在临时路径、绝对路径、未声明额外文件和候选漂移。

### A2 真实 Provider 正式实验

交付物：

- 真实 Provider 身份和授权记录；
- 脱敏请求/响应 receipt、采样时间、模型版本、参数和调用计数；
- 正式 Raw、失败调用、重试、限流、超时和负结果记录；
- Raw SHA-256 与 receipt 一一对应。

硬门槛：

```text
real Provider = 1
formal Raw = Included
credentialsRead = false（发布快照不得保存凭据值）
```

本地 Fake Provider、offline deterministic fake、Doctor READY 和 Process Chaos local pilot 均不能计入 A2。

### A3 外部 baseline

交付物：公开来源、论文/仓库/版本、数据集、许可证、比较参数、资源约束、原始输出和统计结果。

验收：每个比较结论可回溯到公开来源和原始运行记录；项目内部对照不得标记为 external baseline。

### A4 独立复现

由第二机器、隔离环境或非作者执行者完成。交付独立环境信息、命令、日志、结果差异、偏差解释和失败记录。

硬门槛：

```text
external baseline = 1
independent reproduction = 1
```

同作者同机器复跑不能计入独立复现。

### A5 统计和证据审计

补齐样本量、纳入/排除规则、均值/方差、置信区间、效应量、异常值处理、多重比较、失败样本处理和预注册成功标准。

验收命令：

```text
npm run test:statistics
npm run test:paper-evidence
npm run test:reproducibility
npm run test:evidence
npm run evidence:verify
```

科研线达到 90+ 的硬门槛：正式 Raw、真实 Provider、外部 baseline、独立复现、核心 Claim 可追溯、`evidence:verify=PASS` 全部满足。

## 四、轨道 B：论文就绪度 47 → 90+

负责人：论文负责人、引用核验负责人、非作者审阅者。

### B1 Claim–Evidence Matrix

每个 Claim 必须记录：Claim ID、正文位置、Raw/Artifact/脚本来源、candidate、样本量、指标定义、统计依据、图表编号、引用定位、限制和状态。

允许状态：`Pending`、`Blocked`、`Verified`。正式证据缺失时必须保持 `Pending/Blocked`，不能提前写 `Verified`。

### B2 正文和图表一致性

- 摘要、方法、结果、讨论、图、表、附录全部使用同一 candidate；
- 结果数字从最终 Artifact 生成或人工逐项核验；
- 删除无来源数字、旧 candidate、旧覆盖率、TODO 和 NotVerified 强结论；
- 方法章节写明环境、参数、随机种子、失败处理、资源约束和限制；
- 讨论章节明确外部 baseline、不可外推结论、成本和威胁有效性。

### B3 一手引用核验

每条关键引用必须有原始论文或官方来源、作者、年份、DOI/HTTPS、页码/章节/段落，并核实来源真正支持正文表述。

### B4 非作者论文级审阅

使用 [PAPER-NONAUTHOR-REVIEW-TEMPLATE.zh-CN.md](./reviews/PAPER-NONAUTHOR-REVIEW-TEMPLATE.zh-CN.md)，由非作者审阅方法、统计、Claim、图表、引用、伦理、限制、复现和全文一致性。

交付审阅原件、问题清单、修改前后差异、P0/P1 关闭记录和审阅人确认。

验收命令：

```text
npm run test:paper
npm run test:paper-consistency
npm run test:paper-evidence
npm run evidence:verify
```

论文达到 90+ 的硬门槛：核心 Claim 100% 有正式证据、关键引用 100% 完成人工核验、TODO/NotVerified=0、图表与 Artifact 100% 一致、非作者审阅完成且 P0/P1=0。

## 五、轨道 C：生产发行成熟度 68 → 90+

负责人：发行负责人、安全负责人、签名环境负责人、干净 Windows 验收负责人、非作者发行复核人。

### C1 依赖和供应链风险

当前 high：`electron`、`extract-zip`、`nanoid`。

必须完成依赖升级/替代/补丁，或取得正式风险接受。未获授权不得修改依赖和 lockfile；在 high 未清零或无正式批准前，`release:check` 必须保持 `BLOCKED`。

### C2 签名发布物

交付 Windows 安装包、签名信息、证书链摘要、SHA-256、签名 receipt、SBOM、构建日志、版本、candidate 和 release manifest。

验收：签名、包 SHA、SBOM、构建输入和 candidate 相互绑定，第三方可独立验证。

### C3 干净 Windows 安装

在无开发依赖、无本机缓存环境完成首次安装、启动、初始化、核心任务、数据目录、权限路径、卸载、残留检查和失败安装恢复；保存环境信息、日志、截图索引和验收签字。

### C4 升级、回滚和数据完整性

验证 N→N+1、升级中断、迁移失败、启动失败、N+1→N 回滚、回滚后数据完整性、再次升级和卸载重装。

必须存在一条完整 receipt 链：

```text
升级失败 → 回滚 → 数据校验 → 恢复运行
```

### C5 长稳与恢复

按项目规定时长运行（当前发行门禁要求 3600 秒 receipt；如要申报更高成熟度可扩展到 24 小时），记录 CPU、内存、磁盘、错误、崩溃、网络中断、子进程退出、lease 超时和恢复结果；由非作者复核。

验收命令：

```text
npm run test:release
npm run test:security
npm run test:sbom
npm run security:scan
npm run release:check
```

发行线达到 90+ 的硬门槛：critical/high=0 或有正式风险接受、签名安装包存在、SBOM/安全扫描通过、干净 Windows 安装通过、升级/回滚通过、长稳 receipt 完整、`release:check=PASS`。
